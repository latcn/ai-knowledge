
> 本章挑战一个被前五章默认接受、却很少被明确说出的假设：**“Agent 思考时，世界是静止的。”**
> 前五章中，Agent 与世界的交互是回合制的。本章要扩展的，不是观察与动作的**内容**，而是它们的**模态**和**时机**。
> 核心议题贯穿：**大模型异步原生化**——异步处理的责任从应用层（Agent 框架）下移到模型服务层（AI Infra）。

## 一、总纲：模态与触发时机的扩展（6.1）

### 1.1 两个扩展方向

| 维度 | 观察空间 | 动作空间 |
|---|---|---|
| **内容（第2-5章）** | 上下文工程、记忆与知识库 | 工具、代码生成 |
| **模态（本章）** | 语音、屏幕、物理传感器 | 说话、点击、关节运动 |
| **时机（本章）** | 世界主动推送、连续流 | 跨回合、可打断、可抢占 |

### 1.2 回合制是接口约定，不是环境性质

- 早期工具调用接口按同步轮次组织消息。
- 真实环境不会等模型作出反应：邮件在思考时到达，用户说到一半插话，页面在两帧之间变了样，杯子在机械臂伸手途中被碰倒。
- 这个约定正在改变：**GPT-6 Astra 已提供原生异步工具调用和回合中途追加用户指令的能力。**
- 本章同时讨论**原生支持**与**兼容既有同步接口**两条路线。

### 1.3 不同时间尺度的交互变化

| 尺度 | 场景 | 观察侧变化 | 动作侧变化 |
|---|---|---|---|
| 秒—天 | 异步与事件驱动 | 会被外部事件主动唤醒 | 动作跨回合：先发起，后续靠事件收尾 |
| 10ms—1s | 语音 | 边说边听，不等一句说完 | 边想边说，可被打断 |
| 亚秒—秒 | Computer Use | 屏幕在两帧之间持续变化 | 动作后必须重新确认现实 |
| 毫秒 | 机器人 | 传感器连续回流 | 动作分块：一次规划一小段，可被抢占 |

### 1.4 核心问题：LLM 单次调用能否被中断？

**结论：计算层面不能中断，但架构层面可以“追加处理”。**

| 层次 | 含义 | 是否可行 |
|---|---|---|
| **计算中断** | 暂停/回退单次前向传播 | 不可行（前向传播是原子性的） |
| **流式中断** | 停止读取流、取消API请求 | 可行（已生成部分不撤销） |
| **架构中断** | 停止当前调用 + 追加事件 + 重新调用 | 可行（书中说的“取消式处理”） |

**关键区分：**

- LLM 是无状态的，每次调用都是独立的。
- 中断不是“修改当前推理”，而是“在下一次调用时使用更新后的上下文”。
- 已生成的内容不会消失，它会成为下一次调用的上下文的一部分。

**费曼式类比：**

> 你在写作文，写到一半，老师说“换个题目重写。”
> - 你不会接着写，而是重新开始。
> - 但之前写的内容（轨迹）还在，你可以参考。
> - 你不是在原来的作文上涂改，而是重新写一篇。

## 二、异步与事件驱动：当世界主动找上门（6.2）

### 2.1 为什么需要异步（6.2.1）

- **同步**：做完一件事才能做下一件（只会排队的柜台）。
- **异步**：多件事可以同时进行（灵活的秘书）。
- 真实助理场景需要三大核心能力：
  1. **异步执行是常态**：长时间任务不应阻塞用户交互。
  2. **事件优先级的动态判断**：取消（紧急）、队列（常规）、并行（独立查询）。
  3. **中断和恢复的流畅性**：被打断的任务应能自然恢复。

### 2.2 OpenClaw 的事件驱动机制（6.2.2）

| 机制 | 作用 | 事件来源 |
|---|---|---|
| Hooks | 响应 Agent 生命周期事件 | 框架内部 |
| Cron | 定时调度 | 时间驱动 |
| Heartbeat | 心跳检查 | 时间驱动 |

**短板**：缺乏即时接入外部事件的通道。PineClaw 引入 **Channel 机制**，在 Gateway 和 Pine API 之间建立实时事件通道，消息即时推送。

**核心启示**：真正的“主动服务”不仅需要 Agent 能定时检查事件，更需要事件能主动通知 Agent。

### 2.3 事件触发工具（6.2.3）

| 工具 | 处理什么 | 典型场景 |
|---|---|---|
| set_timer | 物理时间事件 | 定时任务、循环查询 |
| monitor_shell | 后台任务事件 | 监控命令行输出 |
| connect_channel | 外部事件 | 新邮件、API 回调、IM 消息 |

**设计原则**：清晰的触发条件和过滤规则；事件载荷包含足够上下文。

### 2.4 用户沟通工具（6.2.4）

- **传统 Agent**：一问一答，用户必须打开指定会话。
- **OpenClaw**：异步沟通，用户无需感知会话，Agent 像秘书一样发消息。
- 多模态沟通：结构化卡片、提醒邮件、生成式 UI。
- **设计原则**：支持异步消息模式、已读/未读追踪、多渠道一致性。
- **通知机制 = 用户召回机制**：根据紧急程度、用户状态、内容性质、用户偏好综合决定渠道。

### 2.5 虚拟身份与隔离执行环境（6.2.5）

- **身份选择**：直接管理用户账号 vs 拥有独立虚拟身份（推荐后者）。
- **虚拟身份组成**：专属通讯账号、存储空间、计算环境。
- **隔离执行环境**：虚拟电脑（VM/容器）、虚拟手机（Android 模拟器）。
- **三大好处**：全天候运行、错误隔离、文件隔离。
- **两个挑战**：反机器人机制（住宅代理）、访问用户真实账号（Human-in-the-Loop 认证）。
- **共享文件系统**：以卷挂载方式连接 Agent、虚拟电脑、虚拟手机，传递路径字符串而非内容。

### 2.6 事件处理机制（6.2.6）

- **骨架**：事件循环（event loop）。
- **事件的结构化建模**：来源、渠道、内容、上下文。
- **三种处理策略**：

| 策略 | 适用 | 做法 |
|---|---|---|
| 取消式 | 紧急事件 | 停止当前操作，清空队列，追加事件，重新调用 LLM |
| 队列式 | 常规事件 | 事件入队，等当前操作完成后再处理 |
| 并行式 | 独立查询 | 另起推理会话，独立执行 |

- **紧急度判定**：建议使用轻量级分类 LLM 作为事件路由器。

**优先级判断的三种层次：**

| 层次 | 情况 | 做法 | 成本 |
|---|---|---|---|
| 第一层 | 规则明确能判断 | 直接处理 | 微秒 |
| 第二层 | 规则判断不了，但事件值得花一次 LLM 调用 | 调 LLM 判断 | 毫秒 + token |
| 第三层 | LLM 也判断不了，或事件太多不值得逐个判断 | 默认队列式 | 零成本 |

**关键区别：**

> 第二层是“主动判断”，第三层是“不判断，走默认”。
> 区别不在“不确定”，而在“值不值得花成本判断”。

- **安全点与退回机制**：

**安全点的定义：**

> 一个可以安全地停止当前操作、消费新事件的位置。

**安全点的三个条件：**

| 条件 | 说明 |
|---|---|
| 当前操作可以安全收尾 | 不会留下未完成的中间状态 |
| 轨迹保持完整 | 所有消息都有配对的结果 |
| LLM 可以重新理解 | 新的完整轨迹可以被 LLM 正确解析 |

**安全点的位置：**

| 阶段 | 安全点 | 非安全点 |
|---|---|---|
| LLM 推理 | 一次完整回复生成完毕 | 生成到一半 |
| 工具调用 | 工具执行完成，返回结果 | 工具执行中 |
| 多工具并行 | 所有工具都完成 | 部分完成 |
| 循环 | 一轮循环结束 | 循环中间 |

**“退回到安全点”的含义：**

> 不是回滚计算，而是：停止在安全点之后的新操作，把状态固定在上一个安全点，追加新事件，重新调用 LLM。

**占位符机制：**

> 未完成的工具结果用显式占位符表示，不能伪造成功。
> 模型可能把“任务已启动”误当成“任务已完成”，应通过明确的任务状态和结果校验防止这种混淆。

- **实验 6-1**：事件驱动的邮件处理 Agent。

### 2.7 不支持原生异步时的兼容方案（6.2.7）

- **核心思想**：常态下让 LLM 看到标准同步轨迹，只在打断时插入占位符修复格式。
- **五条关键规则**：
  1. 及时记录已完成的 assistant 消息和工具调用项。
  2. 工具调用完成时才记录 tool result。
  3. 工具执行中的打断需要占位符。
  4. 取消未完成的生成，保留已确认完成的消息。
  5. 非打断事件进入队列等待批处理。
- **任务句柄表达异步语义**：将“启动”和“完成”解耦（如 initiate_phone_call）。
- **队列式处理中的注意力分散**：用状态栏标记和汇总缓解。
- **实验 6-2**：带并行执行和打断能力的异步 Agent。

### 2.8 模型原生异步：GPT-6 Astra（6.2.8）

- **异步工具调用**：将“发起行动”和“获得结果”分开。
- **回合中途引导（Mid-turn Steering）**：用户可以在任务进行中修正方向。

**回合中途引导详细机制：**

```
1. 用户注入指令：通过 WebSocket 发送 response.steer 事件
2. 服务器接受并排队：返回 response.steer.accepted 事件
3. 完成当前原子工作：安全地完成当前输出或工具调用
4. 开启后续响应：创建新响应，包含新指令
```

**关键区分：**

| 概念 | 说明 |
|---|---|
| Steering ≠ 中断重发 | Steering 保留已完成的工作，中断重发则丢弃 |
| Steering ≠ 撤销 | 无法撤销已执行的不可逆操作 |

**限制：**

- 仅 GPT-6 系列支持
- 必须使用 WebSocket 连接
- 仅支持标准单代理模式
- 无法撤销不可逆操作
- 工具结果依赖时，指令保持 pending

**两条路线对比：**

| 维度 | 兼容方案 | 原生异步 |
|---|---|---|
| 控制权 | 运行时 | 模型 |
| 模型视角 | 同步交互 | 异步交互 |
| 代表 | 实验 6-2 | GPT-6 Astra |

- **修改计划 ≠ 停止工具**：实际执行、取消和状态管理仍由运行时负责。
- **并非所有模型都具备原生异步能力**：根据模型支持范围选择原生交互或兼容方案。

### 2.9 从“能接收异步消息”到“可靠处理异步任务”（6.2.9）

- **三个可靠性检查**：
  1. **结果归属与未完成状态**：延迟到达的结果能否归入正确任务，结果缺席时避免编造数据？
  2. **任务恢复与动作控制**：处理新要求后能否继续原任务，区分修改计划与停止执行？
  3. **多条更新的综合使用**：能否同时遵守所有约束，而非只记住最后一条？
- **两条解决路径**：异步环境中的训练、系统改进（清晰的任务状态、事件来源、执行反馈）。
- **评估覆盖两层**：模型是否理解了变化，系统是否按变化正确执行。
- **实验 6-3**：模型原生异步与回合中途引导。

### 2.10 大模型异步原生化：核心议题

#### 2.10.1 从“应用层编排”到“模型原生异步”的范式转变

**旧范式（应用层编排）：**

- 用户主导，用户 push Agent 做事，用户全程参与。
- 异步处理靠应用层编排：多子 Agent 或并行工具调用。
- Agent 框架负责：任务队列、状态管理、事件路由。

**新范式（模型原生异步）：**

- 用户设定目标，Agent 主导，用户仅做确认、审查、核查。
- 模型在处理一个任务时，同时发起另一个。
- 异步处理的责任从应用层（Agent 框架）下移到模型服务层（AI Infra）。

**责任下移的本质：**

| 层次 | 旧范式 | 新范式 |
|---|---|---|
| 决策层 | 模型决定“做什么” | 模型决定“做什么”+“何时做”+“如何处理结果” |
| 编排层 | Agent 框架管理队列、状态、路由 | AI Infra 管理队列、状态、路由 |
| 执行层 | 工具服务执行 | 工具服务执行 |

**费曼式类比：**

> 旧范式：你是一个员工，项目经理（Agent 框架）告诉你“先做 A，再做 B”。
> 新范式：你自己决定“先做 A，同时做 B”。编排的责任从项目经理（应用层）下移到你自己（模型 + AI Infra）。

#### 2.10.2 AI Infra 需要提供的一整套支撑

| 能力 | 说明 |
|---|---|
| 任务生命周期管理 | 注册、状态、查询、取消 |
| 事件队列管理 | 入队、优先级、路由、批量 |
| 状态管理 | 上下文、未完成状态、结果归属 |
| 执行控制 | 并行、取消、超时、熔断 |

#### 2.10.3 上下文分叉与 KV Cache 管理

当任务拆成 A 和 B，B 的上下文依赖关系不同，处理方式不同：

| 依赖类型 | B 是否需要 A 的产出 | 上下文结构 | KV Cache 策略 |
|---|---|---|---|
| **完全并行** | 否 | 树状分叉 | 前缀共享 + 独立分支 |
| **结果依赖** | 是（最终结果） | 串行拼接 | 前缀复用 + 重新 prefill |
| **过程依赖** | 是（中间状态） | 动态拼接 | 状态栏 + 事件推送 |

**场景一：完全并行**

- 公共前缀共享 KV Cache，从分叉点之后各自独立计算。
- 用树状注意力掩码，让 A 和 B 互不可见。
- 费曼式类比：两个学生做同一份试卷的不同部分，共享题干，各自做。

**场景二：结果依赖**

- B 等 A 完成后，把 A 的结果拼接到 B 的上下文。
- A 的 KV Cache 可以复用，B 的 prefill 只需要计算新增部分。
- 费曼式类比：学生 B 等学生 A 做完，看 A 的答案再做。

**场景三：过程依赖**

- A 的中间状态是动态变化的。B 需要实时看到 A 的中间状态。
- 解决方案：用 Agent 状态栏记录 A 的进度，A 的状态变化作为事件推送给 B。
- 关键原则：不要传递完整轨迹，用状态栏代替；动态状态用事件推送。
- 费曼式类比：你监控一个正在跑步的人，只需要看秒表上的数字。

#### 2.10.4 如何保证上下文不浪费？

| 策略 | 说明 |
|---|---|
| **KV Cache 复用** | 保证静态前缀稳定不变，是 KV Cache 复用的关键 |
| **后缀缓存复用** | 当上下文中间被编辑时，可复用编辑后仍存活部分的 KV 状态 |
| **异步 KV 共享** | 在同一 KV Cache 池中交错存储，通过注意力掩码防止线程间干扰 |
| **模型原生上下文管理** | 让模型像编辑文件一样直接重写、删除、重排上下文 |
| **Agent 状态栏** | 用状态栏传递关键状态，而不是把完整轨迹传给另一个子任务 |

#### 2.10.5 主流趋势与 DeepSeek 的实践

**趋势判断：**

- 模型原生异步是当前大模型发展的明确趋势。
- 工业界正从同步的请求-响应模式，转向事件关联的异步 Agent 架构。

**DeepSeek 的实践：**

- DeepSeek V4 Pro 已支持并行工具调用，`parallel_tool_calls` 参数被忽略。
- Harness 实现中，工具可并行运行，但日志必须按模型给出的固定顺序写入。
- Async Engine 层专门负责管理状态、工具调用、流式输出和任务队列。
- 与 GPT-6 Astra 的侧重差异：
  - DeepSeek 更侧重**并行工具调用**的工程可靠性。
  - GPT-6 Astra 更侧重**回合中途引导**，解决“任务执行中，用户如何动态修正方向”的问题。

#### 2.10.6 异步原生化的代价与风险

| 风险 | 说明 |
|---|---|
| 信任成本 | 用户需要信任 Agent 能正确处理任务 |
| 审查成本 | Agent 做了很多事，审查成本可能很高 |
| 理解债 | Agent 交付速度越快，工程师对系统实际实现的理解越落后 |
| 认知投降 | 工程师习惯用 Agent 代劳，逐渐放弃独立思考与审查 |
| 安全风险 | Agent 自主调用资源，一旦被注入或出错，影响面更大 |

**防御体系：**

| 防线 | 说明 |
|---|---|
| 数据层护栏 | 关键事实来自可信数据源，不是模型生成的 |
| 提议者—审核者 | 独立验证，不同模型，独立证据 |
| 用户确认机制 | 确认来自用户本人，服务端记录，不可伪造 |
| 执行层验证 | 确认与实际一致，参数与确认一致 |
| 审计与回滚 | 完整轨迹，可回放，可追溯 |

## 三、语音：最自然的人机接口（6.3）

### 3.1 交互时序：从级联到全双工（6.3.1）

| 范式 | 核心结构 | 优势 | 限制 |
|---|---|---|---|
| 级联 | VAD → ASR → LLM → TTS | 模块清晰、易调试 | 延迟累积，副语言信息丢失 |
| 端到端 Omni | 原生音频输入输出，按轮次 | 延迟较低，保留语气、情绪 | 仍依赖轮次，训练成本高 |
| 全双工 | 原生音频输入输出，持续听说 | 支持重叠说话、自然打断 | 训练、控制、评估复杂 |

**主线**：如何摆脱“轮流说话”和 VAD 对发言权的猜测。

### 3.2 级联流水线（6.3.2）

- 四个模块：VAD、ASR、LLM、TTS。
- 延迟瀑布：最优 0.9s，最差 2.3s。
- 排队延迟：生产环境是空载的 2-5 倍。
- **流式感知四个优化**：ASR 边听边转、LLM 推测执行、LLM 分段输出、TTS 增量合成。
- **声学事件标记**：speak_start/end、interrupt、emotion、laugh、sigh、noise。
- **实验 6-4**：构建传统语音 Agent；**实验 6-5**：使用 Qwen2-Audio 模拟流式语音感知。

### 3.3 端到端全模态模型（Omni）（6.3.3）

- 用一个模型直接听音频、生成回复、输出语音。
- 优势：延迟低、保留副语言信息。
- 局限：仍假设轮流说话，依赖 VAD。
- **实验 6-6**：本地运行 MiniCPM-o 4.5，对比端到端与自级联。

### 3.4 全双工交互模型（6.3.4）

- 不再预设轮次，持续听、持续说，不断决定继续、停顿、打断或调用工具。
- 研究先声：Kyutai 的 Moshi。
- Thinking Machines Lab 的交互模型：微轮次机制，交互性内建在模型中。
- OpenAI GPT-Live：生产规模的全双工，把复杂任务委派给后台模型。

### 3.5 认知时序：实时交互与深度思考（6.3.5）

三种方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| 方案一 | 快思考回应，慢思考回答 | 简单问题过度思考，快慢不一致 |
| 方案二 | 快思考交互，慢思考提醒 | 沟通间接模糊，无法边想边说 |
| 方案三 | 端到端思考与表达统一 | 训练成本高，升级需重新训练 |

- **快慢分离 vs 统一**：快慢分离能直接承接慢模型的迭代红利，Pine AI 用此架构拿到 τ³-Voice Leaderboard 第一。
- **“端到端模型”的两个含义**：语音通路的端到端、认知架构的端到端。两条轴彼此独立。

### 3.6 更像人的语音合成（6.3.6）

- 传统 TTS 过于流畅、零停顿，反而暴露机器身份。
- 停顿、填充词、重复是人类表达不确定性的信号。
- **控制标记**：THINKING、EMO:happy、SPEED:0.8x、LAUGH、SIGH。
- 两种实现：自研支持控制标记的 TTS、语音克隆 + 多参考音频。
- **实验 6-7**：基于 Fish Audio 的控制标记驱动 TTS。

## 四、Computer Use：GUI 自动化 Agent（6.4）

### 4.1 核心循环

1. 截图
2. 多模态模型接收截图和任务指令，输出思考和动作
3. 执行层在真实环境中执行动作
4. 等待界面响应后再次截图

**关键区分**：“看懂界面” vs “完成任务”。难点在于每一步之后重新确认现实是否仍符合计划。

### 4.2 动作空间设计（6.4.1）

三类工具：
- **GUI 操作工具**：鼠标、键盘、滚动。
- **感知动作**：截图、获取光标位置、等待。
- **命令执行工具**：bash 终端会话，120 秒超时，保持环境状态。
- **文件编辑工具**：str_replace_editor，字符串匹配安全编辑。
- **实验 6-8**：运行 Computer Use（Anthropic 参考路径或开放模型路径）。

### 4.3 视觉定位（Grounding）（6.4.2）

三条路线：

| 路线 | 做法 | 适用 |
|---|---|---|
| DOM/Accessibility Tree 索引 | 读取结构化信息 | 结构化信息可得 |
| Set-of-Mark（视觉标注） | 分割模型切区域 + 编号 | 结构化信息不可得 |
| 纯坐标预测 | 直接输出坐标 | 做过 GUI 定位训练的模型 |

**SoM 不完整时的混合策略：**

```
第一层：尝试 DOM/Accessibility Tree
第二层：尝试 SoM 视觉标注
第三层：回退到坐标预测
第四层：人工介入
```

- **分辨率问题**：按宽高比选目标分辨率，避免非等比拉伸。
- **实验 6-9**：使用 browser-use 实现自动浏览器操作。

### 4.4 能看动画、能听声音的 Computer Use Agent（6.4.3）

- **观察接口（AOI）**：屏幕关键帧截图、音量门控语音转写、用文字描述画面。
- 把连续环境观察转换成模型便于处理的离散事件。

### 4.5 Computer Use 的世界模型（6.4.4）

- 核心公式：桌面状态 + click/type/scroll/wait → 下一状态的表示。
- 用途：动手前比较候选动作、执行时对照预测与真实观察、训练时学习状态变化。
- **Photon-1**：3 万小时 H200，离散潜在 token，预测下一状态表示。

### 4.6 移动端：生态壁垒比技术更难（6.4.5）

- 技术差异：动作空间从鼠标+键盘变成 AccessibilityService，交互方式从鼠标变成触摸手势。
- **真正障碍**：生态壁垒。商业模式冲突：平台靠流量和注意力变现，Agent 绕过变现链路。
- 结构性利益冲突：技术对抗可以绕过，商业模式冲突难以调和。

**小米/华为引入大模型的战略分析：**

| 维度 | 小米 | 华为 |
|---|---|---|
| 核心逻辑 | 以“人车家”生态为场景 | 以“鸿蒙”原生底座为根基 |
| 优势 | 硬件场景丰富，用户基数庞大 | 技术壁垒深厚，系统级整合能力强 |
| 挑战 | 技术栈相对分散，整合难度高 | 生态建设投入巨大 |
| 战略意义 | 争夺AI意图的入口主权 | 实现自主可控 |

**根本原因**：硬件红利见顶，必须寻找新的增长引擎。从卖硬件，转向卖AI Agent驱动的服务。

## 五、机器人操作：以 XLeRobot 整理桌面为例（6.5）

### 5.1 硬件与算法的分工（6.5.1）

- 核心诊断：**硬件本体不是瓶颈，算法才是瓶颈**。
- 遥操作既是数据收集，也是“固定硬件、替换操作者”的诊断实验。
- **实验 6-10**：真机遥操作；**实验 6-11**：模拟器中的理想控制上限。

### 5.2 机器人控制的基本结构（6.5.2）

| 层级 | 核心问题 | 时间尺度 |
|---|---|---|
| 任务目标 | 人想完成什么 | 分钟级 |
| 长程规划 | 先做什么、后做什么 | 秒到分钟 |
| 基本技能 | 当前要完成哪个状态变化 | 约 1—3 秒 |
| VLA / 技能策略 | 这个技能具体怎么动 | 约 1—10 Hz |
| 底层控制与安全层 | 如何稳定、及时地执行 | 约 50—1000 Hz |

- 把“任务顺序”和“眼前动作”分开。

### 5.3 长程规划与任务分解（6.5.3）

- 分解示例：处理红色杯子 → 清理黄色纸张 → 检查桌面。
- 每完成一个技能，得到一个可检查的节点。
- **实验 6-12**：使用 Gemini Robotics-ER 1.5 驱动 XLeRobot 自主整理桌面。

### 5.4 VLA 控制（6.5.4）

- 当前观察 + 技能指令 → 动作。
- 两条路线：离散 token（RT-2、OpenVLA）、连续轨迹（π₀）。
- **动作分块**：在平滑性与反应速度之间取舍。

**动作分块的效率 vs 响应速度：**

| 分块长度 | 平滑性 | 反应速度 | 适用场景 |
|---|---|---|---|
| 短（1-3 步） | 低 | 高 | 动态环境 |
| 中（5-10 步） | 中 | 中 | 一般场景 |
| 长（20-25 步） | 高 | 低 | 静态环境 |

**自适应分块方案：**

```
1. 初始分块：中等长度（5-10 步）
2. 执行中监控：如果环境稳定，继续执行；如果环境变化，缩短分块，重新规划
3. 动态调整：静态环境长分块，动态环境短分块
4. 安全停止：如果检测到异常，立即停止
```

### 5.5 VLA 的局限（6.5.5）

- 训练数据有限、只学会模仿不一定懂后果、机器人各不相同、观察可能过时。
- VLA 回答“现在应该做什么”，世界模型回答“做了之后可能发生什么”。

### 5.6 世界模型（6.5.6）

- 核心公式：当前状态 + 候选动作 → 预测下一状态 → 比较候选结果 → 选择动作。
- 三种用法：动手前、执行时、训练时。
- 预测只能帮助选择，不能代替验收。

**世界模型预演机制：**

```
当前状态 + 候选动作 → 世界模型预演 → 预测下一状态 → 比较候选结果 → 选择最优动作 → 真实执行 → 观察确认
```

**具体例子（XLeRobot 整理桌面）：**

| 候选 | 说明 | 世界模型预测 | 决策 |
|---|---|---|---|
| A：先抓纸 | 直接抓纸 | 杯子可能被碰倒（风险高） | 拒绝 |
| B：先移动杯子 | 先移开杯子，再抓纸 | 杯子移到旁边，纸变得可抓取（风险低） | 接受 |
| C：换一个抓取方向 | 从另一个方向抓纸 | 可能抓不到纸（风险中） | 备选 |

**关键原则：**

> 世界模型预演是“选择”的工具，不是“验收”的工具。
> 预测只能帮助选择，不能代替真实执行后的观察确认。
> 预演成功 ≠ 真实成功。

- **实验 6-13**：在模拟器中比较三种自主整理桌面的闭环（开环、逐步检查、预测式执行）。

### 5.7 从仿真环境到真实机器人（6.5.7）

- 差异来源：背景、光照、相机位置、遮挡、摩擦、传感器噪声、执行器延迟。
- **领域随机化**：在物理参数、视觉外观、传感器噪声等方面引入大范围随机变化。
- **实验 6-14**：同一桌面任务的 RGB 跨环境测试。

## 六、快速交互如何保证不导致无法挽回的后果

### 6.1 不可逆操作的分类

| 类型 | 例子 | 为什么不可逆 |
|---|---|---|
| 物理不可逆 | 删除文件、撕毁纸张 | 无法恢复 |
| 时间不可逆 | 发送邮件、拨打电话 | 已发出，无法收回 |
| 资金不可逆 | 转账、支付 | 已转出，无法追回 |
| 状态不可逆 | 提交表单、确认订单 | 已提交，无法撤销 |
| 物理世界不可逆 | 机器人碰倒杯子 | 杯子已碎 |

### 6.2 五层防御体系

| 防线 | 说明 | 例子 |
|---|---|---|
| **预演（世界模型）** | 在执行前，先在模拟环境中预演 | 删除文件前，预测后果 |
| **快照（可回滚）** | 在执行前，先保存状态快照 | 数据库事务、Git commit |
| **HITL（人工确认）** | 关键不可逆操作，必须人工确认 | 转账需用户点击确认 |
| **延迟执行（撤销窗口）** | 给用户一个“撤销窗口” | Gmail 发送后 30 秒内可撤销 |
| **权限控制** | 不可逆操作需要更高权限 | 删除文件需要高权限 |

### 6.3 三个场景的具体表现

| 场景 | 快速交互 | 安全措施 |
|---|---|---|
| 语音 | 说错了再纠正 | 可逆操作（“撤销”） |
| Computer Use | 先点再看 | 状态确认（点击后截图） |
| 机器人 | 走一步看一步 | 安全停止（急停） |

## 七、本章小结（6.6）

### 7.1 四种场景的时间尺度

| 场景 | 时间尺度 | 核心变化 |
|---|---|---|
| 异步 | 秒—天 | 世界主动推来，动作跨回合 |
| 语音 | 10ms—1s | 边说边听，边想边说 |
| Computer Use | 亚秒—秒 | 屏幕持续变化，动作后重新确认 |
| 机器人 | 毫秒 | 传感器连续回流，动作分块 |

### 7.2 共享的控制骨架

```
持续感知 → 判断当前状态与时机 → 选择回复或动作 → 让输出进入环境 → 观察反馈 → 继续、修正、重试、停止或重新规划
```

### 7.3 共享的原语

唤醒、安全点、取消、抢占、快慢分离。

**安全点在不同时间尺度上的实现差异：**

| 维度 | 事件驱动（秒—天） | 机器人动作分块（毫秒） |
|---|---|---|
| 安全点定义 | 一轮循环结束 | 一个动作块结束 |
| 安全点频率 | 秒到分钟 | 毫秒到秒 |
| 检查方式 | 检查事件队列 | 检查传感器状态 |
| 停止方式 | 取消 LLM 调用 | 发送急停信号 |
| 恢复方式 | 追加事件，重新调用 | 重新规划，继续执行 |

**差异的决定因素：**

| 因素 | 事件驱动 | 机器人 |
|---|---|---|
| 环境变化速度 | 慢（秒到天） | 快（毫秒） |
| 动作可逆性 | 高（可以撤销） | 低（物理动作不可逆） |
| 观察获取成本 | 低（事件队列） | 高（传感器） |

> 差异主要由**环境变化的速度**和**动作的可逆性**决定。环境变化越快、动作越不可逆，安全点越频繁，停止越紧急。

本章完成了“构建 Agent”这一部分的最后一块：观察与动作空间在内容、模态和时机三个方向上都已经展开。接下来：

- 第10章：在完整的单 Agent 基础上转向多 Agent 协作。

## 八、思考题核心解答

1. **优先级判断**：分层路由——规则引擎处理明确情况，轻量 LLM 处理模糊情况，默认策略兜底。第二层是“主动判断”，第三层是“不判断，走默认”。区别在“值不值得花成本判断”。
2. **20 个事件组织**：编号 + 分类 + 汇总 + 显式要求，末尾强制汇总，明确要求涵盖所有关键信息。
3. **身份选择**：虚拟身份优先，高风险场景用 HITL 认证。
4. **端到端可观测性**：旁路记录、关键帧采样、对比调试、可回放。
5. **边想边说**：保留有益特征（填充词、自我纠正、停顿），避免有害特征（未深思熟虑的话）。
6. **SoM 不完整**：混合策略——DOM → SoM → 坐标预测 → 人工介入。
7. **遥操作数据质量**：自动筛选（平滑度、时间、成功率、路径）+ 多操作者对比 + 人工抽检。
8. **统一 vs 快慢分工**：快慢分工更务实，能承接模型迭代红利。混合架构：简单任务统一，高风险任务快慢分离 + HITL。
9. **纯视觉 vs 双路径**：双路径 + 自动切换。维护成本高，但通用性和准确性兼顾。
10. **动作分块**：自适应分块 + 动态调整 + 安全停止。静态环境长分块，动态环境短分块。
11. **快速交互安全**：五层防线——动作分级、可逆操作、状态确认、权限控制、安全停止。不可逆操作需要预演、快照、HITL、延迟执行、权限控制。
12. **安全点差异**：由环境变化的速度和动作的可逆性决定。环境变化越快、动作越不可逆，安全点越频繁，停止越紧急。

## 九、全章核心原则

> **第6章挑战的是“Agent 思考时世界静止”这个默认假设。**
> **观察空间和动作空间各有两个扩展方向：模态与时机。**
> **回合制是接口约定，不是环境性质。真实世界不会等模型作出反应。**
> **不同时间尺度下，交互方式不同：异步（秒—天）、语音（10ms—1s）、Computer Use（亚秒—秒）、机器人（毫秒）。**
> **大模型异步原生化是本章核心议题：异步处理的责任从应用层（Agent 框架）下移到模型服务层（AI Infra）。**
> **模型原生异步需要 AI Infra 提供一整套支撑：任务生命周期管理、事件队列管理、状态管理、执行控制。**
> **上下文分叉与 KV Cache 管理：完全并行用树状 KV Cache，结果依赖用前缀复用，过程依赖用状态栏 + 事件推送。**
> **LLM 单次调用在计算层面不能中断，但架构层面可以“追加处理”：停止当前调用 + 追加事件 + 重新调用。**
> **安全点是“可以安全停止、消费新事件的位置”；退回到安全点不是回滚计算，而是停止在安全点之后的新操作。**
> **不可逆操作需要五层防御：预演、快照、HITL、延迟执行、权限控制。**
> **世界模型预演是“选择”的工具，不是“验收”的工具。**
> **四节共享同一条控制骨架：持续感知 → 判断 → 选择 → 输出 → 观察 → 继续/修正/停止。**
> **也共享同一组原语：唤醒、安全点、取消、抢占、快慢分离。**
> **本章完成了“构建 Agent”这一部分的最后一块：观察与动作空间在内容、模态和时机三个方向上都已经展开。**
