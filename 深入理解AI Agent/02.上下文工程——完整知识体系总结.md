## 一、本章定位与主线

### 1.1 上下文工程是什么

第一章把上下文比作 Agent 的“眼睛”：Agent 只能基于它看到的信息做决策。上下文的设计和管理称为**上下文工程（Context Engineering）**。

从 Harness 工程视角看，上下文工程是 Harness 中“上下文与工具”层面的核心实现，决定 Agent 在每个决策点能看到什么信息、以什么结构看到。

### 1.2 本章主线

> **上下文工程的主线是显式管理信息：API 消息结构定义骨架；稳定前缀提高 KV Cache 命中；Prompt、Skills 和状态栏分别承载规则、按需知识与当前状态；压缩则在保留决策、约束、失败和来源的前提下，提高历史信息密度。**

本章处理一次任务之内的状态更新与上下文腐化。下一章把同一思路扩展到跨任务的用户记忆和共享知识库。

### 1.3 核心结构

```
Agent 的上下文 = 静态前缀 + 轨迹
```

- **静态前缀**：System Prompt + Tool Definitions，每一轮不变。
- **轨迹**：user / assistant / tool 消息历史，随交互不断增长。

## 二、2.1 上下文：决定 Agent 能力上限的关键

### 2.1.1 核心矛盾：模型很强，但 Agent 常让人失望

大语言模型在标准测试中成绩亮眼，但进入实际业务场景却常常让人失望。原因是模型要执行具体任务，需要通用模型根本不知道的背景信息：产品架构、业务规则、内部约定、环境配置等。

**费曼式类比**：一位天才工程师加入团队，理论功底深厚、编程能力卓越，但对产品架构、业务逻辑、技术债务、团队规范一无所知；关键架构决策散落在不同成员记忆中，代码库缺乏文档。这位天才即便智力超群，也难以发挥真正价值——这正是当前 AI Agent 面临的困境。

### 2.1.2 Coding Agent 的例子

同样是“帮我修复这个 bug”，Agent 拿到的上下文质量直接决定能否完成任务。三类信息构成最低信息需求：

| 信息类型        | 内容                           | 缺失后果                   |
| ----------- | ---------------------------- | ---------------------- |
| **实时代码上下文** | 目录结构、模块职责、核心数据结构、代码规范        | 代码语法正确但风格格格不入，甚至引入架构冲突 |
| **流程规范**    | Git 分支策略、提交规范、代码审查、CI/CD 要求  | 可能直接往主分支提交未经测试的代码      |
| **环境信息**    | 开发环境配置、测试数据库地址、部署方式、API 密钥管理 | 本地能跑通，测试环境立刻崩溃         |

**关键区分**：进入上下文的是对环境的观察、描述或配置，而不是环境本身；Environment 仍是与 Agent 交互的外部对象。

### 2.1.3 核心结论：上下文质量 > 模型智力

> 模型本身的智力只是基础，**上下文的质量才是 Agent 能力的真正关键**。一个中等能力的模型配上精心组织的上下文，往往能胜过顶级模型在信息匮乏下的盲目摸索。

**上下文工程的定义**：不是往 prompt 里多塞信息，而是**系统性地设计、组织和提供 AI 完成任务所需的全部背景知识**。

### 2.1.4 不只是技术问题，更是组织问题

大多数团队的关键知识都是**隐性的**：架构决策只有老员工记得，业务规则靠口口相传，重要背景信息锁在私聊记录里。

> 如果团队本身就是一个信息黑洞，再好的 AI Agent 也无计可施。

**对远程工作友好的团队往往也对 AI Agent 友好。** Linux 内核分布在全球的开发者协作维护三十多年，秘诀是高度透明、文档驱动的沟通文化。这种工作方式天然创造了对 AI 友好的环境：信息是公开的、可检索的、结构化的。

> AI Agent 就像一个永远的新员工：给足背景信息，它能干得很好；什么都不告诉它，再聪明也是白搭。所以构建 AI 原生团队，首先是一场**文档化运动**。

### 2.1.5 翁家翌的洞察

OpenAI 研究员翁家翌总结：“人和模型一样，最重要的是 Context。”

- “自己在 OpenAI 的工作也没有那么难，如果换一个其他人，如果有他所有的 context，也是能干的。”
- 决定 Agent 在业务中发挥价值的往往**不是模型参数量**，而是它在每个决策点能获得多么**丰富、精准的上下文**。
- “团队合作中最大的问题也是 context 的不一致。”
- “AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里面。”

### 2.1.6 ReAct 的奠基性定义

ReAct 论文开篇把 Agent、Environment、Context 和 Action 的关系连了起来：

> Agent 的下一步行动取决于**截至当前的完整交互上下文**，而不只是眼前这一条输入。

对 LLM Agent 来说，用户消息和工具执行结果是环境返回的观察，模型回复和工具调用请求是 Agent 已经采取的行动；这些观察与行动交替累积，就形成交互历史。由于模型 API 本身是**无状态**的，每次调用时都必须由 Agent 框架**重新构造足够的上下文**。

**核心问题**：后文所有上下文布局、状态栏和压缩技术，都可以看作在回答同一个问题：**怎样以更低成本向模型提供一个信息充分的 \(c_t\)？**

## 三、2.2 Agent 如何调用大模型：理解 API 的上下文结构

### 3.1 消息的四种角色

| 角色 | 名称 | 来源 | 说明 |
|---|---|---|---|
| **system** | 系统提示词 | 开发者编写 | 定义 Agent 身份、行为规则、约束条件。模型视为最高优先级。通常只有一条，放在最前面 |
| **user** | 用户消息 | 终端用户 | Agent 需要响应的请求 |
| **assistant** | 助手消息 | 模型之前的回复 | 包括文本回复和工具调用请求。多轮对话中会被放回消息列表 |
| **tool** | 工具结果 | Agent 框架 | 执行工具后，将结果以 tool 角色消息送回模型。通过 `tool_call_id` 与对应工具调用关联 |

此外，工具定义（tools）作为请求的独立字段，不是消息角色。

**与第一章“上下文五个组成部分”的对应**：  
“四种消息角色 + tools 字段”恰好覆盖第一章所说的五个上下文组成部分。

### 3.2 单轮对话

请求只包含 system + user，模型返回 assistant 消息。

> 每次调用都是无状态的，所有模型需要的信息必须在请求的消息列表中完整提供。

### 3.3 带工具调用的多轮交互：Agent 的核心循环

**第一次 API 调用**：
- Agent 框架发送 system + user + tools。
- 模型返回 `tool_calls`，包含工具名和参数。
- **关键：模型只发出调用请求，真正执行工具的是 Agent 框架。**

**Agent 框架执行工具，发起第二次 API 调用**：
- 完整对话历史 + tool 结果一起发送。
- 三个关键细节：
  1. 第二次请求包含第一次全部对话历史。
  2. 第一次的 assistant 消息被原样放回。
  3. tool 消息通过 `tool_call_id` 与对应工具调用关联。

**模型根据工具结果生成最终回复**：
- 模型不再返回 `tool_calls`，直接给出文本回复。
- 这就是 **ReAct 循环在 API 层面的具体实现**。

### 3.4 用代码实现 Agent 的核心循环

核心就是一个 while 循环：
- 模型返回 `tool_calls` → 执行工具并继续循环。
- 没有 `tool_calls` → 输出结果并退出。
- `messages` 列表不断增长。

**核心结论**：
> Agent 框架的核心工作就是**管理这个 messages 列表**——在合适的时机往里追加消息，然后把整个列表送给模型。本章后续所有上下文工程技术，本质上都是在**优化这个列表的内容和结构**。

### 3.5 从 API 视角看上下文的构成

```
Agent 的上下文 = 静态前缀 + 轨迹
```

| 部分 | 内容 | 特点 |
|---|---|---|
| **静态前缀** | System Prompt + Tool Definitions | 整个对话过程中保持不变 |
| **轨迹** | 对话历史（user + assistant + tool） | 随交互不断增长 |

> 这个“静态前缀 + 轨迹”的结构，是后续讨论 **KV Cache 优化、上下文压缩**等技术的基础——理解了这个结构，就能理解为什么“**前面不能动、后面可以压缩**”。

### 3.6 实验 2-1：本地 LLM 服务部署与工具调用

**五个观察点**：
1. **小模型的能力**：0.6B 模型在适当提示工程下也能准确理解并执行工具调用。
2. **性能表现**：苹果 M2 芯片上，每秒超过 100 个 token。
3. **ReAct 循环**：多轮思考和工具调用解决复杂问题。
4. **流式响应的优势**：实时看到模型的思考过程。
5. **KV Cache 的影响**：修改系统提示词后首次响应变慢。

**关键发现**：
- 模型的内部思考过程（`<think>` 标签）对调试非常有价值。
- 输出顺序：内部思考 → 文本回复 → 工具调用请求。
- 并行工具调用：无依赖关系的工具可并行执行。
- 模型的终止判断：够了就直接输出最终回复，不够就继续输出新的工具调用请求。

**实验总结**：
> 0.6B 的小模型在合理的提示词设计下也能可靠地完成工具调用。端侧 Agent 的时代比大多数人预期的更近。

## 四、2.3 KV Cache 友好的上下文设计

### 4.1 核心直觉：KV Cache 是什么？

模型每生成一个 token，都要回头看一遍前文所有 token 的中间计算结果。如果每轮都从头算一次，开销会随上下文长度**爆炸式增长**。KV Cache 的做法是：**把前文的中间计算结果缓存下来，下一轮只需要计算新增 token 的部分。**

**前提条件**：
> 要复用的上下文 token **前缀保持不变**——若 token 序列从某个位置开始不同，首个不同 token 及其后的 KV 状态需要重新计算。

**费曼式类比**：
> 你在读一本书：没有 KV Cache，每读一个新句子都要把前面所有句子重新读一遍；有 KV Cache，你把之前读过的内容记在笔记本上，读新句子时只需看笔记本 + 新句子。但前面的内容不能改。

### 4.2 核心故事：一行时间戳的代价

某团队客服 Agent 在系统提示词里加了一行 `Current time: {{now}}`。第二天：首 token 延迟从 0.5 秒涨到 3-5 秒，月度推理账单几乎翻了一倍。

**原因**：
> 那一行时间戳使每次请求的 token 序列**从时间戳所在位置开始不同**，因此该位置及其后的 KV 状态无法复用。

**核心教训**：
> 开发者写下的一行看似无害的代码，可能让整条推理链路**慢一个量级**。

### 4.3 三条核心结论（必记）

1. **系统提示词和工具定义一旦确定就不要改。** 任何改动，哪怕多一个空格，都可能改变 token 序列。
2. **动态信息永远追加到末尾。** 时间戳、用户状态等变化的内容，作为新消息追加到对话末尾。
3. **使用标准 API 格式，不要自行拼接消息。** 结构化消息会被 Chat Template 翻译成固定 token 序列；自行拼接会削弱模型的多步思考能力。

### 4.4 注意力机制可视化（实验 2-2）

**三类向量（表 2-1）**：

| 向量 | 含义 | 例子 |
|---|---|---|
| **Query（查询）** | 当前词发出的“搜索请求” | “怎么样”问：哪个词和我最相关？ |
| **Key（键）** | 每个词的“标签”，用于被搜索匹配 | “北京”的标签偏向“地名” |
| **Value（值）** | 每个词的“内容”，匹配成功后被提取 | 匹配到“天气”后，提取它的语义信息 |

**计算过程**：
1. 生成 Query 向量。
2. Query 与每个词的 Key 做点积，得到注意力权重。
3. 用权重对所有词的 Value 加权求和。

**注意力热力图的四个关键模式**：
1. **注意力储存池**：第一个 token 吸收异常高的注意力权重（有时超过 70%），是 softmax 数学特性的必然结果。
2. **思考的三角形模式**：思维链频繁“回看”之前的思考内容和工具定义。
3. **输出的三角形模式**：用思考过程作为提示来输出回答。
4. **位置偏好**：开头和结尾的注意力更高，中间容易被忽视。

### 4.5 Chat Template（2.3.1）

**核心定义**：
> API 层面的结构化消息需要被转换为模型能理解的线性 token 流——负责这个转换的就是 Chat Template。

**费曼式类比**：
> 可以把 Chat Template 想象成信封格式：API 消息是信的内容，Chat Template 规定了如何在信封上写明寄件人、收件人。

**两个实用价值**：

**第一，解释了为什么必须使用标准 API 格式。**
- 如果绕过 API 自行拼接消息，Chat Template 会误将工具响应识别为新的用户查询，导致模型的思维链保留机制被破坏。
- 不同模型家族对历史思维链的处理策略差异很大：
  - DeepSeek R1：剥离全部历史思考。
  - DeepSeek V4：只要携带 tools 参数，两个 user 消息之间的每条 assistant 消息都必须原样回传 `reasoning_content`，否则 API 返回 400 错误。
  - Kimi K2、GLM-5：采用与 DeepSeek V4 相同的协议。
  - Claude：要求客户端在工具调用循环中把 thinking block（带签名校验）原样回传。

**第二，解释了 KV Cache 为什么对前缀如此敏感。**

### 4.6 KV Cache 的原理与约束（2.3.2）

**没有 KV Cache 时**：
- 每生成一个新 token，都需要重新计算整个前缀的 K、V 向量。
- 累计计算量与 N² 成正比。

**使用 KV Cache 时**：
- 每个 token 的 K、V 只在第一次进入上下文时计算一次。
- 省去的是历史 token 的 K、V 投影重算。
- 但每个新 token 的注意力计算仍要遍历全部缓存的 K、V，计算量随上下文长度**线性增长**。

**为什么修改前缀会导致变动点后的缓存失效？**
- 大语言模型由多层 Transformer 堆叠而成，层是串联的。
- 如果第 k 个 token 发生变化，k 之前的状态不受影响，但从 k 开始的表示会逐层受到影响。

### 4.7 KV Cache 与 Prompt Cache：两个层级的缓存（2.3.3）

| 概念 | 作用层级 | 说明 |
|---|---|---|
| **KV Cache** | 模型内部机制 | 在一次推理过程中，缓存已计算的 token 的键值对 |
| **Prompt Cache** | 推理引擎的优化 | 在多次 API 请求之间缓存相同前缀的计算结果 |

**成本对比**：
> 缓存读取的成本远低于首次计算，例如 Anthropic、DeepSeek、GPT-5 约为**十分之一**。

### 4.8 缓存作为架构约束（2.3.4）

**Claude Code 的三个实践**：
1. **提示词的结构由缓存边界决定。** 系统提示词被缓存边界分为两部分，标记之前的内容跨用户、跨会话全局缓存。
2. **子 Agent 必须与父 Agent 字节级对齐。**
3. **工具结果的替换字符串在首次出现时就被冻结。**

**核心启示**：
> 缓存经济性不是事后优化，而是**前置约束**。

### 4.9 KV Cache 未必是一次性的（2.3.5）

> 在 prefill 阶段，模型其实在“做笔记”。一个字段自己那几个 token 的 KV，对最终决策的贡献往往不到 1%——真正影响输出的，是它在下游留下的那些“读书笔记”。

**两种操作**：
- **编辑（Editing）**：改掉一个字段后，只要模型有显式的 CoT，就能让改动顺着已缓存的思考传播。
- **组合（Composition）**：把预先算好的缓存，通过 RoPE 重定位，直接拼接进另一段上下文。

**论文数据**：
> 首 token 延迟（p90）最多降低数十倍至数百倍，前缀缓存命中率约 98.5%。

**注意**：这仍属研究阶段。

### 4.10 实验 2-3：常见的错误上下文管理模式

| 错误模式 | 问题 | 正确做法 |
|---|---|---|
| **动态系统提示词** | 时间戳等动态信息嵌入系统提示词，破坏缓存 | 作为用户消息追加到对话末尾 |
| **动态用户配置模式** | 更新用户状态信息破坏缓存 | 通过专门的状态管理机制处理 |
| **工具定义的动态排序** | 改变顺序让缓存失效 | 保持固定顺序 |
| **滑动窗口对话历史** | 破坏前缀一致性，可能丢失关键工具结果 | 使用压缩而非丢弃 |
| **文本格式化方法** | 偏离模型训练格式，削弱多步思考能力 | 使用标准 API 格式 |

## 五、2.4 提示工程：优化系统提示词

### 5.1 语气与风格

- 限制回复长度：“You MUST answer concisely with fewer than 4 lines”
- 控制失败回复：“keep your response to 1-2 sentences”
- 大写强调：“NEVER do X” 比 “Please avoid doing X” 更能引起模型注意。

### 5.2 结构化提示

- **XML 标签**：层次化原则，标签名称携带语义信息。
- **Markdown**：保持可读性，提供轻量级结构。
- **XML + Markdown 双层结构**：XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织逻辑。

### 5.3 流程驱动 vs 规则堆砌

- 流程驱动的提示词像一份优秀的新员工培训手册，提供清晰的标准操作流程（SOP）。
- 模型在任何时刻都能清楚地知道自己处于哪个阶段、当前步骤的目标是什么。
- 遇到异常时，模型可以根据当前阶段确定处理方式。

### 5.4 业务规则细化

- 这不是技术问题，而是产品设计问题，需要产品经理的深度参与。
- 案例：打电话处理账单的 Agent，三种计费模式。
- 模糊规则会导致行为极不稳定。
- 产品经理必须将决策规则明确到可执行的程度。
- 核心设计哲学：大语言模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多的自由裁量权。

### 5.5 Few-shot 示例

- 适合：期望的输出难以用规则精确描述。
- 工程决策点：
  - 示例放在哪里：系统提示词中 / 伪造 user/assistant 消息放在首轮。
  - 对 KV Cache 前缀稳定性的影响：固定示例集，不逐请求挑选。
  - 示例数量：两三个精心挑选、覆盖边界情况的示例。

### 5.6 工具定义的设计

- 使用边界：“NEVER invoke grep or rg as a Bash command”
- 具体示例：`timezone: 'America/New_York'`
- 性能提示：“Batch your tool calls together”
- 工具间协作关系：“Use the Read tool at least once before editing”
- 2026 年以来，工具定义向渐进式披露演进：静态前缀只保留名称和简述，完整 schema 按需注入。
- 为什么追加到末尾不破坏缓存？因果注意力决定每个 token 的键值对只依赖它之前的 token。
- “追加到末尾”只发生在工具被发现的那一轮。此后 schema 块固定在轨迹中的原位置。

### 5.7 提示注入：上下文安全的核心威胁

- 本质：攻击者通过外部内容将伪装成系统指令的文本混入上下文。
- 在 Agent 中更危险：Agent 拥有工具调用能力。
- 上下文层的三种防御：
  - 来源标记
  - 结构化角色
  - 输入清洗
- 新的注入面：Skill 机制、Agent 状态栏。
- 分层防御原则：上下文层防御只是第一道防线。

### 5.8 实验 2-4：提示工程的消融实验

- 维度一：语气与风格——对任务完成率影响有限。
- 维度二：信息组织——成功率下降超过 **30%**。
- 维度三：工具描述——错误率增加 **45%**。

### 5.9 实验 2-5：提示注入攻防实验

- 攻击场景：直接注入、间接注入、记忆注入。
- 防御策略：无防御基线、提示词警告、来源标记、组合防御。
- 验收标准：记录每种攻击在不同防御配置下的成功率。

## 六、2.5 动态提示词与 Agent Skills

- 对 KV Cache 友好并非零成本。

### 6.4 Skills 与工具的关系

## 七、2.6 Agent 状态栏：通过元信息增强 Agent 轨迹管理

### 7.1 为什么需要状态栏

Agent 执行复杂任务时容易陷入无限循环、状态遗忘、目标偏离，根源在于缺乏对环境当前状态的感知和对任务进展的跟踪。状态栏通过在上下文中嵌入结构化元信息，为 Agent 补上自我感知和自我调节的机制。

**类比**：操作系统的状态栏——时间、电量、信号、通知数量，随时瞥一眼就掌握设备状态。

### 7.2 理论基础

上下文学习更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和总结。上下文窗口是一台只有一半的检索引擎：检索强，提炼弱。原始轨迹中的信息高度冗余，模型每次决策都要花费额外思考 token 去扫描上下文重新统计。

状态栏把分散在上下文各处的隐式状态提炼为可直接使用的显式知识，以极低的额外 token 成本，呈现原本需要扫描数千个 token 才能获得的信息。

此外，长上下文中注意力资源有限，关键信息容易被淹没。状态栏放在上下文末尾，紧邻模型即将生成的新 token，获得更高注意力权重——这是一种“强制性的注意力引导”。

### 7.3 构成

- **任务规划**：TODO 列表，任务分解为清晰步骤，放在轨迹末尾，提醒进展和后续目标。
- **事件的侧信道信息**：精确时间、地理位置、距上次回复的时间间隔等元数据。
- **环境当前状态的观察摘要**：动态环境信息（系统时间、工作目录）、异常操作提醒、隐式状态到显式观察的转换。

### 7.4 在上下文中的位置

Agent 状态栏在 API 层面作为一条 **user 角色**的消息插入到上下文末尾，而不是修改开头的 system 消息。原因正是 KV Cache 约束：修改 system 消息会破坏整个前缀缓存。这里的 user 角色只是 API 协议层面的技术选择，内容由 Agent 框架自动生成。

### 7.5 状态更新的两种实现与缓存代价

**实现一：每轮替换**  
移除上一轮状态消息，在末尾追加最新状态。保证只有一份最新状态，但移除旧状态会使其位置之后的所有缓存失效——失效范围只覆盖上次注入后新增的消息，整个前缀仍可复用。

**实现二：持久追加**  
状态消息一旦注入就永久留在轨迹中，每轮只在末尾追加新状态。Claude Code 的 `<system-reminder>` 采用这种方式。对缓存完全友好，但陈旧状态会累积，占用 token，要求模型自己关注“最新一条”。

**取舍模型**：设每条状态 S token，两次更新间新增后缀 R token，预计更新 N 次，缓存输入单价为普通输入的 α 倍。  
- $$ C_{替换} \approx (N-1)(1-\alpha)R $$ 
- $$C_{追加} \approx \alpha S N(N-1)/2$$  
当$$\alpha S N/2 < (1-\alpha)R$$ 时倾向实现二，否则倾向实现一。

### 7.6 实验 2-9：五种好用的状态栏技术

1. **时间戳跟踪**：以 `[2025-09-14 10:30:45]` 格式作为前缀添加到用户消息和工具响应中（不是放在系统提示词中，否则破坏 KV Cache）。
2. **工具调用计数器**：维护全局字典，记录每个工具被调用次数，响应中标注 “Tool call #3 for 'read_file'”。显式计数触发模型模式识别能力，实现隐式成本感知。
3. **TODO 列表管理**：借鉴 Manus 的“通过复述操纵注意力”理念，提供 `rewrite_todo_list` 和 `update_todo_status` 工具。启用 TODO 的 Agent 平均 15 次迭代完成任务，禁用时需 21 次且经常遗漏子任务。
4. **详细错误信息**：包含错误类型、完整参数 JSON、调用栈、修复建议。启用后，Agent 在错误场景中找到替代方案的成功率从 60% 提升到 95%。
5. **系统状态感知**：注入当前时间、工作目录、操作系统类型、Shell 环境和 Python 版本。工作目录跟踪尤其关键。

这些技术协同工作产生涌现效应。完全启用后，Agent 不再是机械执行指令的工具，而更像有自我意识的助手。

### 7.7 维护注意

1. **状态栏尽量用代码维护**。实在要用 LLM，也要逐条抽取、再由代码汇总，绝不要一次性批量统计。模型几乎无条件相信状态栏，LLM 做数量统计容易出错。状态栏投毒风险值得认真对待。
2. **谨慎删除原始上下文**。状态栏是对原始上下文的有损投影。如果状态栏够用，可以把原始记录整段删掉，节省大量 token；但只要有一个问题涉及状态栏未计算的维度，仅保留状态栏就会导致准确率断崖式下降。

Agent 状态栏是上下文压缩技术之一。

## 八、2.7 上下文压缩策略

### 8.1 为什么需要压缩：不只是长度问题

1. **解决长度约束和成本约束**：上下文窗口有限，工具结果动辄数万字符，几轮就撑满；token 越多，API 成本越高，推理延迟急剧上升。
2. **提升思考质量**：总结后的知识比原始形式更利于模型使用。即使窗口足够大，把所有原始信息堆在上下文里也不是最优选择：注意力被分散，关键信息容易被遗漏。
3. **缓解上下文焦虑（Context Anxiety）**：当模型认为上下文窗口即将耗尽时，可能在任务尚未完成前提前收尾。提前压缩可能提升决策质量。

### 8.2 上下文学习的内部机制：检索而非推理

注意力机制擅长在已有内容里“查找”，却不擅长在一次前向传播里主动“归纳统计”。状态栏是把算好的结论加进上下文，压缩则是把臃肿的原始记录换成算好的结论——两者是同一枚硬币的两面，都在给那台“只有一半”的检索引擎补上缺失的“提炼”。

**例子**：100 个笼子，90 只黑猫、10 只白猫。问“黑猫白猫各多少只”，不启用思维链的模型很难直接答对；提前做一次总结，在上下文中直接写入“当前统计：黑猫 90 只，白猫 10 只”，模型立刻就能检索到这个结论。

**上下文腐化（Context Rot）**：窗口没满，但 Agent 找不到关键信息，或反复纠结于早已解决的问题。原因是注意力权重被分散，无关内容占据大头。

**设计原则**：与其期望模型从冗长上下文中自动学习，不如主动、显式地进行知识提炼。

### 8.3 压缩与 KV Cache：看似矛盾，实则互补

压缩发生在两次 API 调用之间，由 Agent 框架对消息列表进行预处理：
1. System Prompt 和 Tool Definitions 永远不动——静态前缀，KV Cache 持续缓存。
2. 压缩对象是对话历史中的 tool results——替换位置之后的缓存失效，之前的缓存仍然有效。
3. 有意识的权衡：不压缩，上下文膨胀到超出窗口，任务失败；压缩后，损失部分缓存，但长度可控、信息密度更高。

压缩频次需要权衡——频繁压缩会频繁破坏缓存，最好在上下文接近阈值时批量压缩。

### 8.4 实验 2-10：六种压缩策略对比

任务：识别并追踪 OpenAI 联合创始人的职业状态，使用 Kimi K3，限制 128K 窗口。

| 策略 | Token 用量 | 压缩率 | 迭代次数 | 结果 |
|---|---|---|---|---|
| 无压缩 | 166,043 | 102.1% | 5 | 失败 |
| 个体摘要 | 276,608 | 10.9% | 12 | 成功 |
| 组合摘要 | 93,449 | 4.3% | 10 | 成功 |
| **上下文感知** | **40,157** | **3.0%** | **7** | **成功** |
| 感知+引用 | 222,992 | 4.1% | 10 | 成功 |
| 自适应窗口 | 174,601 | 102.4% | 7 | 成功 |

**关键发现**：上下文感知压缩节省 76% token，迭代次数最少；将查询意图和已有信息纳入压缩决策，保留后续任务需要的关键信息。

### 8.5 生产级分层压缩机制

以 Claude Code 为参照：
1. **工具结果预算控制**：大体积输出存磁盘，模型只看摘要预览。替换决策一旦做出即冻结。
2. **噪声直接删除**：低价值内容直接移除，不做摘要。
3. **API 层微压缩**：服务端从前缀中移除指定工具结果。适合即将溢出时使用。
4. **归档式摘要**：逐轮做结构化摘要（像 git log），保留对话逻辑脉络。
5. **全量压缩**：LLM 驱动的完整压缩，作为最后手段。分两阶段，配备连续失败熔断器。

### 8.6 压缩策略的设计原则

1. **信息价值非均匀分布**：关键决策点 > 支撑性证据 > 冗余噪声。
2. **语义完整性**：“Sutskever 于 2024 年 5 月离开 OpenAI”不能压缩成“Sutskever 离开”。
3. **任务相关性**：检索类任务保留广度，分析类任务保留深度，创作类任务保留灵感触发点。
4. **压缩即理解**：有效压缩需要深层语义理解，负责压缩的模块要接近主模型能力，形成“模型调用模型”的递归架构。

压缩最容易丢失的是早期架构决策、约束背后的理由和失败路径。Agent 需要定期将进展记录到文档中。

### 8.7 隔离优于压缩：子 Agent 上下文隔离

主 Agent 把“在代码库中大范围搜索”这类会产生海量中间内容的任务委派给独立子 Agent；子 Agent 在自己的上下文中完成探索，只把几百 token 的结论性摘要回传给主 Agent。

**本质**：用隔离代替压缩。压缩是有损的、需要额外 LLM 调用的事后补救；隔离让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀完全不受影响。

**代价**：子 Agent 看不到主 Agent 完整上下文，任务描述必须自包含、目标明确。Claude Code 的 Task 工具、Deep Research 的检索子 Agent 都是这一模式的生产实现。

## 十、深入讨论与延伸

### 10.1 工程式管理 vs 理解式管理

上下文管理可分为两类：

**工程式管理**（不依赖语义理解）：
- 前缀缓存、KV Cache、Prompt Cache；
- 工具结果截断、分页、去重、噪声删除；
- 滑动窗口、预算控制、API 层微压缩；
- 子 Agent 上下文隔离。

**理解式管理**（需要语义判断）：
- 上下文感知压缩：把查询意图和已有信息纳入压缩决策；
- 摘要与知识提炼：把原始记录换成结论；
- Agent 状态栏：把隐式状态显式化；
- RAG 检索：判断哪些外部知识相关；
- Skills 按需加载：判断当前任务需要哪份能力。

**更准确的说法**：上下文管理 = 工程式治理 + 理解式治理。压缩是偏理解式的一环，缓存、截断、隔离是工程式的一环。

### 10.2 服务端下沉趋势

服务端正在承接一部分原本属于 Harness 的上下文管理职责：

**已下沉或正在下沉**：
- KV Cache、Prompt Cache；
- 上下文编辑/API 层微压缩；
- 工具搜索/延迟加载（OpenAI `tool_search`、Anthropic `tool_reference`、Codex CLI 默认开启）；
- `previous_response_id`、服务端会话（可选）。

**没有下沉或很难下沉**：
- 任务感知的语义压缩；
- Agent 状态栏；
- 子 Agent 上下文隔离；
- 用户记忆与知识库；
- 安全边界；
- 跨厂商兼容。

**结论**：当前是“工程式下沉、理解式留在 Harness”。服务端做缓存、前缀复用、工具搜索和有限上下文编辑；Harness 做任务感知压缩、状态栏、Skills、RAG、子 Agent 隔离、记忆和安全边界。未来可编辑 KV Cache 可能让服务端进一步下沉，但受隐私、多租户、计费、签名和跨厂商兼容约束，分层协作仍将是长期架构。

### 10.3 压缩与检索本质

“上下文学习本质是检索而非推理”意味着：不要期望模型在单次前向传播中完成统计归纳。突破局限的方法：
- 显式提炼：用 LLM 或代码生成摘要、统计、结论，写入上下文；
- 工具化：用代码解释器、数据库查询做精确统计和推理；
- 结构化知识：RAG、知识图谱、结构化索引，把需要推理的结论提前算好；
- 子 Agent 隔离：让子 Agent 做探索和归纳，主 Agent 只接收结论；
- 后训练：通过 SFT/RL 让模型内化归纳能力；
- 混合架构：模型负责理解和生成，程序负责确定性计算和验证。

### 10.4 状态栏可靠性

状态栏如果包含错误信息，Agent 可能基于错误信息做出有害决策。缓解措施：
- 尽量用代码维护，绝不让 LLM 一次性批量统计；
- 逐条抽取 + 代码汇总；
- 交叉验证：状态栏与原始轨迹、工具返回交叉校验；
- 标记来源和置信度；
- 权限隔离，防止投毒；
- 只追加保留历史状态，模型可对比最新状态；
- 审计与回滚。

### 10.5 提示词熵增

系统提示词由多人维护容易导致熵增。工程实践：
- 版本控制：纳入 Git，变更走 PR；
- 结构化组织：XML + Markdown 分层；
- 流程驱动：用 SOP 组织；
- 自动化回归：建立评估集，每次变更跑回归；
- 提示词敏感性评估：提取渲染后的系统提示，版本化快照；
- 消融实验：定期验证每条规则的实际贡献；
- 最小 diff + 可回滚；
- 所有权明确：产品经理负责业务规则，工程师负责格式和结构。

### 10.6 元认知问题

Skills 渐进式披露依赖模型判断“是否需要加载”，但模型可能不知道自己不知道什么。解决：
- 目录设计：description 写成路由条件，明确“何时使用”“何时不使用”；
- 显式触发：用户斜杠命令；
- 主动工具发现：让模型调用 `discover_tools`，用自然语言描述需求；
- 状态栏提示：列出可用 Skill 目录；
- 训练：通过 SFT/RL 训练模型在能力缺口时主动搜索；
- 兜底监控：任务失败时提示加载相关 Skill；
- 评估：建立元认知评估集。

### 10.7 缓存布局与工具集频繁变动

大量工具且频繁变动时，最大化缓存命中：
- 静态前缀：System Prompt + 核心工具定义固定不变；
- 工具搜索/延迟加载：静态前缀只保留工具名称和简述；
- 完整 schema 按需加载，追加到轨迹末尾；
- 固定位置：已加载的工具 schema 固定在首次注入位置，后续不移动、不重排、不删除；
- 状态栏：维护当前可用工具名称列表，简短，追加到末尾；
- 工具集变动：只追加，不修改前缀；
- 标准 API 格式；
- 监控缓存命中率。

### 10.8 思考题解析

**1. 滑动窗口 vs 完整保留**  
采用分层压缩 + 状态栏 + 子 Agent 隔离 + 只追加不修改。静态前缀稳定，旧工具结果批量压缩为摘要，状态栏补关键状态，子 Agent 隔离大体积中间信息。

**2. Qwen3 思考保留；R1 剥离 vs V4 强制回传**  
修改思路：分层保留 + 思考摘要。R1 剥离节省 token 但丢失关键状态，V4 强制回传保持连贯但 token 消耗大。反转说明 Agent 场景下思考过程承载关键状态，不能简单剥离；未来方向可能是“思考摘要 + 状态栏 + 按需回传”。

**3. 极端压缩的不可逆信息损失**  
用来源引用、分层保留、状态栏、子 Agent 隔离来兜底。压缩必须有损，但关键信息要保留。

**4. 状态栏元信息可靠性**  
代码维护 + 交叉验证 + 权限隔离 + 审计回滚。

**5. 系统提示词熵增**  
版本控制、结构化组织、流程驱动、自动化回归、消融实验、最小 diff、所有权明确。

**6. 突破检索而非推理的局限**  
显式提炼、工具化、结构化知识、子 Agent 隔离、后训练、混合架构。

**7. Skills 元认知问题**  
路由条件、主动发现、状态栏提示、训练、兜底监控、评估。

**8. Skills 后续操作遵从**  
取决于模型能力、指令格式、上下文位置、任务复杂度。强模型更好，弱模型需专用 schema。

**9. 大量工具且频繁变动的缓存布局**  
静态前缀只留名称和简述，完整 schema 按需追加到末尾并固定；工具集变动只追加，不修改前缀。

## 十一、核心原则总结

1. **上下文结构**：Agent 的上下文 = 静态前缀 + 轨迹。
2. **KV Cache 三条核心结论**：
   - 系统提示词和工具定义一旦确定就不要改；
   - 动态信息永远追加到末尾；
   - 使用标准 API 格式，不要自行拼接消息。
3. **注意力机制四个关键模式**：注意力储存池、思考三角形、输出三角形、位置偏好。
4. **两个层级的缓存**：KV Cache（模型内部机制）、Prompt Cache（推理引擎优化，跨请求缓存）。
5. **缓存作为架构约束**：提示词结构由缓存边界决定；子 Agent 与父 Agent 字节级对齐；工具结果替换字符串冻结。
6. **提示工程五个维度**：语气与风格、结构化提示、流程驱动、业务规则细化、Few-shot 示例。
7. **工具定义设计**：使用边界、具体示例、性能提示、协作关系；渐进式披露。
8. **提示注入防御**：上下文层（来源标记、指令/数据分离、输入清洗）+ 执行层（权限控制、沙盒隔离、独立审查）。
9. **Agent Skills**：三层渐进式披露；编写四部分；KV Cache 友好；Skill + 通用执行器。
10. **Agent 状态栏**：把隐式状态显式化；放在上下文末尾；代码维护；谨慎删除原始上下文。
11. **上下文压缩**：三个动机；检索而非推理；与 KV Cache 互补；分层压缩；四条设计原则；隔离优于压缩。
12. **实验结论**：信息组织混乱导致成功率下降 >30%；工具描述缺失导致错误率增加 45%；组合防御最有效；上下文感知压缩节省 76% token。

## 十二、研发启示

1. **先把消息结构、静态前缀、轨迹管理做对**，再谈压缩和缓存。
2. **压缩策略必须任务感知**，否则会丢失后续任务的关键信息。
3. **生产系统采用分层压缩**：预算控制、噪声删除、API 微压缩、归档摘要、全量压缩。
4. **状态栏、Skills、RAG、子 Agent 隔离要组合使用**，不能只靠单一手段。

6. **服务端下沉是趋势，但 Harness 不会消失**，而是上移到更高层的语义决策、验证、安全和业务规则。
