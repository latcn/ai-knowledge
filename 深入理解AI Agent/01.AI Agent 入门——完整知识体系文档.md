## 一、本章定位

### 1.1 什么是AI Agent

如果你用Cursor写过代码，看它搜索代码库、编辑多个文件、运行测试直到通过；用Deep Research调研过课题，看它反复搜索、阅读，总结出完整报告；用Manus操控浏览器完成在线任务；让豆包手机助手帮你在手机上订票、发消息；或者让Pine AI替你打电话给运营商协商降低账单——你已经在使用AI Agent了。

这些产品形态各异，但有一个共同点：

> **它们不再是"你问一句、它答一句"的被动对话，而是能够自主规划执行步骤、调用各种工具完成任务，并根据结果不断调整策略的智能系统。**

## 二、1.1 现代Agent = LLM + 上下文 + 工具

### 2.1 核心公式

> **Agent = LLM + 上下文 + 工具**

这里的加号表示工程组件的组合，而不是强化学习中的形式化定义。更重要的是：

> **这个公式只描述Agent边界之内的实现，不包含Agent与之交互的Environment（环境）。**

### 2.2 三个组件的广义理解

| 组件 | 直觉理解 | 含义 |
|---|---|---|
| **LLM** | 大脑 | 不只是模型参数，而是整个决策内核——理解意图、思考规划、做出判断 |
| **上下文** | 眼睛 | 不只是输入文本，而是Agent在每个决策点收到并保留的信息表示 |
| **工具** | 手脚 | Agent用来感知或改变外部世界的接口 |

**更直观的说法**：Agent = 大脑 + 眼睛 + 手脚。

### 2.3 与强化学习的映射

| 直觉理解 | 实现组件   | 学术概念       |
| ---- | ------ | ---------- |
| 大脑   | LLM    | 策略（Policy） |
| 眼睛   | 上下文构造  | 观察与历史      |
| 手脚   | 工具与适配器 | 观察/行动接口    |

**关键区分**：
- 上下文是具体观察和历史在Agent内部的表示，并不等于整个观察空间；
- 工具则定义Agent可使用的观察与行动接口，工具背后的对象仍属于环境。

### 2.4 图1-1：Agent与Environment的闭环交互

**两个抽象层次**：

**外层**：Agent与Environment的交互关系
- 环境包含文件、数据库、网页、用户、其他Agent以及物理或仿真世界；
- Agent只能通过观察和行动接口与它交互。

**内层**：Agent的Model-Harness结构
- **Model**：负责策略决策；
- **Harness**：Agent边界内环绕模型的运行与治理层，负责构造上下文、暴露工具接口、维护循环和状态，并实施权限、验证与纠正。

**关键边界**：
> Harness可以创建、隔离或代理一个环境，却不因此包含环境自身的状态与转移规律。

### 2.5 1.1.1 观察空间与动作空间：模型与世界的接口

#### 2.5.1 核心定义

观察通道与动作接口共同构成了Agent与外部环境之间的边界。

**关键判断**：
> 没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。

#### 2.5.2 核心结论

> **在底层模型固定时，提升Agent任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。**

许多看似需要"更聪明模型"的问题，其实只是接口问题。

#### 2.5.3 两个关键案例

**Manus：合并原本分离的空间**
- 在Manus之前，生产级Agent沿Deep Research、Coding、Computer Use三条独立路线发展；
- Manus率先把三者放进同一个生产级Agent：虚拟浏览器扩大了观察空间，文件系统、代码执行与命令行执行扩大了动作空间；
- 它没有仅靠替换更强的模型，而是取三类Agent观察空间与动作空间的并集。

**OpenClaw：把接口延伸到用户的数字生活**
- 通过WhatsApp、Telegram、Slack、Discord、iMessage等消息渠道接收任务和返回结果；
- 采用本地Gateway，连接Google Drive、Notion等云应用以及本地文件系统；
- 分散在不同账号与设备中的数字文件都可以在用户明确授权后进入同一个Agent的观察空间。

**核心判断**：
> 产品能力的演进往往就是观察空间和动作空间的演进。

#### 2.5.4 五类Agent产品的对比

| Agent产品 | 眼睛（感知） | 手脚（行动） | 策略 |
|---|---|---|---|
| Cursor等Coding Agent | 需求、代码片段、目录列表、终端输出 | 开放式（代码搜索、文件读写、执行命令） | 增量开发：理解需求→搜索→编辑→测试→调试 |
| Deep Research等搜索Agent | 搜索结果、网页内容、论文摘要 | 开放式（搜索查询、网页读取、生成报告） | 迭代深化：调整搜索方向，逐步综合报告 |
| Browser Use等电脑操控Agent | 屏幕截图、DOM、操作结果 | 开放式（点击、输入、滚动、截图） | 视觉感知+操作：观察→识别→执行→验证 |
| 豆包等手机助手Agent | 手机截图、App界面状态、系统反馈 | 开放式（点击、滑动、输入、打开App） | 意图理解+App操控 |
| Pine AI等个人办事Agent | 账户记录、账单结果、服务商资料 | 开放式（打电话、发邮件、填表单） | 多步骤任务执行：收集→制定策略→联系→谈判→汇报 |

#### 2.5.5 共同特征

- **开放式的动作空间**：不是从有限按钮中选择，而是能生成任意自然语言和代码；
- **内部思考**：在采取行动前先思考和规划；
- **持续交互**：根据环境反馈不断调整策略。

### 2.6 1.1.2 工具：Agent的手脚

#### 2.6.1 五类工具

| 工具类型 | 调用方向 | 作用对象 |
|---|---|---|
| **感知工具** | Agent主动调用 | 获取信息（搜索、文件、API、数据库） |
| **执行工具** | Agent主动调用 | 改变世界（代码执行、文件操作、系统命令） |
| **协作工具** | Agent主动调用 | 驱动其他Agent或人类 |
| **事件触发工具** | Agent注册、外部触发 | 驱动Agent开始执行 |
| **用户沟通工具** | Agent主动调用 | 向用户传递信息 |

#### 2.6.2 工具调用（Tool Calling）

**四步流程**：
1. **声明工具**：在上下文里告诉模型有哪些工具可用；
2. **模型决策**：模型自主判断要不要调用、调用哪个、传什么参数；
3. **结果追加**：工具执行完毕后，结果被追加到上下文中；
4. **下一步决策**：模型据此决定下一步行动。

这个循环就是ReAct的基础。

#### 2.6.3 工具设计的核心原则

> **通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。**

- **从最窄能力起步**：任务简单时用计算器，任务复杂时用Python解释器；
- **通用性的代价**：代码必须在隔离沙盒中运行，默认不能访问网络；
- **长程任务的虚拟工作目录**：同时保存计划、中间结果、运行日志和最终产物；
- **高风险操作**：支付、删除数据、发送邮件、生产部署等应封装为专用工具，参数明确、权限受限、全程可审计。

### 2.7 1.1.3 LLM：Agent的大脑

#### 2.7.1 核心定义

> LLM是Agent的决策核心。收到用户请求后，它需要先解析真实意图，再将模糊或复杂的任务拆解成可执行的步骤。

#### 2.7.2 内部思考能力

LLM Agent的一个独特能力是**内部思考**——在采取实际行动之前，Agent可以先进行规划与推演。

> 与传统强化学习Agent不同，今天基于LLM的Agent不是盲目的随机探索，而是在结构化的知识体系上展开。

#### 2.7.3 模型即Agent：当模型本身成为产品

**核心定义**：
> "模型即Agent"（Model as Agent）这一新范式代表了AI Agent发展的最新方向。先进模型通过后训练将工具调用能力内化为原生能力。

**但Harness依然关键**：
> 模型越强大，围绕模型构建的Harness就越关键。模型是那匹强大但不可预测的马，Harness则是把它的能力引导成可靠任务执行的工程外壳。

**苦涩的教训**：
- Rich Sutton指出，研究者一次次把自己对领域的理解编码进系统，短期见效，长期却总是输给能随算力与数据规模持续扩展的通用方法；
- **本书的立场**：方向认同，节奏务实——模型会持续吃掉Harness，但这个"吃"的过程远比想象中慢；
- **模型此刻的能力边界，就是Harness此刻的价值所在。**

#### 2.7.4 Agent的学习机制：从上下文适应到持久更新

**三条互补路径（图1-2）**：

| 路径 | 主要载体 | 更新特性 |
|---|---|---|
| **任务内适应** | 当前上下文 | 即时、低成本；任务结束后不自动保留 |
| **外部制品更新** | 知识·指令·程序 | 跨任务持久、可审计；依赖检索或工具调用 |
| **模型参数更新** | 模型权重 | 高维能力、广泛泛化；训练与回归成本较高 |

**三者协同**：临场适应 · 可控积累 · 能力内化。

### 2.8 1.1.4 上下文：Agent的眼睛

#### 2.8.1 上下文的五个组成部分

| 组成部分 | 说明 |
|---|---|
| **系统提示词** | 由开发者编写，定义身份、权限和行为准则 |
| **工具定义** | 声明可用工具的名称、功能描述和参数格式 |
| **用户消息** | 来自用户的输入，可能包含RAG动态检索引入的外部知识 |
| **模型回复** | 最多包含三部分：思考过程、文本内容、工具调用请求 |
| **工具执行结果** | Agent框架执行工具后返回的结果 |

**静态前缀与动态历史**：
- 前两项是**静态前缀**；
- 后三项是随交互不断增长的**动态消息历史**。

#### 2.8.2 消融实验（实验1-1）

**实验结果**：

| 缺失组件 | 结果 | 说明 |
|---|---|---|
| **工具定义** | 无法调用工具 | 但模型照样给出格式工整的答案，数据来自参数记忆 |
| **工具执行结果** | 盲目循环 | 反复重试直到耗尽迭代预算 |
| **思考过程** | 决策不连贯 | 当信息可从工具结果重建时，代价较小 |
| **历史记录** | 重复操作 | 防止冗余操作，避免重复犯错 |

**核心洞察**：
> 上下文决定了Agent能看到什么，而Agent只能基于它看到的信息做决策。但组件并不等价，衡量的标准是它承载的信息能否从别处重建。

**工程实践要点**：
> "给出了回答"不等于"完成了任务"，上下文残缺时典型的失败不是报错退出，而是一个看上去毫无破绽的答案。

### 2.9 1.1.5 ReAct循环

#### 2.9.1 核心定义

> **ReAct（Reasoning + Acting）**：模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步。

这个"想→做→看→想→做→看"的循环不断重复，直到任务完成。

#### 2.9.2 轨迹

> **Agent的上下文 = 静态前缀 + 轨迹**

- **静态前缀**：系统提示词 + 工具定义；
- **轨迹**：用户消息 + 模型回复 + 工具执行结果。

#### 2.9.3 图1-6：自主Agent的执行循环

```
① 思考（Reasoning）→ ② 行动（Acting）→ ③ 观察（Observing）→ 判断是否满足退出条件
```

**退出条件（任一满足）**：
- ① 任务完成；
- ② 调用final_answer；
- ③ 无工具调用返回；
- ④ 错误次数超限；
- ⑤ 达到最大轮次。

**关键判断**：
> 自主性不等于无限制——必须设计明确的停止条件，否则Agent容易陷入死循环或过度执行。

#### 2.9.4 实验1-2：Kimi K3原生Agent能力

**模型规格**：约2.8万亿参数的MoE模型，100万token上下文窗口，原生视觉理解，始终开启的思考模式。

**关键观察**：
- 模型自己决定何时搜索、搜索什么；
- 能根据搜索结果动态调整策略。

**关键区分**：
| 归属 | 内容 |
|---|---|
| **RL写进参数** | 决策——何时调用工具、调用哪个、传什么参数 |
| **Agent框架提供** | 工具本身及其执行——web_search的真实实现、代码沙盒环境 |

> 编排循环并没有消失，而是从客户端移到了服务端，决策权则交给了模型。

**突出优势**：长链工具调用的稳定性——连续执行200～300次工具调用而保持思考的一致性。

#### 2.9.5 实验1-3：GPT-5.6原生Deep Research能力

**自由格式工具调用**：
- 传统方式必须把所有参数打包成严格的JSON格式；
- 自由格式工具调用允许模型直接向工具发送原始文本；
- 这是API参数格式的演进，而非模型架构的革新。

**Deep Research能力**：
- 模型自主搜索网络获取实时信息，并编写代码进行深度分析；
- 实现"搜索→阅读→分析→再搜索"的迭代研究过程。

**意图澄清**：
> GPT-5.6将OpenAI Deep Research产品的设计理念内化到了模型层面，引入了意图澄清过程——让"用户说了什么"和"用户真正想要什么"之间的差距，在任务执行之前就得到了弥合。

## 三、1.2 Harness工程：模型之外的竞争力

### 3.1 核心方程

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

### 3.2 精确边界

> **Harness不是模型之外的一切，而是Agent边界内、模型之外的运行与治理层。**

| 属于Harness | 属于Environment |
|---|---|
| 工具定义、调用适配器 | 沙箱内随行动变化的文件和进程 |
| 沙箱的权限与重置机制 | 外部数据库、网页、用户及物理世界 |
| 上下文管理、工具接口 | — |
| 约束、验证、纠正 | — |

### 3.3 Harness五要素

| 功能 | 职责与核心原则 | 实际例子 |
|---|---|---|
| **Context（上下文）** | 信息要充分，让Agent在每个决策点都基于足够的信息判断 | 系统提示词、知识库、Agent状态栏、Sidecar旁路查询 |
| **Tools（工具接口）** | 接口要清晰，命名直观、参数有例子、边界有说明 | MCP工具、代码解释器、搜索工具 |
| **Constrain（约束）** | 故障安全默认值，所有能力默认关闭，必须显式开放 | Claude Code中每个工具默认需要用户授权才能执行 |
| **Verify（验证）** | 安全检查只看结构化数据，不看模型自由生成的文本 | Linter检查、类型系统、工具调用结果校验 |
| **Correct（纠正）** | 在确认无法恢复之前不暴露中间态，静默重试，连续失败熔断 | 静默重试、接续生成、回退到人工判断 |

**五要素闭环**：
> 上下文与工具让Agent"能做事"；约束预防错误，验证发现偏差，纠正使闭环得以形成，三者共同让Agent"不做错事"。

**两类功能的重要性不对称**：
- 早期Agent框架主要关注上下文与工具；
- 生产级Agent系统的重心已经转向约束、验证与纠正。

### 3.4 从提示工程到Graph工程：工程范式的演进

| 阶段 | 名称 | 核心关注 |
|---|---|---|
| 第一波 | **提示工程** | 优化输入给模型的自然语言指令 |
| 第二波 | **上下文工程** | 系统性地管理模型能看到的所有信息 |
| 第三波 | **Harness工程** | 从"模型能看到什么"扩展到"Agent如何组织模型运行并与环境交互" |
| 第四波 | **Loop工程** | 从单次运行扩展到跨轮次的持续自主运转 |
| 第五波 | **Graph工程** | 把Agent循环、确定性程序和人工审批组织成显式的执行图 |

**层层包含关系**：
> 提示工程是上下文工程的子集，上下文工程是Harness工程的子集，Harness工程是Loop工程的子集，Loop工程又是Graph工程的子集。

**竞争优势的转移**：
> 当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践。

**验证例证**：LangChain在Terminal Bench 2.0上，改变的不是模型，而是Harness，得分从52.8%提升到66.5%。

### 3.5 构建有效Agent的核心原则

| 原则 | 内容 |
|---|---|
| **保持简单** | 从最简单的方案开始，只在确实必要时才增加复杂度 |
| **保持透明** | 明确显示规划步骤、执行日志和决策轨迹 |
| **设计好工具接口（ACI）** | 从Agent视角设计接口，用设计消除错误（防呆/Poka-yoke） |

### 3.6 模型选型

| 维度 | 要点 |
|---|---|
| **闭源 vs 开源** | 闭源能力领先但成本高；开源差距在6个月以内，成本低、可私有化 |
| **策略边界** | 模型具备能力不等于产品允许调用，要在真实任务上测试 |
| **思考能力** | 绝大多数Agent需要支持Reasoning的模型 |
| **输出速度** | 直接决定端到端响应延迟 |
| **多模态** | 如果任务需要理解图片、音频或视频，就是硬性要求 |

### 3.7 编排模式：工作流与自主

**从简单到复杂的原则**：
1. 先考虑单个LLM调用；
2. 需要多步骤处理时，考虑工作流；
3. 只有当需要动态决策和灵活的执行路径时，才使用自主Agent。

**工作流模式**：
- 通过预定义的代码路径来编排LLM和工具；
- 优势：严格的流程控制、安全性；
- 局限：缺乏变通性。

**自主Agent**：
- 执行路径不是预先定义的，而是根据环境反馈实时决定的；
- 本质上就是在一个循环中使用工具的LLM——这正是ReAct循环；
- 适用场景：开放式问题、难以预测所需步骤数量的任务。

**混合模式**：
- 关键流程用工作流确保可靠性；
- 需要灵活决策的部分切换到自主模式；
- 或先由自主Agent把工作流写出来，再由工作流去执行。

**核心判断**：
> Harness很重要，不等于Harness越复杂越好。好的结构不是替Agent预演全部思考，而是守住边界，并把边界内的决策空间还给模型。

### 3.8 护栏与安全性

#### 3.8.1 三层护栏模型

| 层级 | 管什么 | 核心机制 | 被绕过的难度 |
|---|---|---|---|
| **上下文层** | 模型能看到什么 | 相关性分类器、安全分类器、内容审核、规则保护、来源标注 | 低 |
| **执行层** | 模型能做什么 | 工具风险评级、独立审查进程、最小权限凭证、沙盒隔离、人在回路 | 中 |
| **数据层** | 世界最终能被改成什么样 | 行级安全策略、约束与校验器、受控视图、访问上下文 | 高 |

**关键判断**：
> 越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透。

#### 3.8.2 规则必然可被绕过

**理论层面的不完备性**：
- 哥德尔不完备定理：任何足够强的形式系统，都存在无法在系统内证明的命题；
- 图灵停机问题：无法用程序判定任意程序是否会停机；
- 赖斯定理：程序的任何非平凡语义性质都不可判定；
- 未知未知：我们不知道自己不知道什么。

**工程层面的必然性**：
- 规则的表达力有限，而攻击面是无限空间；
- 同一行为在不同上下文中风险不同；
- 攻击者会针对规则设计绕过手段；
- 模型本身是概率系统；
- 组合爆炸。

**核心判断**：
> 处在同一个上下文里的Agent，很难判断自己是否已经被注入。所以上下文层只能降低攻击成功率，给不出保证——这正是必须有下面两层的原因。

#### 3.8.3 安全的真正目标

> **不是让攻击不可能发生，而是让攻击的成本高于收益、让攻击的后果可检测可恢复。**

| 目标 | 手段 |
|---|---|
| **提高攻击成本** | 纵深防御、独立验证器、最小权限、沙盒隔离、可信根 |
| **降低攻击收益** | 数据层行级安全、PII过滤器、高风险操作确认门禁、熔断机制 |
| **加快检测与恢复** | 审计日志、可观测性、稳定版本备份、灰度发布、独立仲裁 |

#### 3.8.4 人工干预（Human in the Loop）

**两种主要触发情况**：
- **超过失败阈值**：重试次数或操作次数超限，升级到人工干预；
- **高风险操作**：涉及敏感、不可逆或高风险操作时，触发人工监督。

**优雅移交的挑战**：
- 用户可能不在线、响应很慢、或给出模糊指令；
- 应对策略：超时默认保守、多渠道通知、优先级队列、澄清模糊指令、异步处理、降级回退、状态持久化。

### 3.9 Harness五要素与全书结构的对应

| Harness要素 | 对应章节 | 核心内容 |
|---|---|---|
| **上下文管理** | 第二章 | 提示工程、Agent状态栏、上下文压缩、Agent Skills |
| **上下文管理（跨会话）** | 第三章 | 用户记忆、RAG、结构化索引、智能体化RAG |
| **工具接口与约束** | 第四章 | 工具分类、权限控制、MCP标准、主动工具发现 |
| **验证与纠正** | 第五章 | Coding Agent的Harness、测试驱动、代码化规则 |
| **交互** | 第六章 | 扩展观察与动作空间本身的模态与时机 |
| **评估与进化** | 第七至九章 | 怎么知道Harness建对了、以及怎么让它持续变好 |
| **协作** | 第十章 | 把单个Agent的Harness换成多个Agent的协作结构 |

**安全是横切关注点**：按三层护栏组织——上下文层、执行层、数据层。

## 四、1.3 贯穿全书的设计模式

### 4.1 提议者—审核者（Proposer-Reviewer）

**核心定义**：
> 产出与评判由两个不共享上下文的角色分别承担，评判方看到的是产物本身——渲染结果、测试输出、结构化的调用参数——而不是产出方的推理过程。

**成立前提**：
> 自审不可靠：同一个上下文中的模型难以发现自己的认知盲区，也很难判断自己是否已被注入。

**全书应用**：

| 章节 | 应用 |
|---|---|
| 第三章 | 更新知识 |
| 第四章 | 工具调用的事前审批与事后验证（Sidecar是只读变体） |
| 第五章 | PPT、视频与日志三个实验都以它为骨架 |
| 第七章 | 评估UI |
| 第九章 | 审核更新提案 |
| 第十章 | 对等协作中的形态 |

**核心不变量**：
> 审核者读取独立证据，而不是只复述提议者的解释；退回时必须给出可定位的修复条件。审核者不能修改测试、证据采集器或发布门槛。

### 4.2 渐进式披露（Progressive Disclosure）

**核心定义**：
> 不把全部信息一次性放进上下文，而是先给一份可检索的目录，再按需加载细节。

**双重优化**：
- 上下文预算；
- 选择精度。

**全书应用**：

| 章节 | 应用 |
|---|---|
| 第二章 | Agent Skills（元数据常驻、正文按需加载） |
| 第三章 | 分层检索 |
| 第四章 | 主动工具发现与分页截断 |
| 第十章 | Agent发现 |

### 4.3 只增不改（Append-only）

**核心定义**：
> 状态以追加的方式演进，已经写下的内容不再回头修改。

**核心收益**：
- 可缓存；
- 可重放；
- 可审计。

**全书应用**：

| 章节 | 应用 |
|---|---|
| 第二章 | KV Cache前缀稳定性 |
| 第三章 | 事件式记忆 |
| 第四章 | 新工具schema追加到轨迹末尾 |
| 第九章 | 经验日志、版本化记忆 |

### 4.4 边界集 + 保留集（Boundary Set + Retention Set）

**核心定义**：
> 任何一次修改都要同时在"它应当改变的那批样本"和"它不应当影响的那批样本"上验证。

**为什么需要两个集合**：

| 只测边界集 | 只测保留集 |
|---|---|
| 把过拟合当成进步 | 把无效修改当成安全 |

**全书应用**：

| 章节 | 应用 |
|---|---|
| 第七章 | 回归任务 |
| 第八章 | 训练与评估隔离 |
| 第九章 | 更新提案验证 |
| 第十章 | 多Agent协作中的交叉验证 |

### 4.5 最小 diff + 可回滚

**核心定义**：
> 每次修改尽量小、带来源、可单独回滚，而不是整体重写。

**核心价值**：
> 它让归因成为可能——出了问题能定位到具体哪一次改动。

**三条更新路径的可回滚程度**：

| 更新路径 | 可回滚程度 |
|---|---|
| 上下文内适应 | 高——任务结束自动消失 |
| 外部产物更新 | 中——可通过版本控制回滚 |
| 参数更新 | 低——训练成本高，回滚困难 |

## 五、1.4 本章小结

### 5.1 核心结论

1. **Agent = 大脑 + 眼睛 + 手脚**：LLM是大脑，上下文是眼睛，工具是手脚。三者缺一不可。
2. **扩展眼睛和手脚是最主要的能力杠杆**：在模型固定时，扩展上下文和工具往往能直接把原本不可解的任务变为可解。
3. **眼睛（上下文）是决定性的因素**：上下文由静态前缀和动态轨迹构成，各组件并不等价。
4. **Harness是竞争力所在**：模型能力正在商品化，真正的差异在于Harness——约束、验证与纠正机制。
5. **从工作流到自主Agent**：先优化提示词，再考虑工作流，最后才引入自主Agent。
6. **五个设计模式贯穿全书**：提议者—审核者、渐进式披露、只增不改、边界集+保留集、最小diff+可回滚。
7. **安全是架构问题**：安全问题从第一行代码就要考虑，护栏按被绕过的难度分为上下文层、执行层与数据层。

## 六、思考题与解析

### 思考题1：只能增加一项能力——更强的模型、更丰富的上下文还是更多的工具？

**分析框架**：选择取决于当前瓶颈在哪。

| 瓶颈 | 选择 | 理由 |
|---|---|---|
| 模型能力不足 | 更强的模型 | 失败集中在"模型无法理解、无法推理、无法生成正确内容" |
| 信息不足 | 更丰富的上下文 | 失败集中在"模型不知道关键信息"——最常见的情况 |
| 行动能力不足 | 更多的工具 | 失败集中在"模型知道该怎么做但无法执行" |

**选择会改变的条件**：
- 模型固定时，扩展上下文和工具是最主要的杠杆；
- 模型能力趋同时，竞争优势转移到Harness工程；
- 高风险场景需要更多的约束、验证和纠正机制；
- 成本敏感场景可能优先考虑扩展上下文和工具；
- 长程任务中，上下文的组织和压缩比单纯增加信息更重要。

**一句话**：先判断瓶颈：模型不会做→换模型；模型不知道→扩上下文；模型做不到→加工具。

### 思考题2：如何降低ReAct循环中累计缓存读取量的二次方增长？

**方法**：
1. **KV Cache / Prompt Cache**：保持静态前缀不变，动态信息追加到末尾；
2. **上下文压缩**：接近阈值时批量压缩旧工具结果；
3. **子Agent隔离**：让大体积中间信息根本不进入主上下文；
4. **状态栏**：把关键状态显式化，避免模型反复扫描长历史；
5. **分层保留**：近期思考原样保留，早期思考压缩为摘要；
6. **只增不改**：已加载的工具schema固定在首次注入位置。

**一句话**：降低二次方增长的关键是——保持前缀稳定、压缩旧内容、隔离大体积信息、显式化状态。

### 思考题3："模型即Agent"与Harness重要性增加如何共存？

**共存的逻辑**：
> 模型越强大，围绕模型构建的Harness就越关键。模型自主决策空间越大，出错时的影响面也越大。

**未来框架的核心价值**：
- 约束与验证；
- 上下文管理；
- 错误恢复；
- 工具接口设计；
- 安全护栏；
- 业务集成；
- 可观测性；
- 跨厂商兼容。

**一句话**：模型每内化一层能力，Harness就卸下一层，转而兜底新的能力前沿。

### 思考题4：除了工具结果缺失，还有哪些情况可能让Agent陷入循环？

**可能情况**：
- 工具反复返回同一错误；
- 参数格式错误；
- 权限不足；
- 网络超时；
- 上下文溢出；
- 死循环；
- 死亡螺旋；
- 幻觉调用。

**检测机制**：
- 重复调用指纹；
- 连续失败计数；
- 空闲看门狗；
- 活性与完整性监控。

**终止机制**：
- 最大迭代轮数；
- 会话预算上限；
- 熔断器；
- 分级恢复；
- 终止与升级条件；
- 禁用错误路径上的副作用逻辑。

### 思考题5：用感知、行动、策略三个维度分析一个AI产品

**示例：Cursor**

| 维度 | 分析 |
|---|---|
| 感知 | 需求、代码片段、目录列表、终端输出、Git状态 |
| 行动 | 代码搜索、文件读写、执行命令、运行测试 |
| 策略 | 增量开发：理解需求→搜索→编辑→测试→调试 |

**改进空间**：
- 上下文管理：更高效地按需加载相关代码；
- 验证与纠正：引入提议者-审核者模式；
- 安全护栏：高风险操作确认门禁；
- 可观测性：完整的执行轨迹。

### 思考题6：航班订票客服系统——工作流还是自主Agent？

**推荐方案：混合模式**

**工作流部分**：
- 核实用户身份；
- 完成付款；
- 确认预订。

**自主Agent部分**：
- 理解出行需求；
- 搜索航班；
- 处理改签、航班取消、推荐替代方案。

**关键设计**：
- 工作流强制执行"付款前不能预订"；
- 自主Agent在工作流节点内部灵活处理；
- 关键决策点加入人工确认；
- 用状态栏追踪当前执行到哪一步。

### 思考题7：如何设计动态风险评估？

**设计思路**：
1. **参数语义分析**：分析`path`的值，系统目录风险提升；
2. **上下文感知**：考虑用户、环境、任务类型；
3. **组合风险评估**：单个低风险，组合可能高风险；
4. **分层审批**：低风险自动执行，中风险记录日志，高风险人工确认；
5. **独立审查进程**：Sidecar模式，只看结构化数据；
6. **熔断与回退**：连续拒绝时转为请求用户手动判断。

### 思考题8：受限动作空间在什么场景下优于开放式？

**场景**：
- 高风险操作；
- 强合规要求；
- 强业务约束；
- 简单任务；
- 弱模型；
- 需要审计；
- 实时性要求高；
- 安全敏感。

**核心原则**：
> 通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。

### 思考题9：用户不在线或给出模糊指令时，Agent应该怎么办？

**应对策略**：
1. **超时与默认行为**：超时后采用保守策略；
2. **多渠道通知**：紧急请求多渠道通知；
3. **优先级队列**：紧急优先，普通排队；
4. **模糊指令处理**：请求澄清，给出具体选项；
5. **异步处理**：不阻塞主流程；
6. **降级与回退**：无法获得人工确认时，回退到预设安全策略；
7. **状态持久化**：保存当前状态，支持稍后恢复。

### 思考题10：举一个会随模型能力进步而过时的Agent工程手段

**示例：文生图的提示词改写**

- 在Stable Diffusion时代，需要专门的LLM节点把自然语言需求改写成特定格式；
- 新的多模态模型具备原生图像生成能力后，提示词改写节点不再需要。

**类似案例**：
- few-shot示例、"让我们一步一步思考"被指令微调和推理模型内化；
- 输出格式修复、JSON解析容错被结构化输出和原生工具调用内化；
- 多级上下文压缩、失败数千次才熔断的重试、悲观地默认"不安全"的权限判断。

**核心判断**：
> 设计原则穿越周期，具体手段随模型能力进步而过时——这正是Harness工程"模型还做不稳的，Harness先补上；模型每内化一层，Harness就卸下一层"的体现。

## 七、核心原则总结

### 7.1 核心公式

> **Agent = LLM + 上下文 + 工具**  
> **Agent = 大脑 + 眼睛 + 手脚**

### 7.2 两个抽象层次

- **外层**：Agent与Environment的闭环交互；
- **内层**：Agent的Model-Harness结构。

### 7.3 三个组件的映射

| 直觉 | 实现 | 学术 |
|---|---|---|
| 大脑 | LLM | 策略（Policy） |
| 眼睛 | 上下文构造 | 观察与历史 |
| 手脚 | 工具与适配器 | 观察/行动接口 |

### 7.4 观察空间与动作空间

> 在底层模型固定时，提升Agent任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。

### 7.5 五类工具

感知工具、执行工具、协作工具、事件触发工具、用户沟通工具。

### 7.6 工具调用的四步流程

声明工具 → 模型决策 → 结果追加 → 下一步决策。

### 7.7 工具设计的核心原则

> 通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。

### 7.8 模型即Agent

- 先进模型通过后训练将工具调用能力内化为原生能力；
- 但模型越强大，围绕模型构建的Harness就越关键；
- 模型此刻的能力边界，就是Harness此刻的价值所在。

### 7.9 Agent的学习机制

三条互补路径：
- **上下文适应**：临场适应，快速、低成本；
- **外部产物更新**：可控积累，跨任务持久、可审计；
- **模型参数更新**：能力内化，高维能力、广泛泛化。

三者协同：临场适应 · 可控积累 · 能力内化。

### 7.10 上下文的五个组成部分

系统提示词、工具定义、用户消息、模型回复、工具执行结果。

前两项是静态前缀，后三项是动态消息历史。

### 7.11 消融实验的核心洞察

> 上下文决定了Agent能看到什么，而Agent只能基于它看到的信息做决策。但组件并不等价，衡量的标准是它承载的信息能否从别处重建。

### 7.12 ReAct循环

> 想→做→看→想→做→看，不断重复，直到任务完成。

### 7.13 轨迹

> **Agent的上下文 = 静态前缀 + 轨迹**

### 7.14 Harness的完整组成

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

### 7.15 五阶段工程范式演进

> 提示工程 → 上下文工程 → Harness工程 → Loop工程 → Graph工程

层层包含，每一层扩展工程师的关注范围和影响力。

### 7.16 三个核心原则

- **保持简单**；
- **保持透明**；
- **设计好工具接口（ACI）**。

### 7.17 模型选型

- **闭源 vs 开源**：闭源能力领先但成本高；开源差距在6个月以内；
- **策略边界**：模型具备能力不等于产品允许调用；
- **思考能力**：绝大多数Agent需要支持Reasoning的模型；
- **输出速度**：直接决定端到端响应延迟；
- **多模态**：如果任务需要理解图片、音频或视频，就是硬性要求。

### 7.18 编排模式

- **从简单到复杂**：先单个LLM调用，再工作流，最后自主Agent；
- **工作流**：确定性编排，严格流程控制，安全性高，但缺乏变通性；
- **自主Agent**：动态自主决策，适合开放式问题，但成本和复合错误风险更高；
- **混合模式**：关键流程用工作流，灵活部分用自主Agent。

### 7.19 护栏三层模型

| 层级 | 管什么 | 核心机制 | 被绕过的难度 |
|---|---|---|---|
| **上下文层** | 模型能看到什么 | 相关性分类器、安全分类器、内容审核、规则保护、来源标注 | 低 |
| **执行层** | 模型能做什么 | 工具风险评级、独立审查进程、最小权限凭证、沙盒隔离、人在回路 | 中 |
| **数据层** | 世界最终能被改成什么样 | 行级安全策略、约束与校验器、受控视图、访问上下文 | 高 |

### 7.20 规则必然可被绕过

> 安全的目标不是"绝对安全"，而是"提高攻击成本、降低攻击收益、加快检测恢复"。三层护栏正是这一哲学的工程实现。安全是过程，不是状态。

### 7.21 人工干预

- **超过失败阈值**：重试次数或操作次数超限，升级到人工干预；
- **高风险操作**：涉及敏感、不可逆或高风险操作时，触发人工监督。

### 7.22 五个设计模式

1. **提议者—审核者**：产出与评判分离，审核者读取独立证据；
2. **渐进式披露**：先给目录，按需加载细节；
3. **只增不改**：状态以追加方式演进，保证可缓存、可重放、可审计；
4. **边界集 + 保留集**：修改必须同时在"应当改变"和"不应当影响"两个方向上验证；
5. **最小 diff + 可回滚**：每次修改尽量小、带来源、可单独回滚。

### 7.23 与全书结构的关系

- Agent = LLM + 上下文 + 工具是全书唯一的结构骨架；
- Agent = Model + Harness是"构建"部分内部的观察视角；
- 安全是横切关注点，按三层护栏组织；
- 第六章扩展观察与动作空间的模态与时机，第七至九章讨论评估与进化，第十章讨论协作。

## 八、全文一句话收束

> **第1章建立了理解和构建AI Agent的基础框架：Agent = LLM + 上下文 + 工具，对应大脑 + 眼睛 + 手脚；Agent与Environment闭环交互，内部则是Model-Harness结构；在模型固定时，扩展观察空间与动作空间是最主要的系统工程手段；ReAct循环将三者串联，轨迹不断累积；Harness工程的核心是上下文管理、工具接口、约束、验证与纠正五要素，模型能力正在商品化，Harness成为核心竞争力；五个设计模式贯穿全书；安全是架构问题，三层护栏按被绕过的难度分层，规则必然可被绕过，安全的目标是提高攻击成本、降低攻击收益、加快检测恢复。模型每内化一层能力，Harness就卸下一层，转而兜底新的能力前沿。**



思考题
1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——
你会选哪个？在什么条件下你的选择会改变？
2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？
3. ★★ “模型即 Agent”范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要
性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？
4. ★★ 消融实验中“工具结果反馈”的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工
具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？
5. ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这
三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？
6. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没
有可能在同一个系统中混合使用两种模式？
7. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下
变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
8. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是“开放式”的。一个受限的动作空间（比如
只能从预定义选项中选择）在什么场景下反而优于开放式？
9. ★★ 人工干预机制要求 Agent 能“优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给
出模糊的指令。此时 Agent 应该怎么办？
10. ★★★ 引言指出“好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模
型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。
