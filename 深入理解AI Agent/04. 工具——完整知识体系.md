
> **工具设计决定 Agent 的能力上限。** 本章从工具分类出发，讨论通用设计原则、工具生态、规模膨胀的应对，以及三类主动调用工具（感知、执行、协作）的设计重点。事件触发与用户沟通工具留待第六章。本章还融入了多轮讨论中关于 Sidecar 并行/串行、向量检索误差、工具缺陷与停止点契约等深入问答。

## 一、总纲：工具是 Agent 的手脚和感官

**核心公式：Agent = LLM + 上下文 + 工具**

- LLM：大脑，负责决策。
- 上下文：眼睛，决定看到什么。
- 工具：手脚和感官，决定能做什么。

**本章结构：**

```
工具分类（4.1）→ 通用设计原则（4.2）→ 工具生态（4.3）→ 工具太多怎么办（4.4）
→ 感知工具（4.5）→ 执行工具（4.6）→ 协作工具（4.7）→ 本章小结（4.8）
```

**两个独立决策：**
- **形态**：每条能力常驻多少 token、参数怎么传、谁能改。
- **披露**：同时有多少条摆在模型面前。

## 二、4.1 工具的分类

### 2.1 五类工具

| 工具类型 | 调用方向 | 作用对象 |
|---|---|---|
| **感知工具** | Agent 主动调用 | 获取信息 |
| **执行工具** | Agent 主动调用 | 改变世界 |
| **协作工具** | Agent 主动调用 | 驱动其他 Agent 或人类 |
| **用户沟通工具** | Agent 主动调用 | 向用户传递信息 |
| **事件触发工具** | Agent 注册、外部触发 | 驱动 Agent 开始执行 |

### 2.2 各类工具的例子

| 类型 | 例子 |
|---|---|
| 感知 | web_search、knowledge_base_search、fetch_url、find_file、grep_file、read_file |
| 执行 | shell_exec、code_interpreter、write_file、edit_file、send_email |
| 协作 | spawn_subagent、send_message_to_subagent、cancel_subagent、list_agents |
| 用户沟通 | reply_to_user、send_card_to_user、send_user_notification |
| 事件触发 | set_timer、monitor_shell、connect_channel |

### 2.3 设计重点

- **感知工具**：控制输出信息量，防止上下文爆炸。
- **执行工具**：错误代价极高，安全约束是核心。
- **协作工具**：并行执行、专业化分工。
- **用户沟通工具**：从单会话扩展到多渠道异步消息。
- **事件触发工具**：注册时主动调用，触发时外部回调。

## 三、4.2 工具设计的通用原则

### 3.1 核心概念：ACI（Agent-Computer Interface）

> 工具应该对应 Agent 的目标，而不是底层的 API 操作。核心是让工具对 Agent 而非对人友好。

### 3.2 原则一：能力的表达形式

#### 3.2.1 谱系：专用工具 ←→ Skill

| 形态 | 优点 | 代价 |
|---|---|---|
| **专用工具** | 确定性高、可测试、参数受 schema 约束 | 每个工具定义占数百 token |
| **Skill** | 少量通用工具覆盖大量场景；目录只占几十 token | 需生成合法命令行参数，转义复杂 |

#### 3.2.2 默认取向：通用工具优于专用工具

> 与其提供四则运算计算器，不如提供通用的 code_interpreter，让 Agent 通过执行 Python 代码完成任意数学计算。提供通用工具相当于给 Agent 一个“元能力”。

#### 3.2.3 粒度：偏向整合而非细分

- 粒度过细 → 工具数量激增，选择负担大。
- 粒度过粗 → 单个工具过于复杂。
- 核心标准：功能相似性和使用场景重叠度。
- 例：read_document 统一处理 PDF/Word/PPT，通过 file_type 区分。

#### 3.2.4 什么时候退回专用工具

| 情况 | 理由 |
|---|---|
| 安全、权限与审计 | 需要精细授权、审计留痕 |
| 屏蔽平台差异 | 给出更好的反馈（如 grep/find） |
| 使用频率极高 | 值得专属入口 |
| 参数结构复杂 | 结构化 schema 能更好引导传参 |

#### 3.2.5 四个决策维度

| 维度 | 说明 |
|---|---|
| 安全与权限 | 需要精细授权、审计留痕，用专用工具 |
| 参数复杂度 | 涉及嵌套对象、复杂约束，用专用工具 |
| 变更频率 | 频繁变化用 Skill；稳定底层用专用工具 |
| 模型能力 | 强模型可用 Skill + 通用执行器；弱模型需要结构化 schema |

#### 3.2.6 让代码来编排工具调用

> 通用执行器让模型可以用代码串联多个工具，而不是一次调用一个工具、把每个中间结果都搬进上下文。LLM 一次性生成脚本，中间变量留在执行环境，只有最终结果返回 LLM。Token 消耗可降低约两个数量级。

### 3.3 原则二：工具描述的艺术

- 核心：让 LLM 知道“什么时候用”，而不只是“能做什么”。
- 边界比能力重要：明确做不到什么、不接受什么输入。
- 参数描述：具体例子代替抽象规范。
- 返回值描述清楚；耗时工具注明执行代价。
- 附带 1-5 个真实调用示例，准确率可从 72% 提升到 90%。
- 调试原则：Agent 选错工具时，优先检查工具描述，而非怀疑模型。

### 3.4 原则三：参数传递的保真性

**反模式：静默输入转换 / 静默参数注入**

- Cursor 把中文弯引号静默转为英文直引号，导致模型困惑。
- 某 IDE 的 bash 工具自动附加参数，导致旧版 Git 报错。

**核心原则：**

> 模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。参数传递必须透明，不得在模型不知情的情况下修改输入或输出。

## 四、4.3 工具生态：MCP 与 Skill Hub

### 4.1 两条分发渠道

| 渠道 | 分发对象 | 接入方式 | 代表 |
|---|---|---|---|
| **MCP 协议** | 专用工具 | 客户端-服务器协议 | Anthropic MCP |
| **Skill Hub** | Skill 文件夹 | 注册表（npx） | skills.sh、ClawHub |

### 4.2 MCP 三类原语

| 原语 | 对应 |
|---|---|
| 工具（Tools） | 模型可执行的操作 |
| 资源（Resources） | 应用可读取的数据 |
| 提示（Prompts） | 用户可选用的模板 |

### 4.3 第三方安全风险

| 风险         | 说明                       |
| ---------- | ------------------------ |
| 工具描述投毒     | 恶意服务器在 description 中夹带指令 |
| 恶意或被劫持的服务器 | 供应链攻击、篡改返回结果             |
| 同名工具遮蔽     | 诱导 Agent 路由到攻击者          |
| Skill 恶意代码 | Skill 包含可执行代码，可在用户电脑运行   |

### 4.4 缓解措施

- 接入前审查工具描述（当作不可信输入审计）。
- 锁定服务器版本，拒绝静默更新。
- 最小权限凭证。
- Sidecar 机制：独立安全审查模型只看结构化数据。
- 隔离环境：第三方 Skill 在沙盒中运行，不处理敏感信息。

## 五、4.4 工具太多怎么办：层次化组织与主动工具发现

### 5.1 工具过多的三个伤害

| 伤害 | 说明 |
|---|---|
| 选择正确性下降 | 工具超过 100 个，模型容易选错 |
| Token 开销巨大 | 5 个 MCP 服务器可能引入数万 token |
| KV Cache 失效 | 工具集变动导致缓存失效 |

### 5.2 三层解决方案

| 层次 | 核心思想 | 代表 |
|---|---|---|
| **层次化组织与按需加载** | 工具定义事先备好，但不全量塞进上下文 | Cursor 索引、Pi Coding Agent |
| **主动工具发现** | Agent 主动声明能力缺口，系统动态匹配注入 | MCP-Zero、Claude Tool Search |
| **Skills** | 把工具当成可随手翻阅的参考资料 | SKILL.md 渐进式披露 |

### 5.3 层次化组织

- **按需加载**：只暴露索引，需要时查询定义。
- **层次化分类**：搜索、读取、解析、查询。
- **检索式预筛选**：按语义相似度先筛出一批候选工具再注入。

### 5.4 主动工具发现

- Agent 在执行中意识到能力缺口，主动声明需求。
- 系统通过服务器级 → 工具级两层语义路由匹配注入。
- MCP-Zero 在 2800 个工具上节省约 98% 的 token。
- 动态加载的工具 schema 追加到上下文末尾，静态前缀保持稳定，缓存持续命中。

### 5.5 Skills：按需查阅

- Agent 启动时只看到目录（name + description）。
- 需要时读取 sub-skill，顺着引用逐层深入。
- 不需要嵌入索引 + 语义匹配的基础设施。
- 更接近人使用参考资料的方式。

### 5.6 向量检索的误差与分层防御（用户问答）

**用户问：** 工具过多，通过语义进行向量数据库的查询，但这个是有误差的，可能给出的参数不合适没有查到，或查找到不合适的工具。

**核心结论：** 向量检索是概率性、有损的匹配过程，不是确定性的精确查找。必须引入多层防御：

| 层次 | 防御策略 |
|---|---|
| **查询侧** | 结构化声明（MCP-Zero 的结构化请求块）；能力缺口描述；上下文注入 |
| **检索侧** | 混合检索（向量+BM25）；层次化路由（服务器→工具）；重排序；阈值与降级 |
| **执行侧** | 结构化错误反馈；重试机制；回退到通用工具 |
| **演化侧** | 动态创建工具；描述优化；用户反馈 |

**停止点与契约：** 我们接受检索误差，但承诺误差可恢复、可降级、可请求人工。

## 六、4.5 感知工具

### 6.1 核心挑战：信息洪水

- 返回信息量远超 Agent 处理能力。
- 通用做法：工具层面集成上下文感知压缩（超过阈值自动压缩）。

### 6.2 四类设计重点

| 类型 | 设计要点 |
|---|---|
| **搜索类** | 返回结构化候选列表（标题、位置、摘要），提供分页/cursor |
| **读取类** | 支持 offset/limit，明确标示截断（禁止静默截断） |
| **只读性红利** | 安全缓存 + 并行执行 |
| **多模态** | 按内容类型选择：纯文字用文本提取，布局敏感保留图像 |

### 6.3 多模态感知三条路径

| 路径 | 说明 | 优劣 |
|---|---|---|
| **原生多模态** | ViT 编码器，统一语义空间 | 能力上限最高，token 开销大 |
| **提取为文本** | OCR/转录 → 纯文本 | 节约 token，信息损失 |
| **工具化分析** | 多模态模型封装为工具 | 上下文只保留问题+结果，灵活 |

**实验 4-3 结论：** 原生多模态在图表分析、布局理解上最佳；提取为文本在纯文本文档上成本效益最高；工具化模式在交互式场景中灵活。

## 七、4.6 执行工具

### 7.1 核心问题：错误代价极高

- 误删文件、服务中断、财务损失。

### 7.2 安全机制的层次化设计

| 层次 | 措施 |
|---|---|
| **输入验证** | 检查路径遍历、命令注入、参数格式；快速失败 |
| **权限控制** | 限制工作目录、禁止命令黑名单、配额和速率限制 |
| **提议者-审核者** | 事前审批（不同家族、相似能力的模型互审）+ 事后验证（模态切换） |
| **Sidecar** | 与主模型流式输出并行，门控单次工具调用；只读结构化字段防注入；拒绝熔断器 |
| **自动验证** | 写入后自动 linter，返回结构化错误 |
| **沙盒隔离** | 进程级 → 容器 → microVM；venv 不是沙盒 |
| **可观测性** | 日志、审计追踪、性能指标、告警 |
| **幂等性** | 唯一标识去重；先查询后变更；“预检-确认”两段式 |

### 7.3 Sidecar 的并行/串行澄清（用户问答）

**用户问：** Sidecar 模式不也要在进行操作前进行审查吗，为什么说是并行的，这个审核完才进行，不是串行的吗？

**核心澄清：**
- **串行部分（门控）**：工具执行必须等 Sidecar 审查通过。这是串行的。
- **并行部分（重叠）**：Sidecar 的审查过程，与主模型继续生成后续内容（后续思考、其他工具调用）是并行的。
- **“并行”指的是审查与主模型生成的重叠，而不是审查与工具执行的并行。**

**时间线：**
```
主模型：生成工具调用 A → 继续生成文本 → 继续生成工具调用 B → ...
Sidecar：        ↑ 开始审查 A → 审查完成 → 放行 A
工具执行：                              ↑ A 开始执行
```

**费曼式类比：** 你在餐厅点菜，服务员（Sidecar）立刻去后厨检查过敏原，你继续看菜单；检查通过后，后厨才开始做菜。看菜单和检查并行；检查和做菜串行。

### 7.4 Sidecar 与提议者-审核者的对比

| 维度 | 提议者-审核者 | Sidecar |
|---|---|---|
| 执行时机 | 操作前/后 | 与主模型流式输出并行，门控单次调用 |
| 审查对象 | 操作合理性/结果 | 操作本身 |
| 输入隔离 | 相似信息 | 刻意隔离主模型自由文本 |

### 7.5 幂等性与取消语义

- 幂等：同一操作执行多次影响相同，可安全重试。
- 非幂等操作：采用“预检-确认”两段式。

**契约：** 我们接受执行错误不可避免，但承诺错误可恢复、可审计、可回滚。

## 八、4.7 协作工具

### 8.1 核心价值：专业化分工

- 构建一组各自专精的 Agent，通过协作解决问题。
- 每个子 Agent 可独立优化提示词、工具集、知识库。

### 8.2 子 Agent 提示词关键要素

| 要素 | 作用 |
|---|---|
| 角色定义 | 明确身份 |
| 上下文来源标注 | 防注入，区分信息源 |
| 任务边界 | 明确职责 |
| 输出格式 | 降低解析负担 |

### 8.3 协作机制三组原语

| 原语组 | 工具 |
|---|---|
| 启动与取消 | spawn_subagent, cancel_subagent |
| 消息传递 | send_message_to_subagent |
| 发现 | list_agents |

### 8.4 多种协作形态

- 同步调用、异步调用、流式协作、多轮交互。

### 8.5 人工介入（HITL）

- 超时和降级策略：5 分钟无响应采用保守策略；优先级队列。
- 反馈循环：批准/拒绝理由 → 知识库/Skill 或后训练数据。

**契约：** 我们接受协作中的错误级联和同质趋同，但承诺通过独立验证和差异化降低风险。

## 九、4.8 本章小结（原文整合）

> 工具设计决定 Agent 的能力上限。第一个决策是能力用什么形式表达——默认往通用的一端靠，只在安全权限、参数复杂、使用频率极高和平台差异这四种情况下退回专用工具；它与“一次让模型看见多少条能力”是两个独立的决策，前者定每条能力的常驻成本，后者定同时暴露多少条。能力靠两条渠道分发：MCP 协议统一专用工具的接入，Skill Hub 用包管理器分发 SKILL.md；两条渠道都把引入一条能力的成本压到了一条命令，也都扩大了信任边界，因此必须审查描述与版本、隔离凭证，并保证模型看到的参数与工具真正执行的参数一致。当工具增长到成百上千，层次化组织、按需加载、主动发现与 Skills 依次接管，把“选哪个工具”变成“查哪条资料”。
>
> 本章展开的是五类工具中由 Agent 主动调用的三类：
> - **感知工具**：关键在于粒度权衡、上下文感知的智能总结，以及分页与显式截断等接口设计；只读性使其天然适合缓存与并行。
> - **执行工具**：关键在于层次化的安全防护、提议者-审核者审查（事前审批与事后验证）与 Sidecar 机制。
> - **协作工具**：关键在于子 Agent 的生命周期原语（创建、消息、取消、发现）和人工介入的学习闭环。
>
> 剩下的两类——事件触发工具与用户沟通工具——由外部事件驱动，或需要在用户不一定在线时跨渠道异步触达，它们的设计离不开事件驱动的异步运行时，因此放在第六章讨论。
>
> 本章聚焦 Agent 如何使用工具，下一章要回答一个更基本的问题：Agent 能不能通过写代码来创造工具？

## 十、体系化总结：功能-问题-防御-边界

| 工具类型 | 功能 | 新问题 | 防御 | 边界/契约 |
|---|---|---|---|---|
| **感知** | 获取信息 | 信息洪水 | 压缩、分页、截断、缓存、并行 | 接受信息损失，承诺可感知可恢复 |
| **执行** | 改变世界 | 不可逆错误 | 输入验证、权限、提议者-审核者、Sidecar、沙盒、幂等 | 接受错误不可避免，承诺可恢复、可审计、可回滚 |
| **协作** | 分工协作 | 错误级联、同质趋同 | 结构化移交、独立验证、差异化、预算与取消 | 接受协作风险，承诺通过验证和差异化降低 |
| **生态** | 接入第三方 | 投毒、供应链、遮蔽 | 审查描述、锁版本、最小权限、Sidecar、隔离 | 只信任可信来源，不可信 Skill 沙盒运行 |
| **规模** | 工具过多 | 选择错误、token 爆炸、缓存失效 | 层次化、按需加载、主动发现、Skills | 接受检索误差，承诺可恢复可降级 |

## 十一、问答与深入讨论整合

| 问题 | 核心结论 |
|---|---|
| **Sidecar 为什么是并行不是串行？** | 对工具执行是串行门控；对主模型生成是并行重叠。门控是安全底线，并行是体验优化。 |
| **向量检索有误差怎么办？** | 分层防御：查询侧结构化、检索侧混合+层次+重排序、执行侧结构化错误+重试、演化侧动态创建+描述优化。契约：接受误差，承诺可恢复。 |
| **工具过多语义查询误差？** | 同上。核心：混合检索、层次路由、重排序、阈值降级。 |
| **工具的功用与缺陷？** | 感知：信息洪水；执行：不可逆错误；协作：错误级联；生态：供应链；规模：选择错误。对应防御见上表。 |
| **功能引入必然带来新问题，如何停止？** | 停止点三准则：风险转移到可承受层级；修复成本 < 缺陷损失；明确约定子领域，领域外明确接受。最终签订契约。 |
| **MCP 未来最需扩展什么？** | 会话生命周期、异步事件流、双向通信、能力声明、细粒度权限。 |
| **多来源工具重叠如何选择？** | 多维度评分（功能、格式、质量、成本、信任度）；支持试调用和能力声明。 |
| **执行-验证-反馈适用哪些场景？** | 代码写入、文件写入、数据库写入、API 调用、配置修改；高成本/不可逆操作（大规模删除、物理操作、高风险交易）不适用。 |
| **工具爆炸除了主动发现还有什么？** | 层次化、工具路由器、高阶技能、垃圾回收、使用记忆、代码编排、动态创建。 |

## 十二、费曼式总结

- **工具是 Agent 的手脚和感官**：感知（眼睛）、执行（手脚）、协作（团队）、沟通（嘴巴）、事件（耳朵）。
- **ACI**：工具应该对 Agent 友好，而不是对人友好。
- **形态 vs 披露**：专用工具 vs Skill；全量注入 vs 按需加载。
- **工具生态**：MCP 统一接入，Skill Hub 分发文件夹；第三方风险必须审查、隔离、最小权限。
- **工具太多**：层次化、按需加载、主动发现、Skills；把“选哪个工具”变成“查哪条资料”。
- **感知工具**：防止信息洪水；搜索返回候选列表，读取明确截断；多模态三条路径。
- **执行工具**：错误代价高；层次化安全：输入验证、权限、提议者-审核者、Sidecar、沙盒、幂等。
- **协作工具**：专业化分工；三组原语；HITL 学习闭环。
- **最终停止点**：契约——我们承诺解决什么，明确不解决什么。

**一句话：**

> **工具设计决定 Agent 的能力上限。**
> **核心决策：能力用什么形式表达（专用工具 vs Skill），一次让模型看见多少条（全量 vs 按需）。**
> **两条分发渠道：MCP 协议、Skill Hub。**
> **规模膨胀：层次化组织、按需加载、主动发现、Skills。**
> **三类主动工具：感知（防信息洪水）、执行（防不可逆错误）、协作（防错误级联）。**
> **两类留待第六章：事件触发、用户沟通。**

思考题
1. ★★ MCP 标准将工具定义从 Agent 框架中解耦了出来。但标准化也意味着复杂的工具交互模式（如流
式输出、双向通信、有状态会话）可能难以在标准协议中表达。你认为 MCP 未来最需要扩展的能力是
什么？
2. ★★ 在 MCP 生态中，不同的 MCP 服务器可能提供功能高度重叠的工具。当 Agent 面对多个来源不
同但功能相似的工具时，应该如何选择？如果不同来源的同名工具在行为上略有差异（比如一个返回摘
要，另一个返回全文），Agent 是否有能力感知并利用这种差异？
3. ★★ 本章提出了“执行-验证-反馈”闭环（如写代码后自动运行 linter）。这种“操作后立即自动验证”的模
式还可以应用到哪些工具场景？是否存在某些操作，其验证本身的成本或风险超过了操作本身，导致这
种模式不可行？
4. ★★ 本章提出了“工具爆炸”问题——Agent 面对数千个工具时选择精度下降。除了主动工具发现，还有
哪些方案？可以参考人类专家在面对大量可用工具时的策略。
