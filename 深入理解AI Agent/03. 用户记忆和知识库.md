
> 本章解决的核心问题：**如何让 Agent 在对话结束后仍然记住用户、记住知识。**
> 持久化记忆分为两个尺度：
> - **用户记忆**：针对单个用户的个性化记忆，让 Agent 成为“懂你的助手”。
> - **知识库**：面向所有用户共享的集体知识，让 Agent 成为“领域专家”。
> 两者共用底层技术（向量检索、知识压缩），也面临同样的麻烦（信息冲突、知识过期、检索不准）。

## 二、3.1 用户记忆系统

### 2.1 核心定义

要让 Agent 跨会话提供个性化服务，需要一层持久的用户记忆。它不保存每句对话，而是用额外的 LLM 调用提取、压缩并审查对未来有用的事实。

**提取结果三条规则：**
- **选择性**：丢弃“搜索返回3个选项”这类短期细节。
- **抽象化**：把本次“靠窗座位”归纳为长期偏好。
- **结构化**：用可检索的字段保存事实。

### 2.2 记忆能力的评估：三层次框架

**学术界基准：LoCoMo**
- 平均约 300 轮、最多 35 个会话的超长多轮对话。
- 任务类型：问答（单跳、多跳、时间推理、开放域、对抗性）、事件摘要、多模态对话生成。

**用户记忆能力八项归纳：**
1. 个人信息保留
2. 偏好追踪
3. 上下文切换
4. 记忆更新
5. 多会话连续性
6. 复杂思考（如对花生过敏的用户推荐泰国菜时主动提醒）
7. 时间感知
8. 冲突解决

**三层次评估框架（本书核心）：**

| 层次 | 名称 | 要求 | 例子 |
|---|---|---|---|
| 第一层 | **基础回忆** | 准确存储和检索用户直接提供的、结构化、无歧义的信息 | “我的会员号是 12345” |
| 第二层 | **多会话检索** | 面对不同对象、不同时期的多段会话，检索出所有相关信息并推理判断 | 用户有两辆车，要求“为我的车预约保养”，系统需找出两辆车并主动询问哪一辆 |
| 第三层 | **主动服务** | 综合多个会话、甚至很久以前的信息，提供预见性的主动帮助，发现深层联系 | 预订国际航班时主动关联护照信息，发现即将过期并预警；手机损坏时整合所有保障方案 |

**实验 3-1：用三层次框架评估记忆系统**
- 每层各 20 个测试用例。第一层由单个会话构成；第二、三层由多个跨时间、跨对象的会话构成（每个用例约 50 轮）。
- 要求被测 Agent 根据第一个会话生成记忆，然后根据记忆和下一个会话修改记忆（仅能访问记忆，不可回看原始对话），直到所有会话处理完毕，再根据记忆回答新问题。
- 用 LLM-as-a-judge 对回答与参考答案对比评分。
- 评估集与脚本在 `user-memory` 项目中。

### 2.3 记忆的层次结构

记忆系统的设计可拆成三个维度：**放哪里、怎么存、存什么**。本节先回答“放哪里”。

| 层次 | 定义 | 特点 |
|---|---|---|
| **轨迹（Trajectory）** | 一次 Agent 运行过程中的完整历史记录（用户消息 + 模型回复 + 工具执行结果） | 按时间顺序排列，只增不改（append-only）；为当前决策提供即时上下文 |
| **用户长期记忆** | 跨会话、跨实例的持久化存储，通常以键值对与用户 ID 绑定 | 存储偏好设置、历史交互摘要、提取的知识点；会被反复改写、合并、淘汰 |
| **业务状态** | 开发者定义的高层状态抽象，表示任务的逻辑阶段（如“需要澄清”“处理请求中”“等待付款”） | 在事件驱动的 Agent 架构中尤为重要（第六章讨论） |

**关键区分：**
- 轨迹是**单次会话的完整原始记录**，按时间追加且不修改。
- 用户长期记忆是**跨会话提炼出的稳定信息**，会被反复改写、合并、淘汰。
- 前者是流水账，后者是档案。

### 2.4 用户记忆的四种存储格式（图 3-2）

同一条用户信息，可以用不同的粒度和结构来表示。

| 格式 | 特点 | 优点 | 缺点 |
|---|---|---|---|
| **Simple Notes** | 每条记忆是一个最小、不可再分的事实（如“用户邮箱：john@example.com”） | 开销极低，支持 O(1) 操作 | 信息关联性完全丢失，需重新拼凑碎片 |
| **Enhanced Notes** | 每条记忆保存为包含完整上下文的段落（如“用户在 TechCorp 担任高级软件工程师，专注于机器学习已有三年……”） | 保留叙事结构，语义完整丰富 | 存储冗余，更新复杂（属性变化需重写多个段落） |
| **JSON Cards** | 三层嵌套结构（类别→子类别→键值对，如 `work.position.title`） | 支持部分更新，可预测且可扩展 | 刚性结构假设信息可清晰分类，强制归入单一类别会丢失多维性 |
| **Advanced JSON Cards** | 每张卡片不仅记录事实，还加入叙事背景（backstory）、主体身份（person）、与用户的关系（relationship）和时间戳 | 解决消歧问题，支持知识管理 | 生成和维护成本较高 |

**实践选择标准：**
- 关键且少量的数据（用户偏好、关键人物关系）→ Advanced JSON Cards。
- 大量且非关键的对话事实 → Simple Notes。
- 多数生产系统采用混合模式。

**实验 3-2：记忆策略对比实验**
- 在 `user-memory` 项目中切换四种模式，在三层次评估集上测试。
- 观察：Simple Notes 在第一层多数通过，但在第二、三层频繁失分；Advanced JSON Cards 在消歧和跨会话关联上表现最好，但维护成本高。

### 2.5 进阶知识表示形态：可执行代码（User as Code）

- 把用户状态改成带类型的可执行对象，规则写成普通函数，让“表示”和“推理”使用同一种可验证介质。
- 借鉴“预写日志 + 检查点”机制：会话结束后先把事实追加到只增日志，再定期从完整日志重建带类型的派生状态。
- 既保留原始证据，也能得到可查询、可执行的派生状态。

### 2.6 用户记忆的认知科学基础

认知科学把记忆划分为工作记忆和长期记忆。长期记忆细分为三种类型，在 Agent 记忆中都有直接对应：

| 类型 | 人类例子 | Agent 对应 |
|---|---|---|
| **情景记忆** | “上周三和同事在那家意大利餐厅吃了一顿很棒的晚餐” | “用户订了下周五去东京的 ANA 航班” |
| **语义记忆** | “意大利的首都是罗马” | “用户是素食者”“用户偏好靠窗座位” |
| **程序记忆** | 骑自行车的能力 | 从反复订机票中学到的流程：“先搜索直飞航班 → 确认座位偏好 → 使用常旅客号码 → 订餐” |

**三套分类体系的关系（表 3-1）：**

| 分类体系 | 回答的问题 | 具体类别                                                       |
| ---- | ----- | ---------------------------------------------------------- |
| 记忆层次 | 存在哪里？ | 轨迹、用户长期记忆、业务状态                                             |
| 存储格式 | 怎么存？  | Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards |
| 认知类型 | 存什么？  | 情景记忆、语义记忆、程序记忆                                             |

三套体系是**正交**的，可以自由组合。

### 2.7 记忆框架案例（图 3-3）

**Mem0：从写入时消歧到检索时推理**
- **2025 年论文与 v2**：对话结束后，LLM 先抽取候选事实；再用向量检索找到相近的已有记忆，由 LLM 在 ADD、UPDATE、DELETE、NOOP 中做出决定。优势是记忆库简洁一致；风险是一次错误更新会不可逆丢失历史。
- **2026 年 v3**：用一次 LLM 调用抽取事实，只做 ADD；“住在北京”和“搬到上海”作为带时间信息的两条事实并存。查询时融合语义相似度、BM25 关键词和实体匹配，并结合时间信息排序。避免了错误 UPDATE/DELETE，减少 LLM 调用，提高检索质量。报告：LoCoMo 从 71.4 → 92.5（+21.1），LongMemEval 从 67.8 → 94.4（+26.6）。

**Memobase：用户画像与事件记忆**
- 用户画像（Profile）：一组可由开发者配置的槽位（如 basic_info→姓名、interest→兴趣偏好、work→职位），存放稳定用户属性。
- 事件记忆（Event Memory）：按时间线记录用户经历的事件。
- 工程上采用缓冲批处理策略，摊薄 LLM 调用成本。

**多类型记忆协同参考架构（图 3-4）：**
- 情景/语义/程序记忆 + 工作记忆。
- 工作记忆与长期记忆动态交互：重要信息选择性转移到长期记忆，相关长期记忆被激活并加载到工作记忆。
- 与轨迹的区别：轨迹是不可变的完整事件序列，工作记忆是经过筛选和激活的动态子集。

### 2.8 记忆压缩与整理机制

三层压缩策略：
1. **重要性评分筛选**：综合访问频率、时间衰减、情感强度、信息独特性。低于阈值的记忆标记为可压缩或可删除。
2. **聚类**：相似记忆分组，每组生成代表性摘要（如多次天气对话压缩为“用户经常询问天气，特别关心降雨”）。原始详细记忆可存档到二级存储。
3. **抽象和泛化**：从具体情景记忆中提取一般性规律，转化为语义或程序记忆。

### 2.9 隐私保护：日志脱敏

**实验 3-3：基于本地模型的智能日志脱敏**
- 通过 Ollama 调用本地 Qwen3 0.6B 小模型实现 PII 检测与脱敏。
- 识别结构化信息（身份证号、银行卡号）、半结构化信息（地址）、自然语言表达的敏感内容（如“我的密码是 abc123”）。
- 输出 JSON Schema 结构化结果，包含敏感信息类型、位置、置信度。
- 相比正则表达式，基于 LLM 的脱敏召回率达 95% 以上，假阳性显著降低。

## 三、3.2 RAG 基础：构建 Agent 的知识获取管道

### 3.1 RAG 核心流程（图 3-5）

```
① 用户查询 → ② 检索（稠密检索 + BM25 → Top-K 文本块）
→ ③ 增强（查询 + 检索结果 → 构造完整 Prompt）
→ ④ 生成（LLM 综合上下文 → 生成回答）
```

**书中例子：**
- 查询：“故意杀人罪判几年？”
- 检索到：《刑法》第232条：“故意杀人的，处死刑、无期徒刑或者十年以上有期徒刑……”
- 增强后的 Prompt：“基于以下法条回答问题：[《刑法》第232条……] 问：故意杀人罪判几年？”
- 生成回答：“根据《刑法》第232条，故意杀人罪处死刑、无期徒刑或者十年以上有期徒刑；情节较轻的，处三年以上十年以下有期徒刑。”

### 3.2 文档分块（Chunking）

**为什么必须分块？**
1. 嵌入模型有长度限制：一整篇文档压缩成一个向量时，多个主题混在一起，向量无法精确表达任何一个。
2. 检索目标只需相关片段：片段太大，会连带引入大量无关内容，浪费窗口、稀释注意力。

**三类分块策略：**

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **固定大小切分** | 按固定 token 数（如 512）切分，保留重叠（50–100 token） | 简单、可预测 | 无视文档结构，可能拦腰截断段落/代码/表格 |
| **递归/结构感知切分** | 按自然边界（章节、段落、句子）递归切分 | 保留结构，生产系统默认 | 需要文档有显式结构 |
| **语义切分** | 计算相邻句子嵌入相似度，在语义“断崖”处切分 | 块内主题单一，质量高 | 需额外嵌入计算 |

**块大小与重叠量的权衡：**
- 块太小：信息不完整，脱离上下文后语义模糊。
- 块太大：混杂多个主题，嵌入向量被稀释，检索精度下降。
- 常见起点：每块 256–1024 token，相邻块重叠 10%–20%，再根据检索质量调优。

**分块的固有缺陷：**
> 分块会切断片段与其原始上下文的联系——“该公司”指代谁、这段话出自哪份报告，这些信息留在了块的外面。

### 3.3 稠密嵌入：从词汇关联到语义理解（图 3-6）

**什么是嵌入？**
- 把词或句子转化成一串数字（向量），语义相近的内容向量也相近。
- 向量空间像一张高维地图，每个词/句子是地图上的一个点。
- 经典例子：“国王” - “男性” + “女性” ≈ “女王”。

**稠密 vs 稀疏：**
- 稠密：每个维度都有数值。
- 稀疏：大部分维度为零。

**余弦相似度：**
$$
\cos(\theta) = \frac{A \cdot B}{|A| \times |B|}
$$
- 值越接近 1，方向越一致，语义越相似。
- 为什么用夹角而不是距离？因为我们关心方向（语义），而非长度（文本长度或频率）。

**手算示例（书中）：**
- “如何养猫” A = (0.9, 0.5, 0.1)
- “猫咪饲养指南” B = (0.8, 0.6, 0.1)
- “股票投资策略” C = (0.1, 0.1, 0.9)
- A 与 B 相似度 ≈ 0.99（非常相似）
- A 与 C 相似度 ≈ 0.25（差异很大）

**技术演进（图 3-6）：**

| 阶段 | 代表 | 维度 | 特点 |
|---|---|---|---|
| 2013 | Word2Vec | 300维 | 静态词向量，共现关系 |
| 2014 | GloVe | 300维 | 全局统计，矩阵分解 |
| 2018 | BERT | 768维 | 上下文感知，Transformer MLM |
| 2019 | Sentence-BERT | 768维 | 句子级嵌入，孪生网络对比学习 |
| 2024 | BGE-M3 | 1024维 | 多语言长文本，多阶段混合训练 |

**关键飞跃：** 从“静态词向量（一词一向量）”到“上下文感知嵌入（一词多向量）”，解决了多义词问题（如 bank 河岸 vs 银行）。

**实验 3-4：ANN 索引算法比较**

| 特性 | ANNOY（基于树） | HNSW（基于图） |
|---|---|---|
| 构建速度 | 快 | 较慢 |
| 内存占用 | 低 | 较高 |
| 增量更新 | 不支持 | 支持（建议定期重建） |
| 查询精度 | 较高 | 极高 |
| 适用场景 | 静态数据集 | 动态场景 |

### 3.4 稀疏嵌入：精确匹配的关键词检索（图 3-8）

**核心思想：**
- 基于词袋模型，忽略词序。
- 文档表示为极高维稀疏向量，只有出现的词对应维度非零。
- 从 TF-IDF 发展到 BM25。

**BM25 评分机制：**
$$
\text{Score}(Q, D) = \sum_i \text{IDF}_{\text{BM25}}(q_i) \cdot \frac{\text{TF}(q_i, D)(k_1 + 1)}{\text{TF}(q_i, D) + k_1(1 - b + b \cdot \frac{|D|}{\text{avgdl}})}
$$

| 组件             | 作用                              |
| -------------- | ------------------------------- |
| **词频饱和（TF）**   | \(k_1\) 控制饱和速度，词频翻倍不会导致得分线性翻倍   |
| **逆文档频率（IDF）** | 衡量词的稀有度，稀有词权重远高于常见词             |
| **长度归一化（b）**   | \(b \in [0,1]\) 控制归一化强度，避免长文档偏倚 |

**实验 3-5：从零实现 BM25 搜索引擎**
- 查询“模型蒸馏”，在 10 篇文档语料上演示。
- “蒸馏”比“模型”更稀有，IDF 更高，单次出现贡献更大。
- 最终排序：doc_1 (3.67) > doc_7 (1.68) > doc_5 (1.22) > doc_3 (0.82)。
- **结论：** 稀疏检索精确匹配关键词，但读不懂同义表达。

### 3.5 混合检索与重排序（图 3-9）

**为什么混合？**
- 稠密检索：懂语义，可能漏掉关键词。
- 稀疏检索：精确匹配，读不懂同义词。
- 两者互补，合并结果。

**三阶段流水线：**
```
① 并行检索（稠密 + 稀疏）
    ↓
② 结果融合（RRF：倒数排名融合）
    ↓
③ 神经重排序（跨编码器精排）
```

**倒数排名融合（RRF）：**
$$
\text{得分} = \sum \frac{1}{k + \text{rank}}
$$
- \(k\) 常取 60，平滑排名差距。
- 简单稳健，但只利用排名信息。

**神经重排序（Neural Reranking）：**
- 使用**跨编码器（Cross-Encoder）**，将查询和文档拼接后逐词比对，输出相关性得分。
- 与检索阶段的**双编码器（Bi-Encoder）**形成对比：双编码器独立编码，速度快但精度低；跨编码器深度交互，速度慢但精度高。
- 重排序不是补救 RRF，而是换用更强的匹配范式。
- 常用模型：BAAI/bge-reranker-v2-m3。

**检索质量指标（表 3-3）：**

| 指标 | 回答的问题 |
|---|---|
| **recall@k** | 该找的找到了吗？ |
| **MRR** | 找到得够不够靠前？ |
| **nDCG** | 整个排序列表的质量如何？ |
| **检索失败率** | 正确信息未出现在 top-20 的比例 |

**实验 3-6：混合检索流水线**
- 展示稠密、稀疏、重排序的组合效果。
- 重排序器显著提升最终结果质量，将被单一方法低估的相关文档提升到顶端。
- **结论：** 没有哪种单一检索策略在所有场景下都可靠，组合才是生产级 RAG 的正确做法。

## 四、3.3 超越扁平文本：知识的组织与检索

### 4.1 为什么扁平文本不够？两个案例

**案例一：黑猫白猫的计数问题**
- 知识库有 100 个独立案例文档（90 只黑猫、10 只白猫），用户问“比例是多少？”，受限于 top-k（如 20），大部分案例根本不会被检索到。模型只能基于不完整样本得出错误结论。
- 解决：预先生成摘要“共有 100 只猫：90 只黑猫（90%）和 10 只白猫（10%）”并索引。

**案例二：Xfinity 优惠资格的边界问题**
- 知识库是客服工单归档，几百条工单各自记录一次真实处理结果。护士来问“我能不能享受优惠”时，有三重障碍：
  1. 最近邻偏置：“护士”与“医生”语义最近，模型顺势推断护士也可以。
  2. 边界语义缺失：“仅限……，其他一律不适用”不存在于任何单条工单中。
  3. 完整性信号缺失：模型无从判断自己是否已经看全。
- 解决：离线通读整个工单库，提炼出规则卡“Xfinity 优惠适用于现役与退伍军人、持证医护人员（含护士）；教师等其他职业不适用”。

**结论：** 把原始案例或文档不加处理地直接放进知识库是远远不够的。必须在索引阶段投入计算资源，对原始知识主动提炼、抽象和结构化。

### 4.2 结构化索引：从信息检索到知识建模

**RAPTOR（图 3-10）：树状层次（自下而上递归抽象）**
- 将长文档切分为小的文本块作为“叶子节点”。
- 通过聚类算法将语义相近的叶子节点分组。
- 用语言模型为每个分组生成更高层次的摘要，作为“父节点”。
- 递归进行，最终形成一棵从具体细节（叶子）到高度概括总结（根）的知识树。
- 检索可在多个抽象层次上进行：既能精确回答细节问题，也能提供对宏观概念的理解。

**GraphRAG（图 3-11）：实体-关系图**
- 将文档知识建模为由实体（Entities）和关系（Relationships）构成的知识图谱。
- 通过实体-关系-实体三元组（Triple）构建信息网络，如（北京, 是首都, 中国）、（张三, 就职于, 腾讯）。
- **核心优势一：多跳关系推理**。用户问“我的医生所在医院的地址”时，系统沿“用户 → 医生 → 医院 → 地址”关系链遍历。
- **核心优势二：实体消歧**。区分现实世界中两个同名的“张医生”：（张医生-A, 科室, 牙科）与（张医生-B, 科室, 心脏科）是图中不同节点。
- **局限**：将自然语言转为三元组会导致语义降级。“如果下周还下雨，我就取消去海边的计划，改成去博物馆”被分解后，条件逻辑和时间依赖全部丢失。三元组提取准确性高度依赖 LLM。
- **推荐策略**：分层互补——以完整自然语言保存核心信息，辅以结构化元数据索引；在需要多跳推理和精确消歧的垂直场景，将知识图谱作为专项索引手段。

**实验 3-7：RAPTOR 与 GraphRAG 的知识组织哲学**
- 查询“请解释 SSE 指令集”：
  - RAPTOR 进行“跨层穿梭”：先在高层摘要中定位“SIMD 指令集”宏观概念，再沿树状结构向下钻取。适合“从概念逐步钻进细节”的查询。
  - GraphRAG 在“关系网”中漫游：定位“SSE”实体，遍历关系边找到“XMM 寄存器”“浮点运算”及具体指令。适合“A 和 B 之间是什么关系”的查询。
- **判断标准**：
  - 查询主要是“找到包含某信息的文档片段”→ 混合检索就够了。
  - 查询经常需要跨文档综合或多层次导航→ 结构化索引才值得投入。
- **代价**：索引构建和查询时都需要更多次 LLM 调用，成本和延迟显著增加。

### 4.3 文件系统范式：用目录结构组织知识

字节跳动火山引擎开源的 **OpenViking** 提出第三种哲学：文件系统范式。

**核心设计：**
- 将所有上下文——记忆、资源、技能——映射为虚拟文件系统中的目录和文件，每个条目拥有唯一 URI：
  ```
  viking://
  ├── resources/        # 外部知识：文档、代码库、网页
  ├── user/memories/    # 用户记忆：偏好、习惯
  └── agent/            # Agent 自身：技能、经验
      ├── skills/
      └── memories/
  ```

**L0/L1/L2 三层上下文按需加载：**
- **L0（摘要）**：约 100 tokens 的一句话概述，用于快速判断目录相关性。
- **L1（概览）**：约 2,000 tokens 的核心信息与使用场景，供 Agent 规划决策。
- **L2（全文）**：完整原始内容，仅在需要深入时按需加载。
- 每个目录下自动生成 `.abstract`（L0）和 `.overview`（L1）文件。

**为什么选择 Markdown 纯文本？**
- 用户可直接阅读、编辑和修正 Agent 的知识。
- 可通过 Git 版本控制和回滚。
- Agent 拥有 write_file 能力后，可在工作分支上自主记录和组织知识。

**关键前提：文件之间必须建立链接与索引。**
- 如果只是把知识拆成一堆独立文本文件平铺在目录里，彼此没有交叉引用，Agent 几乎无从在相关条目间导航。
- 正确做法：把知识库组织得像 Wikipedia——每个条目提及其他条目时以链接指向它，辅以入口页与索引页。
- **实践差异**：能力强的模型会自发回指已有条目、维护索引；不少模型不会主动这样做。因此在写入提示词中必须明确要求。

### 4.4 知识应该如何更新

**增量更新：把知识库当代码库**
- 把每次知识变更当成一个 Pull Request（PR）。
- Markdown 知识库、用户记忆文件和规则文档同样应进入 Git，获得差异审查、版本历史、责任追溯和一键回滚。

**提议者—审核者模式的四步闭环：**
1. **Proposer Agent 提交 PR**：从原始证据中发现新事实、冲突或过期内容，在工作分支上提出尽可能小而完整的 diff。
2. **Reviewer Agent 独立审核**：拿到变更前的知识、diff 和原始证据，独立检查每个新断言是否能被证据支持、是否遗漏限定条件、是否与其他文件冲突。
3. **双方迭代至收敛**：Proposer 根据拒绝理由修改 diff，Reviewer 再次回到原始证据复核；只有 Reviewer 明确批准，PR 才可合入。
4. **合入后再发布**：CI 先检查格式、链接、元数据、权限标签；通过后才从已合入的版本增量重建受影响的分块、摘要和向量索引。

**分层管理：**
- **原始证据层**：保存只增不改的对话、轨迹和原始文档。
- **知识层**：保存经过提炼、可持续修订的 Markdown 或代码。
- **服务层**：保存从特定已合入版本生成的检索索引。

**Proposer 和 Reviewer 都必须是 Agent**，而不是两次固定的 LLM API 调用。两个 Agent 应优先使用能力相近但来自不同家族的模型（如 Claude vs GPT，DeepSeek vs Kimi）。权限上强制分工：Proposer 只能写工作分支，Reviewer 只读证据并提交审核结果。

**定期整理：全量重审**
- **去重、去旧与合并**：全量扫描当前知识，识别语义重复、已被取代、过度碎片化或只有表述差异的条目。
- **回到原始数据核查**：不能只在已有摘要之间相互改写，否则早期遗漏和误读会一代代传下去。
- **冲突解决与场景限定**：遇到互相矛盾的说法时，追溯各自的原始信息源，检查它们是否分别在不同时间、对象、地域、任务或前置条件下成立。
- **失效内容的检测与下线**：给每个分块附加版本号、生效/失效时间等元数据。
- **多用户共享的权限与租户隔离**：检索必须按调用者的权限过滤，绝不能让越权文档进入某个用户的上下文。

### 4.5 智能体化 RAG：将知识检索工具化的范式转变（图 3-12、3-13）

**传统 RAG vs 智能体化 RAG：**

| 维度 | 传统 RAG（非智能体化） | 智能体 RAG（Agentic RAG） |
|---|---|---|
| **驱动方式** | 用户查询直接触发检索 | Agent 思考、规划、决策 |
| **检索次数** | 一次性检索 | 多轮迭代检索 |
| **流程结构** | 单向数据流：查询 → 检索 → 生成 | ReAct 循环：思考 → 行动 → 观察 → 思考 → …… |
| **问题处理** | 整体查询直接丢给检索器 | 先分解为子问题，再分别检索 |
| **信息评估** | 不评估检索结果是否充分 | 观察结果，评估是否充分，不充分则继续检索 |
| **纠错能力** | 无。首次检索不精准，结果就不全面 | 有。发现信息不够，可以改写查询、二次检索 |
| **类比** | 在图书馆里只能搜一次，搜完立刻写报告 | 像一位研究员，反复查阅不同书架、调整策略、交叉验证 |

**工作流程：**
1. Agent 思考分析核心需求，自主决定使用什么查询关键词。
2. 行动：调用 `knowledge_base_search` 工具。
3. 观察初步结果后评估信息是否充分。若不够，进入下一轮循环，提炼更精确的查询再次搜索。
4. 只有判断收集到充分信息后，才综合所有上下文生成最终答案。

**RAG 的安全边界：**
- **间接提示注入**：检索到的文档是间接提示注入最典型的载体。攻击者可以把恶意指令藏进会被收录的网页或文档里。
- **知识库投毒**：污染发生在索引之前。
- **防御分两层**：
  1. **指令与数据分离**：对所有检索得到的内容做来源标记。
  2. **不让检索内容直接触发高风险操作**：转账、删除、对外发信这类有副作用的动作，不应仅凭检索内容就自动执行，而要经过独立的授权判断。

**实验 3-8：智能体化 RAG 与非智能体化 RAG 对比**
- 在中文司法问答数据集上对比。
- 简单问题（如“正当防卫是怎么规定的？”）：非智能体化 RAG 响应更快，答案质量相差无几。
- 复杂问题（如“醉酒过失致人重伤且有盗窃前科如何量刑？”）：非智能体化 RAG 首次检索关键词不精确，遗漏关键信息甚至事实性错误；智能体化 RAG 展现多轮迭代检索能力。
- **结论**：智能体化 RAG 的价值在于“解决问题”而非“回答问题”。

### 4.6 上下文感知检索（图 3-14）

**分块的固有缺陷：**
- 标准分块方法不可避免地将紧密关联的上下文分离。
- 一个孤立文本块如“该公司第二季度的收入增长了 3%”，脱离原始上下文后无法回答代词指代、时间参照或实体关系等关键问题。

**上下文感知检索的核心思想：**
- 在向量化索引之前，先利用 LLM 为文本块生成一段简短的、包含核心上下文的“前缀摘要”，然后将前缀与原始文本块拼接后再索引。
- 例如生成前缀：“[本段内容节选自 ACME 公司 2025 年 Q2 财务报告的‘关键业绩指标’章节]”。

**与第二章“上下文感知压缩”的区别：**
- **上下文感知检索**：发生在索引期，针对知识库里的文本块，做“补前缀、加背景”（加法）。
- **上下文感知压缩**：发生在运行期，针对当前会话的对话历史，做“按当前任务裁剪、丢弃无关内容”（减法）。

**效果：**
- 同时增强稀疏检索（BM25 增加可精确匹配的关键词）和稠密检索（前缀注入关键语义背景）。
- Anthropic 研究数据：结合 BM25 可将检索失败率降低 49%，再结合重排序器降幅达 67%。

**实验 3-10 与 3-11：**
- **实验 3-10**：在文档知识库上量化评估上下文感知检索的性能提升。
- **实验 3-11**：将上下文感知检索应用于用户记忆构建。在索引对话历史前增加“上下文生成”步骤，对每个对话块调用 LLM 生成包含关键背景信息的前缀摘要。在处理事实冲突时展现出决定性优势。

### 4.7 从数据集中提取深度知识（图 3-15）

**核心问题：** 隐性知识不在文档里，而在海量结构化案例数据中。

**两阶段流程：**
- **第一阶段：知识提取与结构化**。利用 LLM 将每个案例的非结构化描述转换为包含所有关键判决因素的标准化 JSON 对象。
- **第二阶段：因子分析与重要性建模**。运用数据分析技术发现模式、提炼规律，识别出哪些因素对最终结果具有最显著影响并量化其权重。

**实验 3-12：从结构化数据中提取隐性知识**
- 数据集：CAIL2018 中文刑事判决数据集。
- 知识提取：自下而上因子发现，构建模块化数据模式。
- 因子分析：特征向量化 → KMeans 聚类 → 因子重要性模型。
- 应用：对话式法律咨询 Agent：按因子重要性引导提问 → 检索相似案件原型 → 数据驱动的量刑分析。
- **核心结论：** Agent 不一定要把知识库当成一个只能检索的静态仓库——它可以先把数据“读懂”，提炼出结构化的决策逻辑，再基于这个逻辑来回答问题。

### 4.8 前沿探索：多模态记忆

**三条思路：**

| 维度       | 思路一：原始数据+文本描述 | 思路二：嵌入存上下文    | 思路三：嵌入存参数（Engram）  |
| -------- | ------------- | ------------- | ------------------ |
| **存储位置** | 外部存储          | 上下文           | 模型参数               |
| **表达力**  | 受限于文本描述       | 保留多模态嵌入       | 保留多模态嵌入            |
| **效率**   | 低（需存储原始文件）    | 极高（1 token/条） | 高（写入参数）            |
| **检索方式** | 文本检索 → 读原图    | 注意力机制         | 哈希查表 + 门控          |
| **适用场景** | 人脸识别、声纹识别     | 上下文内多模态记忆     | 长期、跨会话多模态记忆        |
| **局限性**  | 难以表达非文本信息     | 受上下文长度限制      | 需模型支持 Engram，查准率略低 |

**为什么一张人脸/声纹的嵌入只占用 1 个 token？**
- 因为它是压缩后的连续向量，通过投影层映射到模型隐藏空间的一个槽位，不是原始像素/音频的逐点展开。
- 1 个 token 承载了高度压缩的语义特征，而传统图像输入需要数百个 patch token。

## 五、3.4 本章小结

本章把持久化知识分成两个尺度：面向个人的用户记忆，以及面向所有用户的共享知识库。

- **用户记忆**：遵循“读取相关记忆 → 后台提取候选 → 来源与策略核验 → 更新”的生命周期，并可在 Simple Notes、JSON Cards 或可执行状态之间按需求取舍。
- **就全书的结构而言**：本章建的是第一章发现循环中的**提案段**：把一条证据变成一次最小、可审查、可回滚的修改，而不负责判断系统整体是否变好。
- **知识库主流水线**：“分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成”，用 recall@k 等指标验收。
- **RAPTOR、GraphRAG、OpenViking、上下文感知检索和智能体化 RAG** 分别改变知识的组织、分块或检索控制方式；实践中可以让结构化概览常驻上下文，把原始细节按需召回。
- **写入不能跳过来源、时间、冲突和隐私检查**。增量更新吸收新证据，定期整理则回到原始数据去重、合并并重建索引，待验证的 diff 通过独立审核后才发布。
- **上一章管理单次任务内的上下文，本章管理跨任务的陈述性知识**；第九章会把同一基础设施用于“在什么条件下应该怎样做”的行为经验。

**双层记忆架构：**
- 用 **Advanced JSON Cards** 把少量关键事实结构化后常驻上下文，提供随时可见的“概览”。
- 用 **上下文感知检索** 按需从海量原始对话中取回“细节”。
- 回看三层次评估框架：基础回忆靠可靠的存取即可满足，多会话检索靠检索技术补齐，而主动服务之所以最难，正是因为它要求系统同时握有“全局概览”和“精确细节”两种视角。

## 六、思考题深度解析

### 1. ★★ 同一用户在不同会话中提供矛盾信息，记忆系统应如何处理？

**第一性原理：** 矛盾不是“错误”，而是“不同时间/条件下的不同事实”。处理矛盾的核心是**保留来源、时间、上下文，让检索时决策**，而不是写入时粗暴覆盖。

**处理策略：**
- **保留而非覆盖**：Mem0 v3 的做法——只追加，不删除。将“住在北京”和“搬到上海”作为两条带时间戳的事实并存。
- **时间戳与来源**：每条记忆记录获取时间、会话 ID、原始对话引用。
- **冲突检测与标注**：定期整理时，识别矛盾对，标注“待确认”或“在不同时间成立”。
- **检索时决策**：查询时用时间排序、语义相关性、实体匹配综合排序，选择当前最可能有效的事实。
- **主动澄清**：当矛盾无法自动解决，且影响关键决策时，Agent 应主动询问用户。

**费曼式类比：** 你的日记本里同时写着“今天住在北京”和“下个月搬到上海”。你不会撕掉任何一页，而是翻到最新日期的那一页。

### 2. ★★ 上下文感知检索可能放大原始文档的错误。如何引入“信息质量”信号？

**第一性原理：** 检索不仅要“相关”，还要“可信”。需要在索引和检索阶段附加质量元数据。

**具体方案：**
- **来源可信度**：为每个文档/分块标注来源等级（官方文件 > 学术论文 > 新闻 > 个人博客）。
- **一致性检查**：在索引前，用 LLM 检查文档内部是否存在矛盾；若存在，标记为“低一致性”并降低权重。
- **交叉验证**：对同一事实，如果多个独立来源一致，提升可信度；如果只有单一来源，标注“未验证”。
- **时效性**：标注生效/失效时间，检索时过滤过期内容。
- **用户反馈**：记录用户对检索结果的点击、采纳、纠错，动态调整来源权重。
- **检索时融合**：将质量分作为排序特征之一，与语义相似度、关键词匹配加权。

**费曼式类比：** 你在图书馆找资料，不仅看内容是否相关，还要看出版社是否权威、出版时间是否最新、是否有其他书佐证。

### 3. ★★ 图表转文本丢失空间关系。举例并设计保留方案。

**具体例子：** 一个流程图，节点 A → B → C，其中 B 是判断节点，有两个分支“是”和“否”。纯文本描述：“A 后是 B，B 后是 C。”丢失了“B 是判断节点，有两条分支”的空间结构。

**保留方案：**
- **方案一：保留图像**。对于布局敏感的图表，直接返回图像给多模态模型，而不是文本提取。
- **方案二：结构化描述**。用 Mermaid、Graphviz 等格式生成图表的代码表示，保留节点和边的关系。例如：`A --> B; B -->|是| C; B -->|否| D`。
- **方案三：混合模式**。文本描述 + 图像 + 结构化代码，三者一起索引和检索。
- **方案四：多模态嵌入**。直接将图表图像编码为嵌入，与文本嵌入一起存入向量库，支持跨模态检索。

**费曼式类比：** 描述一张地图，不能只说“北京在上海北边”，而要保留经纬度坐标或地图图片。

### 4. ★★★ “苦涩的教训”：本章的知识系统是否也是手工设计？会被全量输入替代吗？

**第一性原理：** 手工设计的特征（分块策略、索引结构、检索管道）确实属于“人类先验”。但**苦涩的教训说的是长期趋势，不是短期现实**。

**分析：**
- **会被部分替代**：随着模型上下文窗口扩大、检索能力内化，一些简单的分块和检索策略会被模型内部化。
- **但不会完全替代**：
  1. **动态事实**：知识库需要更新、引用、删除，模型参数无法做到。
  2. **可溯源**：检索结果需要提供原始出处，模型生成无法保证。
  3. **成本与效率**：全量输入百万 token 的成本远高于检索 top-k。
  4. **私有数据**：企业内部文档无法全部塞进模型参数。
- **结论**：手工设计的检索系统是**当前工程约束下的最优解**。模型能力增强后，部分环节会被简化，但外部知识管理的基础设施仍将长期存在。

**费曼式类比：** 计算器出现后，我们不再手算乘法，但会计系统（账本、审计、凭证）依然需要，因为要追溯、要合规。

### 5. ★★★ 领域知识库还重要吗？基座模型会包含所有信息吗？

**第一性原理：** 基座模型的知识是**静态的、有截止日期的、无法引用来源的**。领域知识库解决的是**动态性、私有性、可溯源性**。

**未来判断：**
- **通用知识**：基座模型会越来越强，许多通用领域知识会被内化。
- **动态事实**：永远需要外部知识库（新闻、政策、价格）。
- **私有知识**：企业内部文档、用户个人记忆，基座模型无法获取。
- **可溯源需求**：法律、医疗等高风险领域，必须提供原始出处。
- **结论**：领域知识库不会消失，但形态会变——从“检索文本块”转向“检索结构化事实+原始证据”，并与模型参数形成互补。

**费曼式类比：** 你读完了所有医学教科书（基座模型），但你还是需要查最新的临床指南（知识库），因为医学在进步。

### 6. ★ RAPTOR 和 GraphRAG 分别擅长什么类型的查询？

| 索引类型 | 擅长查询 | 例子 |
|---|---|---|
| **RAPTOR**（树状层次） | 从宏观到微观、多层次导航 | “请解释 SSE 指令集”：先定位“SIMD 指令集”宏观概念，再下钻到具体 SSE 指令 |
| **GraphRAG**（实体关系图） | 多跳关系、实体消歧、关系推理 | “我的医生所在医院的地址”：用户→医生→医院→地址；或“A 和 B 之间是什么关系” |

**结论：** RAPTOR 适合“从概念逐步钻进细节”，GraphRAG 适合“谁和谁有关，A 如何影响 B”。生产场景可组合使用。

### 7. ★★ 文件系统范式相比向量数据库 RAG 的优势场景？

**优势场景：**
- **需要人工阅读和编辑**：Markdown 纯文本，用户可以直接打开、修改、Git 版本控制。
- **Agent 自主写知识**：Agent 拥有 write_file 能力，可在工作分支上记录，再通过 PR 审核合入。
- **渐进式披露**：L0/L1/L2 三层摘要，按需加载，Token 消耗低。
- **结构化导航**：目录树 + 链接，可像 Wikipedia 一样跳转。
- **混合检索**：文件系统可结合全文检索、向量检索、链接导航。

**劣势场景：**
- 海量非结构化文档、需要高召回率的语义检索时，向量数据库更高效。
- 需要复杂相似度计算时，文件系统需要额外索引。

**结论：** 文件系统范式适合**知识规模中等、需要人机协作、强调可读可编辑**的场景；向量数据库适合**大规模、高吞吐、纯语义检索**的场景。两者可混合使用。

### 8. ★★★ 数据驱动的知识提取能达到人类专家手工编写规则的质量吗？

**第一性原理：** 人类专家规则是**演绎的、基于法理和经验的**；数据驱动规则是**归纳的、基于统计模式的**。

**优势：**
- 能发现人类忽略的隐性模式（如某些因素组合对判决的影响）。
- 大规模、可复现、可更新。
- 能处理高维、非线性的关系。

**局限：**
- 数据偏差会被放大（如历史判决中的歧视）。
- 缺乏因果解释，只是相关关系。
- 边界情况、新情况可能覆盖不足。
- 法律解释的模糊性无法完全量化。

**结论：** 数据驱动可以**辅助**人类专家，发现盲点，但不能完全替代人类判断。最佳实践是：数据驱动生成规则草案 → 人类专家审核、修正、补充法理依据 → 形成可执行的规则卡。

**费曼式类比：** AI 可以从海量病例中总结“某种症状组合更可能指向某病”，但最终诊断仍需医生结合临床经验和伦理判断。

### 9. ★★★ 设计 Markdown 用户记忆库的增量更新与定期整理流程，并分析 Reviewer 与 Proposer 同模型同片段的错误。

**增量更新流程（PR 模式）：**
1. Proposer 从新对话中提取候选事实，搜索相关已有条目，提出最小 diff。
2. Reviewer 独立审核 diff，对照原始对话证据，检查是否遗漏限定条件、是否冲突。
3. 双方迭代至收敛，CI 检查格式、链接、元数据。
4. 合入后重建索引。

**定期整理流程：**
1. 全量扫描，识别重复、过期、碎片化条目。
2. 回到原始对话核查，修正误读。
3. 解决冲突，标注适用场景。
4. 提交重组 diff，Reviewer 审核，回放检索用例验证。

**如果 Reviewer 与 Proposer 使用同一模型，且只能看到 Proposer 挑选的对话片段，可能合入的错误：**
- **模型独立性不足**：同模型有相同的偏见和盲点，可能同时忽略同一类错误。
- **证据覆盖不全**：Proposer 挑选的片段可能遗漏关键上下文，Reviewer 无法发现。
- **工具权限不足**：Reviewer 无法访问完整对话库和原始证据，无法交叉验证。

**改进方案：**
- **模型独立性**：Proposer 和 Reviewer 使用不同家族的模型（如 Claude vs GPT）。
- **证据覆盖**：Reviewer 应有权访问完整对话库、原始轨迹和工具输出，而不是只看 Proposer 挑选的片段。
- **工具权限**：Reviewer 应具备文件搜索、版本比较、测试执行等工具，能主动核查证据。
- **权限分离**：Proposer 只能写工作分支，Reviewer 只读证据并提交审核结果，合并流程独立。
- **最大迭代与人工兜底**：设置迭代上限，超出后转人工审核。

**费曼式类比：** 让同一个学生自己出题、自己批改，他很可能漏掉自己的错误。应该让另一个学生（不同背景）来批改，并且给他完整的参考书和原始资料。

## 七、之前讨论的问答整合

| 之前问答                               | 核心结论                                                                                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **稠密 vs 稀疏嵌入区别**                   | 稠密：低维、稠密、实数向量，捕捉语义相似性；稀疏：高维、大部分为 0，捕捉精确关键词匹配。正式表示：稠密 $$\mathbf{v} \in \mathbb{R}^d，稀疏 \mathbf{v} \in \mathbb{R}^{\|V\|}$$。两者互补，混合检索 + 重排序是生产级 RAG 标配 |
| **Contextual Retrieval 在索引期还是检索期** | 索引期。为每个文本块生成前缀摘要，与原文拼接后再索引。不是用户检索时对查询进行增强                                                                                                            |
| **智能体 RAG vs 传统 RAG**              | 传统 RAG 是被动的、一次性的；智能体 RAG 是 Agent 主动的、分解的、多次不断交互的                                                                                                     |
| **法律模糊性如何减少幻觉**                    | 五层防御：结构化知识建模（GraphRAG+规则卡）、Agentic RAG（多轮迭代）、神经符号结合（规则引擎）、RLVP（惩罚错误路径）、HITL（人类确认）                                                                    |
| **多模态嵌入为什么只占 1 个 token**           | 因为它是压缩后的连续向量，通过投影层映射到模型隐藏空间的一个槽位。1 个 token 承载了高度压缩的语义特征，而传统图像输入需要数百个 patch token                                                                     |
| **层次化、图化、LLM Wiki 三种记忆组织方式**       | 层次化提供概览但会累积局部偏差，图化支撑关系推理但丢失语义细节，LLM Wiki 实现动态关联但必须用确定性验证层兜底幻觉。三者分层互补，确定性验证层是共同信任地基                                                                   |

## 九、费曼式总结

- **用户记忆**：记住“你是谁”，让 Agent 成为懂你的助手。
- **知识库**：记住“世界是什么”，让 Agent 成为领域专家。
- **三层次评估**：基础回忆 → 多会话检索 → 主动服务。
- **四种存储格式**：Simple Notes（原子事实）、Enhanced Notes（段落叙事）、JSON Cards（结构化键值）、Advanced JSON Cards（消歧+关系）。
- **认知类型**：情景记忆（事件）、语义记忆（知识）、程序记忆（流程）。
- **RAG 核心**：分块 → 检索 → 增强 → 生成。
- **混合检索**：稠密（语义）+ 稀疏（关键词）+ 重排序。
- **结构化索引**：RAPTOR（树）、GraphRAG（图）。
- **文件系统范式**：可读可编辑、渐进披露，适合人机协作。
- **智能体化 RAG**：Agent 主导检索循环，从“被动管道”到“主动探索者”。
- **上下文感知检索**：索引期补前缀，修补分块缺陷。
- **双层架构**：结构化卡片常驻 + 上下文感知检索按需取细节。
- **知识更新**：PR 模式，异源审核，证据全覆盖，权限分离。

**一句话：**

> **用户记忆让 Agent 懂你，知识库让 Agent 专业。**
> **评估记忆能力用三层次：基础回忆、多会话检索、主动服务。**
> **存储格式从 Simple Notes 到 Advanced JSON Cards，逐步增强表达力。**
> **RAG 是知识获取管道：分块、稠密/稀疏检索、混合检索、重排序。**
> **结构化索引（RAPTOR/GraphRAG）和智能体化 RAG 让知识组织更智能。**
> **双层记忆架构：关键事实常驻上下文，原始细节按需检索。**
> **知识更新用 PR 模式，异源审核，证据全覆盖，权限分离。**
> **本章建的是发现循环中的提案段；第九章将把同一基础设施用于行为经验的持续进化。**
