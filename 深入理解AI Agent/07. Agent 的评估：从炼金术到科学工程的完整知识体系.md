
## 一、 第一性原理：为什么需要评估？

### 1.1 核心命题
**构建完成 ≠ 构建正确。** 只有能够稳定测量结果，后续的模型训练和系统进化才有可靠方向。

### 1.2 核心痛点
*   **设计选择无标准答案**：用什么模型？调哪些工具？知识库怎么建？提示词怎么组织？Harness加什么约束？
*   **直觉不可靠**：不建立可重复的评估体系，Agent的迭代方向就只能靠“感觉”和“猜测”。

### 1.3 核心价值
*   通过**对比实验**（改变一个变量，观察效果变化）和**消融实验**（逐一关闭组件，判断真实贡献），区分真正的能力提升与表面的波动。
*   把Agent工程从经验驱动的**“炼金术”**转向数据驱动的**“科学工程”**。

### 1.4 关键认识：评估对象是 Model + Harness 组合体
*   **模型替换实验**：固定Harness，只换模型。换强模型分数不涨 → 瓶颈在Harness；换弱模型分数大跌 → 瓶颈在模型。
*   **消融实验**：关闭Harness某个组件。定位Harness内部哪个部件重要。
*   两者互补，区分“模型能力不足”与“Harness设计缺陷”。

## 二、 成功的定义：Pass@k 与 Pass^k（指标口径）

### 2.1 Pass@k（能力上限）
*   **定义**：同一任务运行k次，只要至少有一次通过，任务就算通过。公式：\(1 - (1-p)^k\)。
*   **适用**：技术奇观、科研发现、漏洞挖掘、开放式创作。
*   **案例**：Manus、OpenClaw早期成功率不高，但Pass@k高，展现技术上限。

### 2.2 Pass^k（业务可靠性）
*   **定义**：同一任务连续运行k次，要求每一次都通过。公式：\(p^k\)。
*   **适用**：支付、退款、权限变更、生产部署。
*   **案例**：单次成功率p=0.6，Pass@5≈99.0%，但Pass^5≈7.8%。

### 2.3 评估报告的原则
*   必须写清k次尝试的口径（独立采样 vs 连续任务）。
*   对产生副作用的操作，不能“重试直到成功”，必须在沙盒或可回滚环境中采样，并把每一次失败记入可靠性指标。

## 三、 任务从何而来（评估数据集设计）

### 3.1 基准设计的横向对照
| 基准 | 被测能力 | 任务来源 | 验证器 |
| :--- | :--- | :--- | :--- |
| **τ²-bench** | 客服人机交互 | 人工编写+组合生成 | 四层检查聚合为二元 |
| **SWE-bench Verified** | 软件开发 | GitHub真实issue | FAIL_TO_PASS / PASS_TO_PASS |
| **AndroidWorld** | Android GUI操作 | 参数化模板实例化 | 最终UI状态断言 |
| **OSWorld** | Linux桌面GUI | 预置中间状态启动 | 134个独立评估函数 |
| **Terminal-Bench** | Linux终端coding | 人工编写 | 文件系统检查+真实执行 |
| **GAIA** | 通用AI助手 | 人工编写+专有附件 | 精确字符串匹配 |

### 3.2 验证器的深度
*   **SWE-bench Verified**：双重验证（修复前失败/修复后通过 = 问题解决；修复前后均通过 = 未引入新缺陷）。
*   **OSWorld**：检查文件系统、进程状态、网络连接，连接数据库核实SQL。
*   **Terminal-Bench**：构建Linux内核，Agent无法伪造输出。

### 3.3 难度划分（诊断价值）
*   **GAIA 三级难度**：Level 1（基础工具）→ Level 2（多步规划）→ Level 3（长序列思考）。
*   **τ²-bench 陷阱任务**：用户声称“客服已批准取消”，检验Agent在压力下能否维持正确判断。

### 3.4 数据泄漏防范
*   **GAIA**：组合多个信息源 + 专有附件（互联网不存在的PDF、音频）。
*   **AndroidWorld**：参数化模板，每次随机生成参数值，回放固定操作序列失效。
*   **Terminal-Bench**：嵌入金丝雀标识符（canary GUID），检测泄漏。

### 3.5 质量控制与长期维护
*   **r-bench → r²-bench 五处改进**：拆分指令、精确成功条件、丰富模拟器行为、引入双控环境、动态生成任务。
*   **SWE-bench Verified**：淘汰71%的原始任务（2294→500），高信噪比，降低成本。
*   **OSWorld**：15个月暴露300余问题，进行系统性修复。

### 3.6 评估集的三个来源
1.  **公开基准**：粗筛模型与借鉴设计手法。
2.  **自建业务集**：覆盖真实任务分布，用于模型选型。
3.  **生产轨迹回流**：线上真实失败案例，经归因后沉淀为回归用例。

## 四、 验证方式：从确定性验证到 LLM-as-a-Judge

### 4.1 评估环境五要素
**数据集**、**环境状态**（可重置）、**工具接口**（原子操作）、**评分标准**（Rubric）、**执行协议**（终止条件）。

### 4.2 工具调用型 vs 人机交互型
*   **工具调用型（Verifiers）**：无对话对象，验证行动正确性。四类环境：SingleTurnEnv、ToolEnv、StatefulToolEnv、SandboxEnv。
*   **人机交互型（τ-bench）**：有用户模拟器，验证沟通合理性。双重验证（DB状态 + 对话内容）。

### 4.3 LLM-as-a-Judge
*   **为什么需要**：开放式任务无标准答案，人工评估成本高。
*   **局限性**：长度偏差、位置偏差、同源模型偏见。
*   **防范手段**：Rubric显式惩罚冗长、配对比较控制长度、定期审计长度与分数相关性。
*   **多源异构评判**：不同模型家族分别评判，偏见正交，防止Agent“欺骗”所有评判者。

### 4.4 Rubric 四准则
1.  **基于专家指导**：反映领域知识。
2.  **全面覆盖**：正面标准 + 陷阱（Pitfall）。
3.  **按重要性加权**：必要项、重要项、可选项、陷阱项，支持一票否决。
4.  **评价标准自包含**：独立可操作，避免抽象标准。

### 4.5 失败归因（核心枢纽）
*   **定义**：标出主要错误类别、首次出现不可接受行为的步骤、工具调用或模型输出，附可复核证据。
*   **原则**：定位**首个导致任务偏离的错误**，而非最后一个报错。
*   **三类信号**：用户纠正、点踩、事后审计。
*   **结构化记录**：JSON/YAML，区分根因与后果，给出置信度。
*   **策略**：规则先筛、LLM再定位，更便宜更准。
*   **三类典型错误**：“做对了但说错了”（观察通道缺失）、作用域敏感文档格式错误、精确复制错误（逐层定位）。

### 4.6 回归任务
*   **端到端回归**：从初始状态出发，验证完整工作流不退化。
*   **轨迹前缀回归**：截取首个错误之前的状态，验证决策边界。答案定义为“可接受动作集合”。
*   **实验7-7结论**：改变上下文表示方式（JSON/Markdown/Python）并不会自动修复应用策略。

### 4.7 配对比较与模型排名
*   **Elo评分**：国际象棋排名系统。\(E_A = 1/(1+10^{(R_B-R_A)/400})\)。
*   **Bradley-Terry模型**：Elo的统计基础。极大似然估计（MLE），从比赛结果反推实力分数。
*   **MLE与BT的关系**：BT是概率模型，MLE是参数估计方法。MLE用于拟合BT模型。
*   **位置偏差缓解**：交换顺序各评一次，只有两次判决一致时才计入。

## 五、 结果转化为决策（评估驱动的模型选型与统计显著性）

### 5.1 选型的关键维度
*   **吞吐量与延迟**：Prefill（决定TTFT） vs Decode（决定出字速度）。p95尾部延迟比平均值更能反映用户体验。
*   **成本**：计算“每任务平均成本”（单次成本/成功率），而非单次定价。
*   **性能**：Pass@1、Pass@k、Pass^k。
*   **速率限制与可靠性**：RPM/TPM，鲁棒性。
*   **预算-能力曲线**：短预算领先不能外推成长时间运行能力。
*   **多模型协同**：轻量模型处理简单，强大模型处理复杂。

### 5.2 模型的行为策略（行动阈值）
*   **来源**：Harness系统提示词 + 模型行为策略（后训练塑造）。
*   **实验7-9**：GPT-5.6-sol先读4.67个文件再改；Claude Sonnet 5先读3.56个文件就改。两者都100%通过。
*   **启示**：选型不仅看“能不能做”，还要看“默认怎么做”。

### 5.3 成本分析
*   **三个层次**：模型推理成本（上下文累积、思考token）、工具调用成本、基础设施成本。
*   **上下文累积效应**：总输入token = $$T \times N(N+1)/2$$。
*   **优化策略**：复用KV Cache、压缩上下文、分层选择模型、异步批处理、成本监控。
*   **注意**：节省比例不能直接相加（稳定前缀+压缩历史只节省30%）。

### 5.4 评估结果的统计显著性
*   **标准误**：$$SE(p) \approx \sqrt{p(1-p)/n}$$。
*   **95%置信区间**：$$p \pm 1.96 \times SE$$。
*   **为什么这样算**：大数定律（保证收敛） + 中心极限定理（保证分布形态为正态）。
*   **二项分布方差**：\(np(1-p)\)。因为它是n个独立伯努利变量之和，每个伯努利方差为\(p(1-p)\)，独立变量方差可加。
*   **配对分析**：McNemar检验，逐题记录谁胜出，比直接相减独立成功率更可靠。
*   **多重比较**：收紧显著性阈值，或对正向结果做独立复跑。
*   **实务标准**：分差超过噪声、配对分析成立、能够复现。

### 5.5 评估驱动的持续迭代
*   **问题不是“哪个更强”**，而是“在我的特定任务上，新模型是否更好？好多少？切换成本是什么？”
*   **差异化策略**：简单任务迁移新模型，复杂任务保留原模型。

## 六、 可观测性与内部评估基础设施（生产级评估体系）

### 6.1 Agent的可观测性
*   **Trace与Span树**：一次任务对应一条trace，每个LLM调用、工具调用都是span，父子关系构成执行树。
*   **标准化协议**：OpenTelemetry（通用）+ OpenInference（LLM特有）。
*   **代表性平台**：LangSmith（整合可观测性、评估、优化闭环）。
*   **数据去向**：回流并转化为评估资产（筛选失败案例→脱敏→沉淀为回归测试）。

### 6.2 从Benchmark报告到系统改进（AndroidWorld案例）
*   **原则**：先检查评测系统本身，再动Agent。
*   **五步法**：观察（诊断报告）→ 假设（三层改进框架）→ 实验（分阶段验证，每轮只改一个变量）→ 决策（成本-收益权衡）→ 迭代（新一轮循环）。
*   **关键结论**：一轮证据只支持与它规模相称的下一步；完整复测后才能部署。

### 6.3 内部评估基础设施（五大组件）
1.  **消融基础设施**：总开关禁用多个特性，创造“裸模型”基线。启动路径极早期注入。定期运行发现“特性债务”。
2.  **AB测试方法论**：多臂而非二元、区分机制指标与目标指标、设置护栏指标、记录基线统计。
3.  **双层特性开关系统**：编译时开关（物理移除代码）、运行时开关（服务端下发，本地缓存）。曝光事件每会话最多记录一次。
4.  **提示词敏感性评估**：确定性渲染、版本化快照、纳入CI体系运行回归测试。
5.  **隐私感知分析**：类型系统强制，将隐私约束从文档规范变成编译时检查。


##  七、 仿真环境：从评估到后训练的桥梁

### 7.1 评估环境 vs 仿真环境
*   **核心区别**：交互频率高得多（数百万次 vs 数千次）、需要随机化、必须提供即时反馈。
*   **桥梁两端**：评估侧的验证器 → 训练侧的奖励函数（RLVR）。
*   **训练新要求**：可靠的reset语义、远高于评估的吞吐。

### 7.2 数字环境与具身环境
*   **数字环境（AWorld）**：26个MCP服务器，126个工具函数，14.6倍加速。
*   **具身环境（RoboTwin2 + OpenVLA）**：多相机 + 14维关节状态，VLA模型，物理引擎，动作分块。
*   **隔离机制**：VM/容器隔离、住宅代理、HITL认证、共享文件系统。

### 7.3 保真度权衡与领域随机化
*   **高保真 vs 低保真**：高保真迁移好但计算贵。
*   **领域随机化**：物理参数、视觉外观、传感器噪声。适度随机化提升泛化，过度随机化任务太难。
*   **数字环境中的sim-to-real**：界面渲染、响应时间，引入延迟和失败随机化。

## 八、 深度思考与有限预算下的最优策略

### 8.1 九大思考题核心结论
1.  **LLM-as-a-Judge盲区**：多源异构评判 + 长度控制 + 人工校准。
2.  **数据泄漏**：没有终局，用动态生成 + 专有附件 + 形式化验证。
3.  **主观维度Rubric**：拆解为具体行为 + 示例 + 边界案例。
4.  **模拟用户质量**：真实数据校准 + 人工抽检 + 对抗测试。
5.  **非传递偏好**：多维度分别排名 + 循环检测。
6.  **Pass@k vs Pass^k**：看失败成本、重试成本、副作用。
7.  **有限预算**：分层抽样 + 配对分析 + 提前停止 + 漏斗式评估。
8.  **自动裁剪UI节点**：删除无语义节点 + 保留关键节点 + 验证。
9.  **渐进式信息透露**：更真实，但需校准模拟用户。

### 8.2 有限预算下最大化评估信息量（漏斗式评估）
*   **宏观粗筛**：低成本跑任务，获取基础统计量。
*   **智能过滤**：规则先筛（交叉核对完成声明、检查测试断言、检查API改动），筛出5-10条“嫌疑trace”。
*   **深度trace分析**：对少量trace逐帧解剖，定位首个错误，区分主因与后果。
*   **转化为资产**：截取前缀，定义可接受动作集合，形成轨迹前缀回归任务。
*   **核心结论**：Trace是答案的起点，不是终点。真正的终点，是从trace中提炼出可复用的知识。

## 九、 全章核心原则总结（一句话体系）

> **评估对象是 Model + Harness 的组合体。**
> **Pass@k 衡量能力上限，Pass^k 衡量业务可靠性。**
> **验证方式从确定性验证器到配对比较，LLM 评判只用于确实无法机械判定的维度。**
> **失败归因定位首个错误，轨迹前缀回归直接检查决策边界。**
> **评估不是偶尔做一次的考试，而是从真实问题案例中持续生成回归任务和边界任务的验证系统。**
> **外部评估告诉你“Agent 有多好”，内部评估基础设施告诉你“哪项改动让它变好了”。**
> **核心方法论：观察 → 假设 → 实验 → 验证 → 新认识 → 新假设，使 Agent 工程从经验驱动的“炼金术”转向数据驱动的科学工程。**
> **评估体系不仅服务于当前系统的优化，也为后续两章提供关键基础：第八章把评估环境和数据转化为模型后训练的输入；第九章则把生产轨迹的多维评价转化为知识、指令、程序的更新。**


思考题
1. ★★ 在异步 Agent 架构中，事件队列的优先级策略需要在设计时确定。但如果优先级判断本身需要语义
理解（比如判断一条新消息是否比当前任务更紧急），这个判断应该由谁来做——规则引擎还是另一个
LLM 调用？各有什么代价？
2. ★★ 在队列式事件处理中，模型倾向于只关注最后一个事件，本章通过 Agent 状态栏标记和汇总来缓
解。但如果队列中积压了 20 个事件（10 个工具结果 + 5 条用户消息 + 5 个系统提醒），你会如何组织
这些事件的呈现顺序和格式，使模型不遗漏关键信息？
3. ★★★ Agent 代表用户与外部世界交互时，本质上面临一个身份选择：是用独立的虚拟身份（专属邮箱
和电话号码）以第三方身份行动，还是直接以用户本人的身份操作其个人账号？前者可以在后台自主操
作，但第三方可能不信任一个非真人的身份；后者拥有更完整的上下文和权限，但引入了信任授权和安
全边界的问题。你认为在什么场景下应该选择哪种模式？
4. ★★ 语音 Agent 的端到端模型将 ASR-LLM-TTS 合并为单一模型，降低了延迟却失去了模块化。如果
端到端模型在某个环节（如语音识别）出错，调试和修复比串行管道困难得多。你会如何设计端到端语
音 Agent 的可观测性（observability）系统？
5. ★ Step-Audio R1 通过 MPS 双脑架构实现“边想边说”。但人类在“边想边说”时经常会说出未经深思熟
虑的话、自我纠正或使用填充词。Agent 的“边想边说”应该模仿人类的这些特征吗？
6. ★★ SoM（Set-of-Mark）及其结构化变体（DOM 元素索引）将 Computer Use 的视觉定位从开放坐标
预测转为封闭 ID 选择，但都需要先检测和标注界面元素——无论靠分割模型还是靠 DOM。如果界面
包含非标准控件或动态变化的元素，标注就可能不完整或不准确。这种情况下应该回退到坐标预测吗？
7. ★★ XLeRobot 等几百美元级机器人平台让遥操作数据收集变得廉价。但遥操作数据的质量高度依赖操
