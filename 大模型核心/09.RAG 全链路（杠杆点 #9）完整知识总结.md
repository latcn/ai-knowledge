## 0. 它在十讲依赖图中的位置

依赖图：

```
分词 → Embedding → Attention → 多头 → Transformer Block
                                        ↓
```

读图规则只有一条：

> 箭头左边不懂，右边学到的就是名词，不是知识。

RAG 在依赖图中的位置：

> LoRA 之后，Agent 之前。

它回答的问题是：

> 模型不知道的事，怎么让它知道？

RAG 是**外部知识注入的第一站**。  
它不改变模型权重，而是在推理时把外部知识塞进上下文。  
没有 RAG，模型只能靠参数化记忆，事实性差、更新慢、不可溯源。  
有了 RAG，模型可以访问最新、可更新、可溯源的知识。

## 2. 第一性原理：RAG 为什么存在

### 2.1 参数化记忆的局限

LLM 的知识存储在权重中，这带来四个问题：

1. **知识截止**：训练数据有时间截止，之后的事不知道。
2. **不可更新**：想更新知识，需要重新训练或微调。
3. **不可溯源**：模型说不出答案来自哪里。
4. **幻觉**：不知道时也可能编造。

### 2.2 RAG 的核心思想

RAG 的做法：

> 在推理时，从外部知识库检索相关信息，塞进上下文，让模型基于检索内容生成。

数学形式：

$$
p(y \mid x) = \sum_{z \in \text{Retrieve}(x)} p(z \mid x) \cdot p(y \mid x, z)
$$

其中：

- $$x$$：用户问题
- $$z$$：检索到的文档片段
- $$y$$：生成答案

### 2.3 RAG vs 微调

| 维度 | RAG | 微调 |
|---|---|---|
| 知识更新 | 实时，改数据库即可 | 需要重新训练 |
| 可溯源 | 可以给出出处 | 不可溯源 |
| 行为塑造 | 不改变模型行为 | 可以改变行为 |
| 成本 | 推理时增加检索开销 | 训练时一次性成本 |
| 适用场景 | 事实性、时效性知识 | 行为、格式、风格 |

一句话：

> RAG 补充知识，微调塑造行为。  
> 两者常组合，不是互斥选项。

## 3. RAG 全链路主干拆解

完整链路：

```
chunk → embed → retrieve → rerank → compose → generate
```

### 3.1 Chunk（切块）

**做什么**：把长文档切成小块。

**为什么**：

- 检索粒度太粗，噪声大。
- 检索粒度太细，语义不完整。
- 需要平衡召回率和精确率。

**常见策略**：

- 固定长度切块
- 按段落切块
- 按语义切块
- 重叠切块

**难点**：

> 切块切断语义单元，检索再准也没用。

例如：把一个完整的定义切成两半，检索到一半也没用。

### 3.2 Embed（嵌入）

**做什么**：把文本块编码成向量。

**为什么**：

- 向量空间中可以计算语义相似度。
- 支持快速近似最近邻检索。

**常见模型**：

- 双塔模型（如 Sentence-BERT）
- 对比学习训练的嵌入模型

**难点**：

> embedding 对否定、数字、专有名词不敏感。

例如：

- “猫不是狗”和“猫是狗”可能嵌入很接近。
- “2023 年”和“2024 年”可能嵌入很接近。
- 专有名词可能被嵌入模型忽略。

### 3.3 Retrieve（召回）

**做什么**：从向量库中找出与问题最相关的 top-k 文档。

**为什么**：

- 双塔模型速度快，适合大规模召回。
- 用近似最近邻（ANN）算法加速。

**常见方法**：

- 余弦相似度
- 内积相似度
- HNSW、IVF 等 ANN 索引

**难点**：

> 召回正确但排序靠后。

例如：正确文档在 top-100 中，但不在 top-10 中，直接被截断。

### 3.4 Rerank（重排）

**做什么**：对召回的文档重新排序，提升精确率。

**为什么**：

- 双塔模型快但精度有限。
- 交叉编码器精度高但慢。
- 先用双塔召回，再用交叉编码器重排。

**常见方法**：

- Cross-Encoder
- ColBERT
- LLM-based reranker

**难点**：

> 重排模型本身也可能出错，需要选择合适的模型和阈值。

### 3.5 Compose（上下文组织）

**做什么**：把检索到的文档组织成上下文。

**为什么**：

- 上下文长度有限。
- 不同位置的文档对模型的影响不同。
- 需要处理冲突信息。

**常见策略**：

- 按相关性排序
- 按时间排序
- 去重
- 压缩

**难点**：

> 关键信息放中间会“迷失在中间”。

研究表明，模型对上下文开头和结尾的信息更敏感，中间的信息容易被忽略。

### 3.6 Generate（生成）

**做什么**：基于上下文生成答案。

**为什么**：

- 模型需要综合检索内容生成回答。
- 需要引用出处。

**难点**：

> 模型无视检索内容，凭参数知识编答案。

这是 RAG 最危险的失败模式：检索到了正确内容，但模型不采信，仍然凭记忆回答。

## 4. 检索前增强手段（Pre-Retrieval）

检索前增强可以分成四层：

```
用户问题
   ↓
【查询理解层】查询改写、扩展、分解、路由
   ↓
【索引增强层】混合索引、元数据、摘要索引、父子索引
   ↓
【检索策略层】稀疏+稠密混合、多路召回、迭代检索
   ↓
【重排前处理层】去重、压缩、过滤
   ↓
召回结果
```

### 4.1 查询理解层（Query Understanding）

#### 4.1.1 查询改写（Query Rewriting）

**问题**：用户问题口语化、有指代、有歧义，直接检索效果差。

**做法**：用 LLM 把用户问题改写成更适合检索的形式。

**例子**：

- 原始问题：“它多少钱？”
- 改写后：“iPhone 15 Pro Max 256GB 的价格是多少？”

**常见方法**：

- **指代消解**：把“它”“这个”替换成具体实体。
- **口语转书面**：把口语表达转成正式查询。
- **关键词提取**：从问题中提取核心关键词。

#### 4.1.2 查询扩展（Query Expansion）

**问题**：用户问题用词和文档用词不一致，召回不全。

**做法**：给查询添加同义词、相关词、上下位词。

**例子**：

- 原始问题：“如何预防感冒？”
- 扩展后：“如何预防感冒 流感 上呼吸道感染 预防措施 免疫力”

**常见方法**：

- **同义词词典**：基于领域词典扩展。
- **LLM 扩展**：用 LLM 生成相关查询。
- **伪相关反馈**：用第一次检索的结果扩展查询。

#### 4.1.3 查询分解（Query Decomposition）

**问题**：复杂问题包含多个子问题，单次检索无法覆盖。

**做法**：把复杂问题拆成多个子问题，分别检索，再合并。

**例子**：

- 原始问题：“比较 Transformer 和 RNN 的优缺点。”
- 分解后：
  - “Transformer 的优点和缺点是什么？”
  - “RNN 的优点和缺点是什么？”

**常见方法**：

- **LLM 分解**：用 LLM 把问题拆成子问题。
- **链式分解**：多步推理，每步生成一个子查询。

#### 4.1.4 多查询生成（Multi-Query Generation）

**问题**：单一查询视角有限，可能漏掉相关文档。

**做法**：从不同角度生成多个查询，并行检索，合并结果。

**例子**：

- 原始问题：“如何学习深度学习？”
- 生成查询：
  - “深度学习入门路线”
  - “深度学习书籍推荐”
  - “深度学习课程推荐”

**常见方法**：

- **LLM 生成多查询**：让 LLM 生成 3-5 个不同角度的查询。
- **RRF 合并**：用 Reciprocal Rank Fusion 合并多路结果。

#### 4.1.5 HyDE（Hypothetical Document Embeddings）

**问题**：用户问题短，文档长，嵌入空间不匹配。

**做法**：先让 LLM 生成一个假设答案，再用假设答案的嵌入去检索。

**流程**：

1. 用户问题 → LLM 生成假设答案。
2. 假设答案 → 嵌入。
3. 用假设答案的嵌入检索真实文档。

**为什么有效**：

> 假设答案和真实文档在嵌入空间更接近，因为它们都是“答案”形式。

**例子**：

- 问题：“什么是 Attention？”
- 假设答案：“Attention 是一种加权平均机制，通过 Query、Key、Value 计算……”
- 用假设答案的嵌入检索，比用问题的嵌入检索更准。

#### 4.1.6 查询路由（Query Routing）

**问题**：不同问题需要查不同数据源。

**做法**：先判断问题类型，再路由到对应的索引或数据源。

**例子**：

- 事实性问题 → 查知识库。
- 操作性问题 → 查操作手册。
- 代码问题 → 查代码库。

**常见方法**：

- **分类器路由**：训练一个分类器判断问题类型。
- **LLM 路由**：用 LLM 判断应该查哪个数据源。

#### 4.1.7 Step-Back Prompting

**问题**：用户问得太具体，缺少背景，检索不到相关文档。

**做法**：先让 LLM 退一步，问一个更一般的问题，再检索。

**例子**：

- 原始问题：“为什么我的 PyTorch 训练 loss 不降？”
- 退一步：“PyTorch 训练 loss 不降的常见原因有哪些？”

**为什么有效**：

> 更一般的问题更容易检索到相关文档，然后再用具体问题筛选。

### 4.2 索引增强层（Index Augmentation）

#### 4.2.1 混合索引（Hybrid Index）

**问题**：纯向量检索对关键词不敏感，纯关键词检索对语义不敏感。

**做法**：同时建立稀疏索引（BM25）和稠密索引（向量），检索时合并。

**常见方法**：

- **BM25 + 向量**：两路召回，RRF 合并。
- **SPLADE**：学习稀疏表示，兼顾关键词和语义。

#### 4.2.2 元数据过滤（Metadata Filtering）

**问题**：向量检索可能召回不相关的时间、来源、类型的文档。

**做法**：给每个文档块加元数据，检索时先过滤。

**例子**：

- 时间过滤：只查 2024 年之后的文档。
- 来源过滤：只查官方文档。
- 类型过滤：只查 API 文档。

#### 4.2.3 摘要索引（Summary Index）

**问题**：长文档直接切块，块之间缺少全局信息。

**做法**：为每个文档生成摘要，检索时先查摘要，再查原文。

**流程**：

1. 文档 → 摘要。
2. 摘要 → 嵌入。
3. 检索摘要 → 找到相关文档 → 再查原文。

#### 4.2.4 父子索引（Parent-Child Index）

**问题**：小块检索精度高但语义不完整，大块语义完整但检索精度低。

**做法**：建立父子关系，小块用于检索，大块用于生成。

**流程**：

1. 大块 → 切成小块。
2. 小块 → 嵌入，用于检索。
3. 检索到小块 → 返回对应的大块 → 塞进上下文。

#### 4.2.5 多向量索引（Multi-Vector Index）

**问题**：单一嵌入无法表达文档的多个方面。

**做法**：为每个文档生成多个嵌入（如不同摘要、不同问题）。

**例子**：

- ColBERT：每个 token 一个嵌入，延迟交互。
- 多摘要：每个文档生成多个摘要，分别嵌入。

### 4.3 检索策略层（Retrieval Strategy）

#### 4.3.1 混合检索（Hybrid Retrieval）

**做法**：稀疏检索 + 稠密检索，合并结果。

**合并方法**：

- **RRF（Reciprocal Rank Fusion）**：
  $$
  \text{score}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}
  $$
- **加权求和**：给不同检索器不同权重。

#### 4.3.2 多路召回（Multi-Route Retrieval）

**做法**：用多个查询、多个索引、多个模型并行召回，合并结果。

**例子**：

- 查询 1：原始问题。
- 查询 2：改写后的问题。
- 查询 3：假设答案。
- 三路召回，RRF 合并。

#### 4.3.3 迭代检索（Iterative Retrieval）

**做法**：多轮检索，每轮基于上一轮结果优化查询。

**例子**：

- 第 1 轮：检索 → 得到初步结果。
- 第 2 轮：基于初步结果生成新查询 → 再检索。
- 重复直到收敛。

**常见方法**：

- **Self-RAG**：模型自己判断是否需要检索、检索结果是否相关。
- **IRCoT**：检索和思维链交替进行。

#### 4.3.4 自适应检索（Adaptive Retrieval）

**做法**：判断是否需要检索，避免不必要的检索。

**例子**：

- 简单问题 → 不检索，直接回答。
- 复杂问题 → 检索。
- 事实性问题 → 检索。
- 创意性问题 → 不检索。

**常见方法**：

- **分类器判断**：训练分类器判断是否需要检索。
- **LLM 判断**：用 LLM 判断是否需要检索。

### 4.4 重排前处理层（Pre-Rerank Processing）

#### 4.4.1 去重（Deduplication）

**问题**：多路召回可能返回重复文档。

**做法**：按文档 ID 或内容相似度去重。

#### 4.4.2 压缩（Compression）

**问题**：召回文档太长，上下文放不下。

**做法**：用 LLM 或抽取式方法压缩文档，只保留关键信息。

**常见方法**：

- **抽取式压缩**：只保留与问题相关的句子。
- **生成式压缩**：用 LLM 生成摘要。

#### 4.4.3 过滤（Filtering）

**问题**：召回文档可能不相关或低质量。

**做法**：用分类器或 LLM 过滤掉不相关文档。

### 4.5 完整检索前增强流程

```
用户问题
   ↓
查询改写（指代消解、口语转书面）
   ↓
查询扩展（同义词、相关词）
   ↓
查询分解（复杂问题拆子问题）
   ↓
多查询生成（不同角度）
   ↓
HyDE（生成假设答案）
   ↓
查询路由（选择数据源）
   ↓
混合检索（BM25 + 向量）
   ↓
多路召回（多查询并行）
   ↓
RRF 合并
   ↓
去重、压缩、过滤
   ↓
重排（Cross-Encoder）
   ↓
上下文组织
   ↓
生成
```

## 5. 五种具体失败模式

### 失败模式 1：切块切断语义

**表现**：检索到的块不完整，缺少关键信息。

**例子**：一个定义被切成两半，检索到前半句，后半句丢失。

**解决**：

- 重叠切块
- 按语义切块
- 按段落切块

### 失败模式 2：embedding 对否定/数字/专有名词不敏感

**表现**：语义相反的句子嵌入很接近。

**例子**：

- “猫不是狗” vs “猫是狗”
- “2023 年” vs “2024 年”
- “张三” vs “李四”

**解决**：

- 使用更好的嵌入模型
- 混合检索（关键词 + 向量）
- 加入元数据过滤

### 失败模式 3：召回正确但排序靠后

**表现**：正确文档在 top-100 中，但不在 top-10 中。

**例子**：召回率很高，但精确率低。

**解决**：

- 增加 top-k
- 使用重排模型
- 混合检索

### 失败模式 4：上下文太长导致“迷失在中间”

**表现**：模型忽略中间的关键信息。

**例子**：检索到 20 个文档，关键信息在第 10 个，模型没看到。

**解决**：

- 压缩上下文
- 把关键信息放在开头或结尾
- 使用重排模型精选 top-k

### 失败模式 5：模型无视检索内容，凭参数知识编答案

**表现**：检索到了正确内容，但模型不采信。

**例子**：检索到“2024 年诺贝尔奖得主是 X”，但模型回答“Y”。

**解决**：

- 提示词强调“必须基于检索内容回答”
- 使用引用机制
- 微调模型学会采信检索内容

## 6. 换条件

### 6.1 什么时候 RAG 不如微调？

- 需要稳定行为、格式、语气时。
- 需要领域推理风格时。
- 需要模型“内化”知识时。

例如：

- 让模型用特定格式写报告 → 微调。
- 让模型用特定语气回答 → 微调。
- 让模型学会领域推理 → 微调。

### 6.2 什么时候必须 RAG？

- 需要最新、可更新、可溯源的事实时。

例如：

- 最新新闻 → RAG。
- 公司内部文档 → RAG。
- 法律条文 → RAG。
- 医疗指南 → RAG。

### 6.3 如果只用 RAG 不用微调会怎样？

- 模型可能不遵循检索内容。
- 模型可能不会引用出处。
- 模型可能不会处理冲突信息。

### 6.4 如果只用微调不用 RAG 会怎样？

- 知识更新慢。
- 不可溯源。
- 幻觉仍然存在。
- 知识截止问题无法解决。

### 6.5 如果不用查询改写会怎样？

- 指代消解失败，检索不到相关文档。
- 口语化问题检索效果差。

### 6.6 如果不用查询扩展会怎样？

- 用户用词和文档用词不一致时，召回不全。

### 6.7 如果不用查询分解会怎样？

- 复杂问题只能召回部分相关文档，答案不完整。

### 6.8 如果不用 HyDE 会怎样？

- 短问题和长文档嵌入空间不匹配，检索效果差。

### 6.9 如果不用混合检索会怎样？

- 纯向量检索对关键词不敏感。
- 纯关键词检索对语义不敏感。

### 6.10 如果不用迭代检索会怎样？

- 单轮检索可能不够，复杂问题需要多轮。

### 6.11 如果不用自适应检索会怎样？

- 简单问题也检索，浪费算力。
- 复杂问题不检索，答案不准。

## 7. 标失效

### 7.1 RAG 不改变模型的行为习惯

RAG 只提供知识，不改变模型的行为模式。  
如果模型本身喜欢编造，RAG 也不能完全解决。

### 7.2 微调不保证事实准确

微调可以让模型学会格式和风格，但不保证事实准确。  
微调后的模型仍然可能幻觉。

### 7.3 RAG 和微调不是互斥选项

两者常组合：

- RAG 补充知识。
- 微调塑造行为。

### 7.4 RAG 不解决推理能力问题

RAG 提供信息，但不提升模型的推理能力。  
如果模型推理能力弱，RAG 也帮不上忙。

### 7.5 RAG 不保证检索质量

检索质量取决于：

- 切块策略
- 嵌入模型
- 召回算法
- 重排模型
- 上下文组织

任何一个环节出问题，RAG 效果都会下降。

### 7.6 检索前增强的标失效

- 查询改写可能引入错误，改写后的问题偏离原意。
- 查询扩展可能引入噪声，召回不相关文档。
- 查询分解可能拆错，子问题不完整。
- HyDE 的假设答案可能错误，导致检索偏差。
- 混合检索需要调权重，权重不当效果反而差。
- 迭代检索可能陷入死循环，需要设置最大轮数。
- 自适应检索的分类器可能判断错误。
- 检索前增强不是万能的，检索质量最终取决于索引和嵌入模型。

## 8. 与前后讲的关联

### 8.1 与第 1 讲（Attention）的关联

第 1 讲：

> Attention 是加权平均。

RAG 的检索可以理解为一种硬注意力：从外部知识库中选择相关文档。

### 8.2 与第 2 讲（交叉熵）的关联

第 2 讲：

> 交叉熵是训练目标。

RAG 生成时，模型仍然在算下一个 token 的概率分布。  
检索内容被塞进上下文，影响这个分布。

### 8.3 与第 5 讲（缩放定律）的关联

第 5 讲：

> 缩放定律只优化预训练 loss。

RAG 不改变预训练 loss，但改变推理时的上下文。

### 8.4 与第 6 讲（KV-Cache）的关联

第 6 讲：

> 长上下文 KV-Cache 大。

RAG 需要长上下文，KV-Cache 是瓶颈。  
需要 GQA、量化等技术来支持长上下文。

### 8.5 与第 7 讲（SFT/RLHF/DPO）的关联

第 7 讲：

> 对齐让模型学会“怎么回答”。

RAG 让模型知道“回答什么”。  
两者互补。

### 8.6 与第 8 讲（LoRA/量化）的关联

第 8 讲：

> LoRA 可以低成本微调。

可以用 LoRA 微调模型，让它更好地利用 RAG 检索内容。

### 8.7 与第 10 讲（Agent）的关联

第 10 讲：

> Agent 需要规划、工具、记忆。

RAG 是 Agent 的记忆模块之一。  
Agent 可以调用 RAG 作为工具。

### 8.8 检索前增强与第 9 讲主干的关联

第 9 讲主干讲的是：

> chunk → embed → retrieve → rerank → compose → generate

检索前增强是在 **retrieve 之前**加的优化层：

| 主干步骤 | 检索前增强 |
|---|---|
| chunk | 父子索引、摘要索引、元数据 |
| embed | 多向量索引、HyDE |
| retrieve | 混合检索、多路召回、迭代检索、自适应检索 |
| rerank | 去重、压缩、过滤 |

所以完整的 RAG 链路应该是：

```
查询理解 → 索引增强 → 检索策略 → 重排前处理 → 重排 → 组织 → 生成
```

## 9. 四关学习法

### 9.1 费曼关：讲给一个没学过 RAG 的人

> 模型不知道的事，怎么让它知道？  
> 答案是 RAG：先从外部知识库检索相关信息，塞进上下文，让模型基于检索内容生成。  
> 链路是：切块 → 嵌入 → 召回 → 重排 → 组织 → 生成。  
> 难点不在向量库选型，在切块策略、重排、上下文组织。  
> 五种失败模式：切块切断语义、嵌入对否定/数字不敏感、召回正确但排序靠后、上下文太长迷失在中间、模型无视检索内容编答案。  
> RAG 补充知识，微调塑造行为。  
> 两者常组合，不是互斥选项。  
> 检索前还有大量增强手段：查询改写、扩展、分解、多查询生成、HyDE、路由。  
> 索引增强：混合索引、元数据、摘要索引、父子索引。  
> 检索策略：混合检索、多路召回、迭代检索、自适应检索。  
> 重排前处理：去重、压缩、过滤。  
> 这些手段直接影响召回质量。  
> 没有它们，RAG 效果会大打折扣。

### 9.3 第一性原理关：合上书，从零推

从问题出发：

> 模型不知道的事，怎么让它知道？  
> 参数化记忆有四个局限：知识截止、不可更新、不可溯源、幻觉。  
> RAG 在推理时检索外部知识，塞进上下文。  
> 链路：chunk → embed → retrieve → rerank → compose → generate。  
> 难点：切块策略、重排、上下文组织。  
> 五种失败模式：切块切断语义、嵌入不敏感、排序靠后、迷失中间、无视检索。  
> RAG 补充知识，微调塑造行为。  
> 两者常组合，不是互斥选项。  
> 检索质量取决于查询和文档的匹配程度。

> 查询扩展让查询覆盖更多相关词。

> 混合检索兼顾关键词和语义。  
> 多路召回提高覆盖率。  
> 迭代检索多轮优化。  
> 自适应检索按需检索。

### 9.4 预测实验关

1. 切块太粗，检索噪声大。
2. 切块太细，语义不完整。
3. 嵌入模型对否定不敏感，语义相反句子嵌入接近。
4. 召回正确但排序靠后，top-k 截断丢失正确文档。
5. 上下文太长，中间信息被忽略。
6. 模型无视检索内容，仍然凭参数知识回答。
7. RAG 和微调组合，效果优于单独使用。
8. RAG 不改变模型行为习惯。
9. 加查询改写，召回率提升。
10. 加查询扩展，召回率提升但可能引入噪声。
11. 加 HyDE，短问题检索效果提升。
12. 加混合检索，关键词和语义都覆盖。
13. 加多路召回，覆盖率提升。
14. 加迭代检索，复杂问题效果提升。
15. 加自适应检索，简单问题省算力。

## 13. 最终一句话总结

第 9 讲的核心不是“RAG 是什么”，而是：

> 参数化记忆有四个局限：知识截止、不可更新、不可溯源、幻觉。  
> RAG 在推理时检索外部知识，塞进上下文，让模型基于检索内容生成。  
> 链路：chunk → embed → retrieve → rerank → compose → generate。  
> 难点不在向量库选型，在切块策略、重排、上下文组织。  
> 五种失败模式：切块切断语义、嵌入对否定/数字不敏感、召回正确但排序靠后、上下文太长迷失在中间、模型无视检索内容编答案。  
> 检索前还有大量增强手段：查询改写、扩展、分解、多查询生成、HyDE、路由。  
> 索引增强：混合索引、元数据、摘要索引、父子索引。  
> 检索策略：混合检索、多路召回、迭代检索、自适应检索。  
> 重排前处理：去重、压缩、过滤。  
> 这些手段直接影响召回质量。

> RAG 补充知识，微调塑造行为。  
> 两者常组合，不是互斥选项。

这就是杠杆点 #9：

> 没有 RAG，模型只能靠参数化记忆，事实性差、更新慢、不可溯源。  
> 有了 RAG，模型可以访问最新、可更新、可溯源的知识。  
> 但 RAG 不是万能药，五种失败模式需要逐一解决。  
> 检索前增强是提升 RAG 效果的关键手段。
